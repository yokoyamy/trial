# アンケート業務運営アプリ 実装要件
# 全差し替え版

---

## 1. 基本方針

本アプリは、アンケート運営者が以下の業務を一連の流れとして実行できるものとする。

- アンケートの作成
- アンケートの編集
- アンケートの保存
- アンケート内容の確認
- アンケートの公開
- アンケートの終了
- 顧客一覧の取得
- 送信対象者の選択
- メール内容の作成・確認
- アンケートメールの送信
- 送信結果の確認
- 回答の受付
- 回答状況の確認
- 回答結果の確認
- 回答結果の集計
- メール送信設定
- kintone接続設定

画面上だけで処理を完了したように見せず、
サーバー側で正式なデータを保存・更新した結果を画面へ反映する。

---

# 2. 動作環境

以下の環境で動作すること。

- Apache 2.4
- PHP 8.4 / 8.5
- Windows / Unix
- データベースを使用しない
- HTML / CSS / JavaScript / PHPを1つのindex.phpに格納する
- 永続データはアプリルート配下へ保存する
- 永続データの保存形式はJSONとする
- 文字コードはUTF-8とする
- cURLは使用しない

PHPから外部サービスへ通信する場合は、
stream_context_create() と file_get_contents() を使用する。

---

# 3. Webページの実行環境

index.phpはApacheからHTTPまたはHTTPSのWebページとして提供する。

以下の実行方法は動作対象外とする。

- file://による直接表示
- data: URLによる表示
- sandboxによって通常の同一オリジンが無効になったiframe
- Originがnullとなるその他の実行環境

index.php自身のAPIを利用する場合は、
現在表示しているindex.phpを基準として通信先を決定する。

別ホスト、別ポート、別スキームの固定URLを
アプリ内部APIの通信先として使用しない。

本アプリ内部のAPIについて、
任意の外部Originから利用できるようなCORS設定は行わない。

---

# 4. アプリ内APIの基本方針

画面からサーバーへ要求する処理は、
現在表示しているindex.phpに対して行う。

すべてのAPI要求には操作内容を識別できるactionを指定する。

状態を変更する処理はPOSTを使用する。

主なactionは以下とする。

- get_settings
- save_mail_settings
- test_mail_settings
- save_kintone_settings
- test_kintone_connection
- refresh_customers
- get_customers
- get_surveys
- get_survey
- save_survey
- delete_survey
- publish_survey
- close_survey
- get_send_data
- send_survey
- get_send_history
- get_response_status
- get_response_results
- save_response
- get_public_survey

画面上で使用しないactionは実装しない。

---

# 5. JSONファイル構成

アプリルート配下にdataディレクトリを設ける。

基本構成は以下とする。

    data/
    ├─ settings.json
    ├─ customers.json
    ├─ surveys.json
    ├─ responses.json
    └─ sends.json

必要に応じて一時保存用の領域を使用できるが、
一時ファイルを正式なデータとして扱ってはならない。

必要なディレクトリ・ファイルが存在しない場合は、
初回起動時に安全な初期状態として作成できるものとする。

---

# 6. JSON保存の共通ルール

JSONへの保存は、複数の処理が同時に実行されても
データが壊れないようにする。

保存時には以下を必須とする。

- 排他制御を行う
- 保存前に現在のJSONを正常に読み込めることを確認する
- JSONとして正しい形式で保存する
- 保存途中で既存データが壊れないようにする
- 保存失敗時に既存データを破壊しない
- 保存後に保存したJSONを再読み込みする
- 再読み込みした内容が正しいことを確認する
- 保存成功を確認してから成功レスポンスを返す

JSONの読み込みに失敗した場合は、
破損したデータを正常データとして上書きしてはならない。

---

# 7. データの正規性

正式なデータの優先順位を以下とする。

1. サーバー側JSON
2. サーバーから取得したAPIレスポンス
3. 現在画面に入力されている未保存データ
4. ブラウザに残っている一時状態

localStorage等に残った以前の画面状態を、
サーバーに保存されたデータより優先してはならない。

---

# 8. データID

アンケート、グループ、質問、選択肢、回答、送信記録には、
それぞれデータを一意に識別できるIDを持たせる。

表示番号と内部IDを分離する。

質問番号は、

- 全体で通番
- グループごとの番号

の表示方法に従って画面上で生成する。

質問の追加・削除・並べ替えによって
表示番号が変わっても、質問自体のIDは変更しない。

---

# 9. settings.json

設定情報は以下の2系統を保持する。

- mail
- kintone

基本構造は以下とする。

    {
      "mail": {
        "smtp_server": "",
        "smtp_port": 587,
        "security": "STARTTLS",
        "auth_enabled": true,
        "username": "",
        "password": "",
        "from_address": "",
        "from_name": "",
        "configured": false,
        "verified": false,
        "updated_at": ""
      },
      "kintone": {
        "domain": "",
        "app_id": "",
        "login_name": "",
        "password": "",
        "proxy_host_port": "",
        "proxy_enabled": false,
        "ssl_verify": false,
        "configured": false,
        "verified": false,
        "updated_at": ""
      }
    }

パスワードは画面やAPIレスポンスへ返さない。

---

# 10. パスワードの保持

設定画面のパスワード欄は、
保存済みパスワードそのものを表示しない。

パスワード欄が空欄の場合は、
既存パスワードを保持する。

パスワードを変更する場合だけ新しい値へ変更する。

パスワードを画面表示用の伏字文字列として
保存済みデータに書き戻してはならない。

例として、

    ********

を実際のパスワードとして保存してはならない。

---

# 11. メール設定

メール設定では以下を入力できる。

- SMTPサーバ
- ポート番号
- 接続方式
- 認証を使用するか
- 認証ユーザー名
- 認証パスワード
- 送信元メールアドレス
- 送信元名

接続方式は以下のみとする。

- なし
- STARTTLS
- SSL/TLS

---

# 12. メール設定の入力検証

サーバー側で以下を検証する。

- SMTPサーバが入力されている
- ポート番号が有効な範囲である
- 接続方式が許可された値である
- 送信元メールアドレスが正しい形式である
- 認証を使用する場合はユーザー名が入力されている
- 認証を使用する場合はパスワードが設定されている
- 各文字列が許容する最大長を超えていない

画面側の検証だけを信用してはならない。

---

# 13. メール設定保存

メール設定保存は、

    save_mail_settings

で処理する。

保存対象はmailだけとし、
kintone設定を初期値へ戻してはならない。

保存前にCSRFを検証する。

保存後にsettings.jsonを再読み込みし、
mail設定が正しく保存されたことを確認する。

保存確認に成功した場合だけ成功レスポンスを返す。

設定変更後は以前の接続確認結果を無効にする。

    verified = false

とする。

---

# 14. メール接続確認

「送信設定を確認」は、
保存済みメール設定を使用してSMTPサーバーへの接続を確認する。

単なる入力値チェックだけで
「接続確認済み」としてはならない。

接続確認成功時だけ、

    verified = true

とする。

接続確認失敗時は、

    verified = false

とする。

接続確認結果にはパスワードや認証情報を含めない。

---

# 15. メール設定状態

メール設定は以下の状態を区別する。

- 未設定
- 設定済み
- 接続確認済み
- 接続エラー

「設定済み」と「接続確認済み」を同一状態として扱わない。

設定変更後は「接続確認済み」の状態を維持しない。

---

# 16. kintone設定

kintone設定では以下を入力できる。

- 利用先
- 顧客管理アプリID
- ログイン名
- パスワード
- プロキシ設定

APIトークンは使用しない。

認証はkintoneのログイン名・パスワードを使用する。

---

# 17. kintone利用先

以下の入力を許容する。

    example

    example.cybozu.com

    https://example.cybozu.com

入力値を共通の処理で正規化し、
正しいkintone URLを生成する。

以下の重複を発生させてはならない。

    https://https://example.cybozu.com

    example.cybozu.com.cybozu.com

URL生成処理はアプリ内で統一する。

---

# 18. kintoneプロキシ

プロキシは任意設定とする。

入力形式は、

    host:port

とする。

プロキシ設定が入力されている場合は、
kintoneへのすべての通信で同じプロキシ設定を使用できるようにする。

プロキシ認証は使用しない。

プロキシのユーザー名・パスワード入力欄は設けない。

---

# 19. kintone通信

kintone通信にはcURLを使用しない。

以下を使用する。

- stream_context_create()
- file_get_contents()

SSL証明書検証は無効固定とする。

設定画面からSSL検証を変更する項目は設けない。

---

# 20. kintone通信の共通化

kintoneへのすべての通信は、
同じ通信ルールを使用する。

すべてのkintone通信で、
その処理に必要なプロキシ設定を受け取れる構成とする。

プロキシが設定されている場合は、

- proxy
- request_fulluri = true

を適用する。

プロキシが設定されていない場合は、
通常の通信を行う。

---

# 21. kintone認証

認証には、

    X-Cybozu-Authorization

を使用する。

Base64化する対象は、

    trim(ログイン名) . ":" . trim(パスワード)

とする。

APIトークンは使用しない。

以下を画面・ログ・APIレスポンスへ出力してはならない。

- パスワード
- Authorizationヘッダー
- Base64化された認証情報

---

# 22. kintone GET通信

GETではパラメータをURLへ付与する。

クエリ文字列は、

    http_build_query($params, '', '&', PHP_QUERY_RFC3986)

を使用する。

GET通信ではリクエスト本文を送信しない。

GET用の通信にcontentを設定しない。

---

# 23. kintone POST / PUT通信

POST / PUTではJSON形式でデータを送信する。

JSONは、

    json_encode($data, JSON_UNESCAPED_UNICODE)

を使用する。

Content-Typeは、

    application/json

とする。

---

# 24. kintoneエラー

kintoneからエラーが返った場合は、
可能な範囲で以下を利用者へ表示できるようにする。

- HTTPステータス
- kintoneエラーコード
- kintoneメッセージ
- 利用者が確認すべき設定

ただし以下は表示しない。

- パスワード
- 認証情報
- CSRFトークン
- セッション情報
- Authorizationヘッダー
- Base64認証情報

---

# 25. kintone接続確認

「接続設定を確認」は、
保存済み設定を使用して実際にkintoneへ接続する。

使用する確認先は以下のいずれかとする。

    /k/v1/apps.json?limit=1

または顧客管理アプリIDが設定されている場合、

    /k/v1/app.json?id={app_id}

を使用する。

実際の通信に成功した場合だけ接続確認済みとする。

---

# 26. kintone設定変更後の状態

kintone設定を変更した場合は、

    verified = false

とする。

変更後に改めて接続確認を行い、
成功した場合だけ、

    verified = true

とする。

---

# 27. 顧客情報

顧客情報はkintoneの顧客管理アプリから取得する。

少なくとも以下を取得できるようにする。

- 顧客ID
- 顧客名
- メールアドレス

必要な顧客情報については、
顧客一覧画面・送信画面で利用できるようにする。

---

# 28. 顧客情報の項目設定

顧客管理アプリの項目名は環境によって異なる可能性がある。

そのため、
顧客名として使用する項目と、
メールアドレスとして使用する項目を明確に設定できるものとする。

項目が設定されていない、
または指定した項目が存在しない場合は、
顧客取得を成功扱いにしない。

---

# 29. customers.json

kintoneから取得した顧客一覧を保存する場合は、

    data/customers.json

へ保存する。

取得日時を保存する。

基本構造は以下とする。

    {
      "updated_at": "",
      "source": "kintone",
      "customers": [
        {
          "id": "",
          "name": "",
          "email": "",
          "fields": {}
        }
      ]
    }

顧客情報を取得できなかった場合、
以前の顧客一覧を最新データとして扱わない。

ただし、取得失敗だけを理由に既存の正常な顧客データを
破壊してはならない。

画面には、

- 最新取得に成功しているか
- 最終取得日時

を判別できる状態を表示する。

---

# 30. アンケートデータ

surveys.jsonにはアンケートを保存する。

アンケートには最低限以下を保持する。

- ID
- アンケート名
- 説明
- 状態
- 作成日時
- 更新日時
- 公開開始日時
- 公開終了日時
- 質問番号形式
- グループ
- 質問
- 選択肢
- 必須／任意
- 分岐設定

状態は以下のみとする。

    draft
    open
    closed

---

# 31. グループ

グループには一意なIDを持たせる。

グループには、

- ID
- グループ名
- 表示順
- 質問一覧

を保持する。

グループの追加・削除・並べ替えが可能であること。

---

# 32. 質問

質問には一意なIDを持たせる。

質問には、

- ID
- 質問文
- 回答形式
- 必須／任意
- 表示順
- 選択肢
- 分岐設定

を保持する。

回答形式は以下の3種類だけとする。

- 自由記述
- 単一選択
- 複数選択

その他の回答形式は受け付けない。

---

# 33. 選択肢

単一選択・複数選択には、
選択肢ごとに一意なIDを持たせる。

選択肢には、

- ID
- 表示名
- 表示順

を保持する。

選択肢の表示名が空欄の場合は保存しない。

---

# 34. 質問番号

質問の内部IDと表示番号を分離する。

質問番号形式として以下を使用する。

- 全体で通番
- グループごとの番号

質問・グループの追加、削除、並べ替え時には、
画面上の番号を自動更新する。

保存データには、
表示番号だけを質問識別情報として使用しない。

---

# 35. 分岐設定

分岐は単一選択質問についてのみ設定できる。

選択肢ごとに、

- 次の質問
- 指定した質問
- アンケート終了
- 分岐なし

を設定できる。

分岐先は質問IDで管理する。

---

# 36. 分岐の整合性

分岐先として存在しない質問IDを保存してはならない。

質問削除によって分岐先が存在しなくなった場合は、
保存を拒否する。

質問の並べ替えによって内部IDを変更してはならない。

分岐による循環が発生する場合は、
公開前に検出して公開を拒否する。

アンケート開始から終了まで、
到達不能な状態にならないことを確認する。

---

# 37. アンケート保存

アンケート保存は、

    save_survey

で処理する。

保存時にはサーバー側で以下を再確認する。

- CSRF
- アンケートID
- アンケート名
- 説明
- グループ
- 質問
- 回答形式
- 選択肢
- 必須設定
- 分岐設定
- 質問番号形式
- 公開期間
- 状態
- データ構造

画面側だけの検証で保存成功としてはならない。

---

# 38. アンケート状態変更

状態変更はサーバー側で行う。

状態変更時には、
現在の状態と変更可能な状態を確認する。

基本的な遷移は以下とする。

    draft → open
    open → closed

closedからopenへ戻す操作は、
業務要件で明示されない限り提供しない。

draftのみ削除可能とする。

---

# 39. 公開前検証

公開前には必ずサーバー側で再検証する。

以下を確認する。

- アンケート名が存在する
- グループが1つ以上存在する
- グループ名が存在する
- 質問が1つ以上存在する
- 質問文が存在する
- 回答形式が許可された値である
- 単一選択・複数選択では選択肢が存在する
- 選択肢名が存在する
- 必須設定が正しい
- 分岐先が存在する
- 不正な分岐循環がない
- 公開期間が正しい
- 公開開始日時と終了日時の関係が正しい

検証に失敗した場合は公開しない。

---

# 40. 公開期間

公開開始日時・公開終了日時を保存する。

公開期間が設定されている場合、
現在日時との関係によって回答可能かどうかを判定する。

公開期間外は回答を受け付けない。

管理画面上の状態と、
実際に回答可能かどうかの判定を一致させる。

---

# 41. 公開URL

公開中アンケートには、
回答者がアクセスできる回答用URLを生成する。

URLにはアンケートを識別するための情報を含める。

回答者はそのURLから回答画面へアクセスできる。

回答画面から管理画面へ戻るためのリンクを設けない。

---

# 42. 回答者画面

回答者画面では、

- 運営者向けヘッダー
- 管理メニュー
- 設定画面へのリンク
- 管理画面への戻るボタン

を表示しない。

公開中かつ回答可能なアンケートだけを表示する。

下書き・終了済み・公開期間外のアンケートは回答できない。

---

# 43. 回答者の識別

回答には、
顧客一覧に存在するかどうかに関係なく、
回答を識別できる情報を保持する。

顧客から送信された場合は、
送信対象者との関連を保持できるようにする。

顧客一覧に存在しない回答者からの回答も受け付ける。

顧客登録の有無を理由として回答を拒否しない。

---

# 44. 回答データ

responses.jsonには最低限以下を保存する。

- 回答ID
- アンケートID
- 回答者識別情報
- 関連する顧客ID（存在する場合）
- 回答開始日時
- 回答完了日時
- 回答完了状態
- 質問ID
- 回答内容
- 保存日時

回答内容は質問IDと関連付けて保存する。

質問番号だけを回答との関連付けに使用しない。

---

# 45. 回答入力のサーバー側検証

回答送信時にはサーバー側で再検証する。

以下を確認する。

- 対象アンケートが存在する
- 対象アンケートが回答可能な状態である
- 質問IDが存在する
- 質問IDが対象アンケートに属している
- 回答形式が一致している
- 必須質問が回答されている
- 選択肢IDが存在する
- 選択肢IDが対象質問に属している
- 複数選択の値が許可された選択肢だけで構成されている
- 自由記述の長さが上限以内である
- 分岐によって回答対象となった質問のみを有効な回答として扱う

画面側の検証だけを信用しない。

---

# 46. 回答の二重送信防止

回答送信には一意な送信識別情報を使用する。

同じ送信識別情報による再送信は、
同じ回答を二重登録しない。

送信処理が完了した後に
同じ回答を再度送信した場合は、
新しい回答として登録しない。

---

# 47. 回答の途中状態

回答開始後、最後まで回答せずに終了した場合と、
正式に回答を送信した場合を区別できるようにする。

集計対象は完了した回答とする。

未完了の回答を正式な回答数へ含めない。

---

# 48. 送信記録

メール送信の結果をsends.jsonへ保存する。

送信記録には最低限以下を保持する。

- 送信記録ID
- アンケートID
- 送信日時
- 件名
- 本文
- 送信対象者数
- 成功数
- 失敗数
- 対象者ごとの送信結果

対象者ごとの送信結果には、

- 顧客ID
- 顧客名
- メールアドレス
- 送信状態
- エラー内容

を保持できるものとする。

SMTPパスワードや認証情報は保存しない。

---

# 49. 送信対象者

送信画面ではkintoneから取得した顧客一覧を利用する。

以下を行えるようにする。

- 顧客検索
- 顧客選択
- 複数選択
- 選択解除
- 選択した顧客の確認

送信対象者が0人の場合は送信できない。

---

# 50. 顧客メールアドレス

送信対象者のメールアドレスをサーバー側でも再確認する。

不正なメールアドレスを送信処理へ渡さない。

顧客一覧に表示されていることだけを理由として、
メールアドレスを正しいものとして信用しない。

---

# 51. メール内容

送信画面では以下を入力・確認できる。

- 件名
- 本文
- 回答用の案内

回答用の案内には、
回答者がアンケートへアクセスするためのURLを含める。

件名・本文は送信前にサーバー側で再確認する。

---

# 52. メール送信前チェック

メール送信開始前にサーバー側で以下を再確認する。

- 対象アンケートが存在する
- 対象アンケートが公開中である
- 公開期間内である
- メール設定が存在する
- 必須メール設定が存在する
- 必要な場合は接続確認済みである
- 送信対象者が1人以上いる
- 送信先メールアドレスが妥当である
- 件名が入力されている
- 本文が入力されている
- 回答用URLが対象アンケートと一致している

画面側だけのチェックを信用して送信しない。

---

# 53. メール送信確認

送信実行前に確認画面を表示する。

以下を確認できるようにする。

- アンケート名
- 送信対象者数
- 送信対象者
- 件名
- 本文
- 回答用案内

確認画面で明示的に送信を確定してから送信する。

---

# 54. メール送信

メール送信は保存済みメール設定を使用する。

送信処理開始後は、
同じ送信操作を重複して開始しない。

送信処理中に同一アンケート・同一対象者への
重複送信が発生しないようにする。

---

# 55. メール送信結果

送信完了後は、

- 対象者数
- 成功数
- 失敗数
- 失敗対象者
- 送信日時

を確認できるようにする。

一部失敗の場合も、
全体を失敗扱いにして成功分の記録を失わない。

---

# 56. メール再送

失敗対象者を確認できるようにする。

再送する場合は、
前回失敗した対象者だけを選択できるようにする。

成功済みの対象者を誤って再送することを防止する。

再送結果は新しい送信記録として保存する。

---

# 57. 回答状況

回答状況画面では、
対象アンケートだけの情報を表示する。

以下を表示する。

- 回答数
- 回答率
- 未回答数
- 公開期間
- 回答状況の推移
- メール送信対象者数
- メール送信済み数
- 未回答者数

アンケート一覧には、
このダッシュボードを表示しない。

---

# 58. 回答率の定義

回答率の計算方法を明確にする。

基本的には、

    回答完了者数 ÷ メール送信対象者数 × 100

とする。

ただし、顧客一覧に登録されていない回答者については
送信対象者数に含めない。

顧客一覧に存在しない回答者からの回答は、
総回答数・回答者数には含めるが、
送信対象者を分母とする回答率には含めない。

送信対象者が0人の場合は、
回答率を0%とするのではなく、
「算出対象なし」と表示する。

---

# 59. 未回答者

未回答者は、

    送信対象者
    －
    完了回答が確認できた送信対象者

として扱う。

回答者と送信対象者を関連付けられない場合は、
未回答者数を推測して補完しない。

---

# 60. 回答状況の推移

回答状況の推移を表示するため、
回答完了日時を保存する。

日別・日時別など画面で必要な単位に集計できるようにする。

過去の回答記録を現在の状態へ書き換えない。

---

# 61. 回答結果

回答結果画面では対象アンケートだけを集計する。

以下を表示する。

- 総回答数
- 回答者数
- 質問ごとの回答状況

顧客一覧に存在しない回答者も集計対象とする。

---

# 62. 単一選択の集計

単一選択では選択肢ごとに、

- 回答数
- 割合

を表示する。

割合の分母を明確にし、
回答数と一致するデータを使用する。

---

# 63. 複数選択の集計

複数選択では選択肢ごとに、

- 選択回数
- 割合

を表示する。

1人が複数選択した場合、
選択された各選択肢をそれぞれ集計する。

複数選択の割合については、
集計画面で分母を明確に表示する。

合計が100%を超える場合があることを前提とする。

---

# 64. 自由記述の集計

自由記述では、
回答内容を一覧表示する。

回答内容をHTMLとしてそのまま画面へ出力しない。

---

# 65. 削除

削除できるのは下書きアンケートだけとする。

公開中または終了済みアンケートを削除する操作は提供しない。

削除前に確認を行う。

削除対象に質問・回答・送信履歴が存在する場合の扱いを明確にする。

下書きには通常回答・送信履歴が存在しないことを前提とし、
存在する場合は削除を拒否する。

---

# 66. 終了

公開中アンケートだけ終了できる。

終了時にはサーバー側で状態を再確認する。

終了後は回答を受け付けない。

既に保存済みの回答は削除しない。

送信履歴・回答履歴も削除しない。

---

# 67. 同時更新

複数画面から同じアンケートを同時に編集した場合に、
後から保存した画面が無条件で先の変更を消してしまわないようにする。

保存時に更新日時または同等の変更確認情報を使用し、
保存対象データが保存開始時点から変更されている場合は
データ競合として扱えるものとする。

競合が発生した場合は、
利用者へ再読み込み・再確認が必要であることを表示する。

---

# 68. 設定の同時更新

メール設定とkintone設定を同時に保存しても、
互いの設定を消去しない。

メール設定保存ではmailだけ更新する。

kintone設定保存ではkintoneだけ更新する。

---

# 69. セッション

セッションはアプリ固有の領域を使用する。

セッション開始時は、

    session_start([
        'cookie_httponly' => true,
        'cookie_samesite' => 'Lax'
    ]);

を使用する。

セッション直下へ汎用的なキーを作成しない。

本アプリでは例えば、

    $_SESSION['yokoyamy_newapp']

配下を使用する。

---

# 70. CSRF

状態変更を伴うすべての処理でCSRF対策を行う。

対象には以下を含む。

- メール設定保存
- メール接続確認
- kintone設定保存
- kintone接続確認
- 顧客情報更新
- アンケート保存
- アンケート削除
- アンケート公開
- アンケート終了
- メール送信
- 回答保存
- その他状態を変更する処理

セッション開始時に十分な長さのランダムなCSRFトークンを発行する。

画面再表示だけではCSRFトークンを変更しない。

複数タブで同じ画面を開いても正常に操作できるようにする。

---

# 71. CSRFエラー

CSRF検証に失敗した場合は処理を実行しない。

HTTPステータスは403とする。

画面では通常の通信失敗とCSRFエラーを区別できるようにする。

CSRFトークンそのものをエラーメッセージへ表示しない。

---

# 72. JSON APIレスポンス

APIは必ずJSON形式で返す。

成功例：

    {
      "success": true,
      "message": "処理が完了しました。"
    }

失敗例：

    {
      "success": false,
      "message": "入力内容を確認してください。",
      "errors": {}
    }

APIレスポンスにHTMLを混在させない。

JSONレスポンス出力前に既存の出力バッファを破棄する。

Content-Typeは、

    application/json; charset=utf-8

とする。

JSON出力後は必ず処理を終了する。

---

# 73. HTTPステータス

APIでは処理内容に応じて以下を使用する。

- 200: 正常終了
- 400: 入力不正
- 401: 認証失敗
- 403: CSRF等による拒否
- 404: 対象データなし
- 409: データ競合
- 500: サーバー内部エラー
- 502: 外部サービス通信エラー

HTTPステータスだけでなく、
利用者向け日本語メッセージも返す。

---

# 74. fetch通信

fetchによる通信開始時は必ず、

1. 入力値を確認する
2. 対象ボタンをdisabled=trueにする
3. ローディング表示を開始する
4. fetchを開始する

の順番とする。

通信終了時は、

1. 成功・失敗を判定する
2. メッセージを表示する
3. finallyでdisabled=falseにする
4. ローディング表示を解除する

とする。

通信中の二重送信を防止する。

---

# 75. fetchエラー

fetch失敗時に、

    サーバーとの通信に失敗しました。

だけを表示して終了してはならない。

可能な範囲で以下を判定する。

- HTTPステータス
- JSONレスポンスの有無
- APIのmessage
- validation error
- CSRFエラー
- サーバーエラー
- 外部サービス通信エラー

JSONが返らない場合も、
利用者が次に何を確認すればよいか分かる表示にする。

通信失敗時には入力内容を不用意に消去しない。

---

# 76. JavaScript実行位置

すべてのJavaScript処理は、

    document.addEventListener('DOMContentLoaded', ...)

の内部で実行する。

イベントリスナー登録前には対象要素の存在を確認する。

存在しない要素を参照してJavaScript全体が停止する状態を作らない。

---

# 77. XSS対策

PHPからHTMLへ動的値を出力する場合は、
共通エスケープ関数を使用する。

以下の定義を使用する。

    function h(?string $str): string {
        return htmlspecialchars(
            $str ?? '',
            ENT_QUOTES | ENT_SUBSTITUTE,
            'UTF-8'
        );
    }

JavaScriptからDOMへ値を表示する場合は、
原則としてtextContentを使用する。

innerHTMLを使用する場合は、
安全性を確認した値だけを使用する。

アンケート本文、質問文、自由記述回答、顧客名、
メール本文などの利用者入力をHTMLとして実行しない。

---

# 78. PHP名前空間

PHPファイルの先頭には、
本アプリ固有の階層型名前空間を宣言する。

本アプリでは、

    namespace yokoyamy\trial\newapp;

を使用する。

汎用的なnamespace Appなどは使用しない。

ヘルパー関数も同一名前空間へ配置する。

---

# 79. PHP 8.4 / 8.5互換性

PHP 8.4 / 8.5で動作すること。

以下を禁止する。

- `$http_response_header` の直接参照
- PHPの非推奨機能への依存
- 暗黙的なnullable指定
- 型の不整合を前提とした処理

HTTPレスポンスヘッダーは、
安全な共通処理を使用して取得する。

---

# 80. HTTPレスポンスヘッダー

HTTPレスポンスヘッダー取得処理は共通化する。

PHP 8.4 / 8.5対応のため、
`$http_response_header` を直接参照しない。

HTTPステータスを取得できない場合は、
通信失敗として適切に扱う。

---

# 81. 機密情報

以下を画面・ログ・APIレスポンスへ出力しない。

- SMTPパスワード
- kintoneパスワード
- CSRFトークン
- セッションID
- Authorizationヘッダー
- Base64化された認証情報
- プロキシ認証情報
- その他認証に使用する秘密情報

外部サービスから返されたエラー内容に秘密情報が含まれる可能性がある場合も、
そのまま画面へ表示しない。

---

# 82. ログ

エラー調査に必要な情報は記録できるが、
機密情報を記録してはならない。

少なくとも以下をログへ記録しない。

- パスワード
- Authorization
- CSRFトークン
- セッションID
- メール本文に含まれる認証情報
- kintone認証情報

# 83. アンケート編集画面

同じ画面で以下を操作できるようにする。

- 基本情報編集
- グループ追加
- グループ編集
- グループ削除
- グループ並べ替え
- 質問追加
- 質問編集
- 質問削除
- 質問並べ替え
- 選択肢編集
- 必須／任意変更
- 分岐設定

# 84. 未保存変更

アンケート編集中に保存せず別画面へ移動しようとした場合、
未保存の変更があることを利用者へ知らせる。

保存済みデータを誤って未保存状態へ戻さない。

---

# 85. 保存後の画面

アンケート保存成功後も、
現在の編集画面を維持する。

保存成功後はサーバー側の保存結果を正式な状態として扱う。

保存失敗時は、
画面上の入力内容を保持する。

---

# 86. 画面状態とサーバー状態

画面上の表示だけを変更して、
保存成功として扱ってはならない。

正式な保存成功とは、

    サーバー側で保存完了
    ↓
    保存後データを再読み込み
    ↓
    正常に読み込めることを確認

まで完了した状態とする。

---

# 87. エラー表示

利用者向けエラーは、
次に何を確認すればよいか分かる内容とする。

例えば、

    入力内容を確認してください。

    メール設定を保存できませんでした。

    kintoneへ接続できませんでした。
    利用先、アプリID、ログイン情報、プロキシ設定を確認してください。

などとする。

内部処理の詳細や機密情報は表示しない。

# 90. データ整合性

以下のデータ間の関連を維持する。

    アンケート
       ↓
    グループ
       ↓
    質問
       ↓
    選択肢

    アンケート
       ↓
    送信記録
       ↓
    送信対象者

    アンケート
       ↓
    回答
       ↓
    質問
       ↓
    選択肢

IDを使用して関連付ける。

表示名・表示番号を関連付けの正式なキーとして使用しない。

---

# 91. データ削除時の整合性

質問や選択肢を削除する場合、
既存の回答データが参照しているIDを壊さないようにする。

公開後のアンケートでは、
回答結果の意味が変わるような質問削除・選択肢削除を許可しない。

公開済みアンケートを編集する場合の制約を設ける。

少なくとも、

- 回答済み質問の削除
- 回答済み選択肢の削除
- 回答形式の変更

は、既存回答との整合性を確認してから実行する。

---

# 92. 公開済みアンケートの編集

公開中アンケートについて、
回答データの意味を変更する編集を許可しない。

特に以下は制限する。

- 回答形式変更
- 選択肢削除
- 質問削除
- 分岐構造を破壊する変更

業務上変更が必要な場合は、
終了後に編集するか、新しいアンケートとして作成する。

---

# 93. 回答結果の不変性

保存済み回答は、
後からアンケートの表示順が変更されたことだけを理由として
別の質問への回答として扱ってはならない。

回答は質問IDを基準として集計する。

---

# 94. 顧客情報更新と送信履歴

顧客情報がkintone側で更新された場合でも、
過去の送信記録に保存された送信対象者情報を書き換えない。

送信時点の、

- 顧客ID
- 顧客名
- メールアドレス

を送信履歴へ保持する。

これにより、
過去の送信結果を後から確認できるようにする。

---

# 95. 回答者と顧客の関係

顧客から送信されたアンケートへの回答については、
可能な場合は顧客IDと回答を関連付ける。

ただし、
顧客一覧に存在しない回答者についても
回答を保存できる。

顧客情報が後から変更・削除されても、
過去の回答データを失わない。

---

# 96. 自動状態判定

公開期間を設定している場合、
画面表示だけでなく回答受付時にも
現在日時を使用して回答可能か確認する。

公開期間外のアクセスを
公開中として扱わない。

---

# 97. エラー時のデータ保持

保存や通信に失敗した場合、

- 正常に保存済みのデータ
- 現在画面で編集中のデータ

を混同しない。

保存失敗時に、
未保存の画面入力を正式データとして扱わない。

ただし利用者が再送できるよう、
画面上の入力内容は可能な限り保持する。

---

# 98. APIの入力値

APIへ送信された値は、
すべてサーバー側で形式を確認する。

想定外の項目を受け取った場合でも、
その値をそのまま保存データへ混入させない。

特に、

- ID
- 状態
- 回答形式
- 日付
- メールアドレス
- ポート番号
- 選択肢ID
- 分岐先ID

については許可された形式だけを受け付ける。

---

# 99. 文字数制限

利用者が入力する文字列には、
項目ごとに適切な最大長を設定する。

少なくとも以下には上限を設ける。

- アンケート名
- アンケート説明
- グループ名
- 質問文
- 選択肢
- メール件名
- メール本文
- 顧客名
- メールアドレス
- kintone利用先
- ログイン名
- プロキシ設定

上限を超えた値は保存しない。

---

# 100. 日付・時刻

日時はサーバー側で一貫した形式を使用する。

保存する日時にはタイムゾーンを明示する。

画面表示時には、
利用者が理解できる日時形式へ変換する。

公開期間の判定と回答受付判定では、
同じ基準日時を使用する。

---

# 101. 初期データ

初回起動時には、
必要なJSONファイルを正常な空データとして作成できるものとする。

初期状態では、

- メール設定：未設定
- kintone設定：未設定
- 顧客一覧：0件
- アンケート：0件
- 回答：0件
- 送信履歴：0件

として扱う。

---

# 102. 空データ

データが0件の場合もエラーとして扱わない。

以下のように明確に表示する。

- アンケートがありません
- 顧客がありません
- 回答がありません
- 送信履歴がありません

---

# 103. 設定未完了時

メール設定が未完了の場合、
アンケート送信画面では送信操作を開始できない。

kintone設定が未完了の場合、
顧客一覧取得操作を開始できない。

不足している設定画面へ移動できるようにする。

---

# 104. 顧客取得失敗時

kintoneから顧客一覧を取得できなかった場合、
既存の顧客一覧を「今回取得した最新データ」として表示しない。

利用者へ、

- 接続設定を確認する
- kintone接続を確認する
- 必要に応じて再取得する

ことが分かる表示を行う。

---

# 105. APIレスポンスと機密情報

設定取得APIでは、
パスワードそのものを返さない。

代わりに、

    password_configured: true / false

など、
設定済みかどうかだけを返す。

---

# 106. APIレスポンスとデータ量

一覧取得APIでは、
必要以上の情報を返さない。

特に顧客一覧では、
送信に必要のない機密情報を返さない。

設定情報についても、
画面表示に不要な内部情報を返さない。

---

# 107. APIレスポンスの一貫性

すべてのAPIで、

    success

    message

を基本とする。

失敗時には必要に応じて、

    errors

を返す。

画面側がHTTPステータスだけに依存せず、
messageとerrorsを利用して利用者へ案内できるようにする。

---

# 108. 画面遷移

アンケート作成・編集では、
質問ごとに別画面へ移動しない。

個別アンケートを選択した後は、

- アンケート内容
- 送信
- 回答状況
- 回答結果

を切り替えて確認できる。

---

# 109. 回答者画面と管理画面の分離

回答者画面と管理画面を明確に分離する。

回答者用URLへアクセスした場合に、
管理画面のメニューや設定情報を表示しない。

回答者から管理用APIを直接利用できる構成にしない。

---

# 110. 操作完了表示

以下の操作では、
成功・失敗が利用者に明確に分かる表示を行う。

- 保存
- 追加
- 削除
- 公開
- 終了
- 接続確認
- 顧客取得
- メール送信
- 回答送信
- 集計表示

成功していない処理を成功表示しない。

---

# 111. セキュリティヘッダー

以下のレスポンスヘッダーを出力する。

    X-Frame-Options: SAMEORIGIN

    X-Content-Type-Options: nosniff

---

# 112. CORS

本アプリ自身のAPIについて、
任意の外部Originからの利用を許可しない。

以下を設定しない。

    Access-Control-Allow-Origin: *

    Access-Control-Allow-Origin: null

セッションを利用するAPIについて、
外部Originからの利用を前提としない。

Originがnullとなる環境は通常の動作環境外とする。

# 113. 本番コードの構成

本番用index.phpは、

- PHP
- HTML
- CSS
- JavaScript

を1ファイルに格納する。

既存コードの局所修正だけを前提とせず、

- 業務要件
- モック
- 実装要件

を基準として全体の整合性を確保する。

# 115. 特に重要なメール設定保存フロー

メール設定保存は以下がすべて成立して初めて
「保存成功」とする。

    画面入力
      ↓
    画面側入力確認
      ↓
    保存ボタンを即時無効化
      ↓
    ローディング表示
      ↓
    CSRFトークン付きPOST
      ↓
    PHP受信
      ↓
    CSRF検証
      ↓
    サーバー側入力検証
      ↓
    settings.json読み込み
      ↓
    mailだけを更新
      ↓
    JSON保存
      ↓
    保存後JSONを再読み込み
      ↓
    保存結果確認
      ↓
    verified=falseへ更新
      ↓
    JSONレスポンス
      ↓
    画面へ保存成功表示
      ↓
    ボタン再有効化
      ↓
    ローディング解除

途中で失敗した場合は、
「保存成功」として扱わない。

# 119. 最終方針

本アプリは、
「画面が動くこと」だけでは実装完了としない。

以下の3つが一致することを最終条件とする。

    業務要件
       ↓
    モックで確認した操作
       ↓
    本番版で実際に保存・通信・集計される結果

画面上の表示だけが正しく、
サーバー側の正式データが一致しない状態を
完成状態としてはならない。

特に、

- 保存
- 公開
- メール送信
- 回答
- 集計
- 顧客情報
- 接続確認

については、
画面表示・JSONデータ・業務上の状態が一致することを確認する。

# 実装要件

## 1. 目的

本システムは、アンケートの作成・配信・回答・集計を一体で管理するWebアプリケーションとする。

外部のkintone顧客アプリを顧客情報のマスタとして利用できるものとし、本システムの顧客情報との同期を行えるようにする。

実装は以下を正本として整合させる。

- 業務・操作要件
- 参照モック
- 本実装要件

実装上の都合で業務上の操作や意味を変更してはならない。

---

# 2. 実装上の基本方針

## 2.1 構成

- Apache 2.4
- PHP 8.4 / 8.5
- データベースは使用しない
- データはアプリケーションルート直下のJSONファイルで保持する
- 画面とAPIの入口は同一の `index.php`
- 外部通信はPHPの標準機能を使用する
- kintone接続は `stream_context_create()` と `file_get_contents()` を使用する
- cURLは使用しない
- CORSによる回避実装は行わない

## 2.2 データ更新

JSONファイル更新時は以下を必須とする。

- ファイルロックを取得してから読み書きする
- 読み込み失敗時に空データとして扱わない
- JSONが壊れている場合、既存ファイルを空データで上書きしない
- 一時ファイルへ書き込み後、成功時のみ本ファイルへ反映する
- 同時更新による上書きを防止する
- 途中失敗で不完全なJSONを残さない

## 2.3 セッション・CSRF

- POST APIはセッション認証を必須とする
- POST APIはCSRFトークンを必須とする
- セッションCookieはHttpOnlyを有効にする
- SameSiteはLaxとする
- 外部から直接APIを悪用できる設計にしない

## 2.4 セキュリティ

以下を必須とする。

- HTML表示時はエスケープする
- JavaScriptで表示する値は原則として `textContent` を使用する
- HTML文字列を組み立てて外部値を挿入しない
- パスワードを画面へ再表示しない
- SMTPパスワードをAPIレスポンスに含めない
- kintone認証情報をAPIレスポンスに含めない
- `X-Cybozu-Authorization` の値を画面・ログ・エラーにそのまま出さない
- 認証情報をエラーメッセージへ埋め込まない
- セキュリティ関連HTTPヘッダーを設定する
- 外部通信エラー時にサーバー上の物理パスや認証情報を表示しない

## 2.5 PHP 8.5対応

PHP 8.5で動作すること。

HTTPレスポンスヘッダー取得では `$GLOBALS['http_response_header']` に依存せず、PHP 8.4以降で利用可能な `http_get_last_response_headers()` を使用する。

曖昧な関数定義や実行環境依存のフォールバック処理は実装しない。

# 4. アンケートデータ

## 4.1 survey

アンケートは以下の情報を持つ。

- id
- name
- description
- status
- startAt
- endAt
- numberingFormat
- groups
- createdAt
- updatedAt

## 4.2 status

以下のみ許可する。

- draft
- published
- closed

## 4.3 公開状態

公開できるのはバリデーションをすべて通過したアンケートのみとする。

公開時には保存済みデータを再検証する。

画面上で正常に見えていても、サーバー側の公開処理で再検証に失敗した場合は公開しない。

# 5. アンケートグループ・質問

## 5.1 グループ

グループは以下の操作を提供する。

- 追加
- 編集
- 削除
- 並べ替え

## 5.2 質問

質問は以下の操作を提供する。

- 追加
- 編集
- 削除
- 並べ替え

質問形式は以下を対象とする。

- text
- single
- multiple

## 5.3 選択肢

single / multiple の選択肢は以下を満たす。

- choiceIdは一意
- 表示名は必須
- 空文字を禁止
- 同一グループ内のchoiceId重複を禁止
- 削除済みchoiceIdを分岐先として残さない

---

# 6. 分岐

## 6.1 対象

分岐を設定できるのは `single` 質問のみとする。

`text` と `multiple` には分岐を設定しない。

## 6.2 分岐先

分岐先は以下のみ許可する。

- next
- question:<questionId>
- end

## 6.3 分岐バリデーション

保存時および公開時に以下を検証する。

- 指定された質問IDが存在する
- 削除済み質問を参照していない
- 存在しないchoiceIdを参照していない
- 自分自身を直接参照していない
- 分岐経路上に循環が存在しない
- 到達不能な質問を意図せず残していない
- `end` 到達後に別質問へ進まない
- 分岐先が不正な形式でない

循環が存在する場合は公開不可とする。

---

# 7. 顧客データ

## 7.1 customer

顧客データは少なくとも以下を管理する。

- customerId
- name
- email
- status
- createdAt
- updatedAt
- kintoneRecordId
- kintoneUpdatedAt
- syncStatus
- syncError

`kintoneRecordId` はkintone上のレコードと本システムの顧客を対応付ける外部識別子として利用する。

## 7.2 顧客識別

kintoneとの同期ではメールアドレスを主キーとして扱わない。

同期対象の同一性は原則として `kintoneRecordId` で判定する。

メールアドレスが変更された場合でも、同一kintoneレコードであれば同一顧客として更新する。

同一メールアドレスを持つ複数のkintoneレコードを自動統合しない。

---

# 8. kintone接続設定

`settings.json` にkintone接続設定を保持する。

## 8.1 設定項目

- subdomain
- appId
- login
- password
- proxyHostPort
- verifySsl

## 8.2 認証

パスワード認証を利用する。

認証ヘッダーは以下の形式で生成する。

`X-Cybozu-Authorization: Base64(login:password)`

前後の空白は除去する。

ログイン名やパスワードを画面・ログ・同期結果へ表示しない。

## 8.3 URL

サブドメイン設定からkintoneのURLを正規化して生成する。

同一のURL生成方式を全kintone APIで使用する。

## 8.4 GET

GETではJSON本文を送信しない。

クエリパラメーターはRFC3986形式でエンコードする。

## 8.5 POST / PUT

POST / PUTはJSON形式で送信する。

## 8.6 Proxy

proxyHostPortが設定されている場合はstream contextのproxyを利用する。

プロキシ利用時はrequest_fulluriを有効にする。

## 8.7 SSL

SSL証明書検証は設定値に従う。

デフォルトは現行環境要件に合わせて検証OFFとする。

---

# 9. kintone接続確認

設定画面から「kintone接続確認」を実行できること。

接続確認は、単に通信先へ到達できたかだけでなく、指定アプリへのアクセス権を確認できるAPIで実施する。

成功時は一般利用者が理解できるメッセージを画面に表示する。

失敗時は以下を区別して表示する。

- 接続先不正
- 認証失敗
- アプリID不正
- アプリへのアクセス権不足
- 通信失敗
- kintone APIエラー

`X-Cybozu-Authorization` の実値は絶対に表示しない。

ブラウザコンソールへ結果を出すことを利用者向けの結果表示手段にしない。

---

# 10. kintone顧客アプリ同期

## 10.1 同期の基本方針

kintone顧客アプリを外部顧客マスタとし、本システムの顧客データへ同期する。

同期は以下の手順を必須とする。

1. kintone接続設定を確認する
2. 対象アプリIDを確認する
3. kintoneのフィールド定義を取得する
4. 取得したフィールド定義を画面に表示する
5. 本システムの顧客項目とkintone項目をマッピングする
6. マッピング内容をサーバー側で検証する
7. マッピングを保存する
8. 同期前プレビューを実行する
9. 問題がなければ同期を実行する
10. 同期結果を記録する

「接続確認だけをして、フィールド定義を取得せずに同期する」実装は禁止する。

「フィールド名の文字列を推測して自動的に同期する」実装も禁止する。

---

# 11. kintoneフィールド定義取得

## 11.1 API

対象アプリのフィールド定義は以下のAPIから取得する。

`GET /k/v1/app/form/fields.json`

対象アプリIDを必須とする。

取得するフィールド情報は少なくとも以下を保持する。

- field code
- field type
- field label
- 必須設定
- 選択肢情報が存在する場合は選択肢
- 同期可否判断に必要な設定

表示名は画面上の確認用に使用し、実際のマッピング識別子はfield codeを使用する。

## 11.2 取得結果保存

取得したフィールド定義は `kintone_mapping.json` に保存する。

保存情報には以下を含める。

- appId
- fetchedAt
- schemaHash
- fields
- mappings
- syncKey
- updatedAt

## 11.3 schemaHash

取得したフィールド定義から、順序に左右されない決定的なハッシュ値を生成する。

ラベルだけでなく、最低限以下をハッシュ対象とする。

- field code
- field type
- 必要なフィールド設定
- 選択肢

ラベル変更だけでもマッピング確認が必要な場合は、ラベルもハッシュ対象とする。

---

# 12. kintoneフィールドマッピング

## 12.1 マッピングの考え方

マッピングは、

「本システムの顧客項目」
→
「kintoneのフィールドコード」

の対応関係として保持する。

画面上ではkintoneの表示名を使用して分かりやすくする。

保存時は表示名ではなくfield codeを保存する。

## 12.2 必須マッピング

同期に必要な本システム項目について、必須項目が未設定の場合は同期不可とする。

少なくとも顧客名とメールアドレスを同期対象とする場合、それぞれ対応するkintoneフィールドが存在しなければ同期不可とする。

## 12.3 型チェック

以下を必須とする。

- 本システム項目とkintone field typeの組み合わせを検証する
- 未対応のfield typeを自動変換しない
- 読み取り専用フィールドを同期先として扱わない
- ルックアップ等によって値が入力されるだけのフィールドを更新可能項目として扱わない
- 対応不能なfield typeをマッピング候補にしない

## 12.4 自動マッピング

自動マッピングを行う場合でも、最終的な対応関係を画面上で確認できること。

自動推測だけで無条件に同期を開始してはならない。

自動マッピングの優先順位は以下とする。

1. 完全一致するfield code
2. 本システムで明示的に保存済みのmapping
3. それ以外は候補として表示するのみ

表示名の一致だけを確定マッピングの根拠にしない。

---

# 13. マッピング変更検知

kintone側でフィールドが変更された場合、過去のマッピングを無条件に使い続けない。

同期開始前に必ず最新のフィールド定義を取得する。

以下の場合は通常同期を停止する。

- field codeが削除された
- field codeが変更された
- field typeが変更された
- マッピング対象フィールドが利用不可になった
- 必須となるフィールドがなくなった
- schemaHashが前回保存値と一致しない

schemaHashが変更された場合は、

「kintoneの顧客アプリの項目構成が変更されています。フィールドマッピングを確認してください。」

という状態とし、再取得・再マッピング・再保存を要求する。

---

# 14. 同期前プレビュー

同期実行前に、少なくとも以下を表示する。

- 対象件数
- 新規顧客件数
- 更新顧客件数
- 変更なし件数
- 同期対象外件数
- エラー件数
- マッピングエラー
- 値変換エラー
- 必須値不足

プレビューで重大なエラーがある場合は同期ボタンを無効化する。

利用者が明示的に内容を確認してから同期を開始できること。

---

# 15. kintoneレコード取得

## 15.1 件数制御

大量データ取得を前提とする。

1回のレコード取得に依存してはならない。

500件を超える場合は分割取得する。

10,000件を超えるデータを取得する場合はoffset方式に依存せずカーソル方式を使用する。

## 15.2 取得対象

同期に必要なフィールドのみを取得する。

保存済みmappingに含まれるfield codeを取得対象にする。

## 15.3 取得エラー

途中の取得に失敗した場合、同期を成功扱いにしない。

一部だけ顧客データを書き込んだ状態を成功として扱わない。

---

# 16. 同期処理

## 16.1 更新対象

マッピングされている項目のみ更新する。

マッピングされていない本システム側の項目は保持する。

## 16.2 空値

マッピング対象のkintoneフィールドが空の場合、その値を本システム側にも反映する。

ただし、同期前プレビューで空値による更新件数を確認できること。

## 16.3 新規

`kintoneRecordId` が本システムに存在しない場合は新規顧客として登録する。

## 16.4 更新

`kintoneRecordId` が存在する場合は対応する顧客を更新する。

## 16.5 削除

kintone上で削除された顧客を本システムから物理削除しない。

アンケート回答履歴や過去の配信履歴との整合性を保持するため、必要に応じて非アクティブとして管理する。

過去の回答データを顧客削除によって失わない。

## 16.6 重複

同一 `kintoneRecordId` が複数顧客に登録されている状態が検出された場合は同期エラーとする。

メールアドレスだけが一致する別kintoneレコードを自動統合しない。

---

# 17. 同期ログ

`kintone_sync_logs.json` に同期実行結果を保存する。

最低限以下を記録する。

- syncId
- startedAt
- finishedAt
- appId
- schemaHash
- mappingVersion
- totalCount
- createdCount
- updatedCount
- unchangedCount
- inactiveCount
- skippedCount
- errorCount
- status
- errorSummary

認証情報および個人情報を必要以上にログへ保存しない。

---

# 18. 同期の二重実行防止

同期処理の同時実行を防止する。

同時に2つの同期を実行できないこと。

同期中は画面上に実行中状態を表示する。

ブラウザを複数開いた場合でも、サーバー側で二重実行を防止する。

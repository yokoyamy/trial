# アンケート業務運営アプリ 実装要件
全体改訂版

---

## 1. 基本方針

本アプリは、アンケート運営に必要な以下の業務を一つのアプリで管理する。

- アンケートの作成・編集・削除
- アンケートの公開・終了
- 顧客一覧の取得
- アンケートのメール送信
- 回答受付
- 回答状況の確認
- 回答結果の集計
- メール送信設定
- kintone接続設定

動作環境は以下とする。

- Apache 2.4
- PHP 8.4 / 8.5
- Windows / Unix
- データベースは使用しない
- HTML / CSS / JavaScript / PHP は1つの index.php に格納する
- 永続データはアプリルート配下のJSONファイルへ保存する
- 文字コードはUTF-8とする

---

## 2. 画面の利用方法と通信方式

### 2.1 本番画面の利用

本アプリはApache上で公開された `index.php` をブラウザから開いて利用する。

HTMLファイルとして保存したものを直接ブラウザで開く `file://` 形式での利用を正式な動作対象としない。

以下のような利用方法は禁止する。

- index.phpをローカルファイルとして直接開く
- HTMLをファイルとして保存して直接開く
- `file://` を起点として本アプリの保存処理を呼び出す

本アプリは必ずApacheから提供されたWebページとして利用する。

### 2.2 画面と保存処理の関係

画面表示とデータ保存は、原則として同一の `index.php` が処理する。

ブラウザから保存処理を呼び出す場合も、別ドメイン・別サイトのURLを使用しない。

API通信先は、現在表示している本アプリ自身のURLを基準として生成する。

固定した別ホスト名・別ドメインのAPI URLを画面側へ埋め込まない。

### 2.3 CORS

本アプリは同一サイト内で画面と保存処理を完結させるため、通常の業務処理にCORSを必要としない。

以下を禁止する。

- 別ドメインへのAPI送信を前提とする
- 別オリジンからの保存処理を前提とする
- CORSを有効にすることで同一サイト構成の問題を回避する

特に、画面を `file://` から開いた結果として発生するCORSエラーを、サーバー側で無条件に許可して解決してはならない。

### 2.4 API通信先

JavaScriptから本アプリ自身へ通信する場合は、現在表示しているページを基準としたURLを使用する。

通信先に以下を固定記述しない。

- 開発用ホスト名
- 本番用ホスト名
- IPアドレス
- 開発環境専用URL

これにより、Apache上の配置場所が変更されても本アプリ自身への通信が成立する構成とする。

## 3. データ保存

### 3.1 保存ファイル

以下のJSONファイルを使用する。

    data/
    ├─ customers.json
    ├─ settings.json
    ├─ surveys.json
    ├─ responses.json
    └─ mail_logs.json

必要なディレクトリ・ファイルが存在しない場合は、アプリ初回起動時に安全に作成できるものとする。

JSONファイルはUTF-8で保存する。

### 3.2 JSONファイルの役割

#### customers.json

kintoneから取得した顧客一覧を保存する。

#### settings.json

メール送信設定とkintone設定を保存する。

#### surveys.json

アンケートの定義、公開状態、質問、選択肢、分岐等を保存する。

#### responses.json

回答データを保存する。

#### mail_logs.json

アンケートのメール送信履歴を保存する。

---

## 4. JSON保存の基本ルール

JSONへの保存は、複数の処理が同時に実行されてもデータが壊れないようにする。

保存処理では以下を必須とする。

- 排他制御を行う
- JSONとして正しく保存する
- 保存途中で既存データが壊れないようにする
- 保存失敗時は既存データを破壊しない
- 保存成功後に保存結果を確認する
- 保存失敗時は画面に原因を表示できる情報を返す
- パスワード等の機密情報をレスポンスに含めない

### 4.1 同時更新

JSONを読み込んで内容を変更して保存する処理については、読み込みから保存完了までを同時更新から保護する。

単にファイルを書き込む瞬間だけを保護するのではなく、

    読み込み
      ↓
    内容確認
      ↓
    内容変更
      ↓
    保存
      ↓
    保存結果確認

を一連の更新処理として扱う。

同時更新によって他の利用者の変更を不用意に上書きしてはならない。

---

## 5. JSONファイルの破損対策

JSONファイルを読み込む際は、以下を確認する。

- JSONとして正しく解析できる
- 必須項目が存在する
- 配列であるべき項目が配列である
- オブジェクトであるべき項目がオブジェクトである
- 数値項目が数値である
- 文字列項目が文字列である
- 真偽値項目が真偽値である
- IDが重複していない

破損したJSONを正常なデータとして扱わない。

破損したJSONをそのまま上書き保存してはならない。

既存データの読み込みに失敗した場合、初期値で既存データを上書きしてはならない。

## 6. settings.json

メール送信設定とkintone設定を1つの設定データとして保存する。

基本構造は以下とする。

    {
      "mail": {
        "smtp_server": "",
        "smtp_port": 587,
        "security": "STARTTLS",
        "username": "",
        "password": "",
        "from_address": "",
        "from_name": "",
        "configured": false,
        "verified": false,
        "updated_at": ""
      },
      "kintone": {
        "domain": "",
        "app_id": "",
        "login_name": "",
        "password": "",
        "proxy_host_port": "",
        "proxy_enabled": false,
        "ssl_verify": false,
        "configured": false,
        "verified": false,
        "updated_at": ""
      }
    }

実際の保存形式では、パスワードを画面やAPIレスポンスへ返してはならない。

画面再表示時には保存済みパスワードを表示しない。

設定画面のパスワード欄を空欄にした場合、既存パスワードを不用意に消去しない。

パスワードを変更する場合だけ新しい値を保存する。

## 7. 設定保存の部分更新

メール設定を保存する場合は、mailだけを更新する。

kintone設定を保存する場合は、kintoneだけを更新する。

対象外の設定を初期値へ戻してはならない。

例えば、

    メール設定保存
    ↓
    mailだけ更新
    ↓
    kintone設定は保持

とする。

同様に、

    kintone設定保存
    ↓
    kintoneだけ更新
    ↓
    mail設定は保持

とする。

## 8. メール送信設定

### 8.1 設定項目

以下を設定できる。

- SMTPサーバ
- ポート番号
- 接続方式
- 認証ユーザー名
- 認証パスワード
- 送信元メールアドレス
- 送信元名

接続方式は以下とする。

- なし
- STARTTLS
- SSL/TLS

### 8.2 必須項目

以下は必須とする。

- SMTPサーバ
- ポート番号
- 送信元メールアドレス

SMTP認証を使用する場合は、

- 認証ユーザー名
- 認証パスワード

を必須とする。

### 8.3 入力制限

SMTPサーバ名には適切な最大長を設定する。

送信元名には適切な最大長を設定する。

ユーザー名には適切な最大長を設定する。

メールアドレスには適切な最大長を設定する。

ポート番号は1～65535の範囲とする。

許可されていない接続方式は保存しない。

## 9. メール設定保存API

メール設定保存は現在のindex.phpに対するPOST処理とする。

操作は `action=save_mail_settings` で識別する。

リクエストにはCSRFトークンを含める。

保存処理は以下の順序とする。

    入力
      ↓
    CSRF確認
      ↓
    リクエスト形式確認
      ↓
    入力値確認
      ↓
    settings.json読み込み
      ↓
    mailだけ更新
      ↓
    保存
      ↓
    保存後再読み込み
      ↓
    保存結果確認
      ↓
    成功レスポンス

どこか一つでも失敗した場合は成功として扱わない。

操作を識別するため、リクエストに `action` を持たせる。

使用する操作は以下とする。

- delete_survey
- publish_survey
- close_survey
- send_survey
- load_responses
- save_response
- load_survey_results
- load_mail_logs

APIごとに、

- 必須項目
- 任意項目
- 入力制限

- 成功時レスポンス

## 11. APIレスポンス

APIレスポンスは必ずJSON形式とする。

成功時：

    {
      "success": true,
      "message": "処理が完了しました。"
    }

失敗時：

    {
      "success": false,
      "message": "入力内容を確認してください。",
      "errors": {
        "field": "エラー内容"
      }
    }

JSONレスポンスではHTMLを返さない。

JSONレスポンス出力後は処理を終了する。

APIレスポンスには以下を含めない。

- パスワード
- CSRFトークン
- セッション情報
- Authorization情報
- 認証情報
- 内部ファイルパス
- PHPエラーの詳細
- スタックトレース

---

## 12. HTTPステータス

API処理では内容に応じてHTTPステータスを設定する。

- 200: 正常終了
- 400: 入力不正
- 401: 認証失敗
- 403: CSRF等による拒否
- 404: 対象データなし
- 409: データ競合
- 500: サーバー内部エラー
- 502: 外部サービス通信エラー

HTTPステータスだけでなく、画面に表示可能な日本語メッセージも返す。

---

## 13. CSRF対策

状態変更を伴うすべての操作でCSRF対策を行う。

セッション開始時にアプリ固有のセッション領域へCSRFトークンを保存する。

CSRFトークンは十分な長さのランダム値とする。

セッション領域は他アプリと衝突しない固有キーを使用する。

例：

    $_SESSION['yokoyamy_newapp']['csrf_token']

状態変更APIでは、送信されたCSRFトークンとセッション内の値を検証する。

CSRF検証に失敗した場合は処理を実行しない。

CSRF検証失敗時はHTTP 403を返す。

---

## 14. CSRFトークンと複数タブ

同じアプリの画面を再表示しただけではCSRFトークンを変更しない。

複数タブで同じ画面を開いていても正常に操作できるようにする。

画面再描画だけを理由としてCSRFトークンを無効化してはならない。

---

## 15. JavaScript通信

JavaScriptから本アプリへ通信する場合は、現在表示している本アプリ自身を通信先とする。

別ドメインを通信先として指定しない。

`file://` からの利用を前提としない。

通信開始前には対象ボタンを無効化する。

処理開始時には必ず以下の順序とする。

1. 対象ボタンをdisabled=trueにする
2. ローディング表示を付ける
3. 通信を開始する

通信終了時には必ず、

1. 成功・失敗を判定する
2. メッセージを表示する
3. finallyでdisabled=falseにする
4. ローディング表示を解除する

とする。

---

## 16. 通信失敗時

通信失敗時に常に、

    サーバーとの通信に失敗しました。

だけを表示して終了させない。

可能な範囲で以下を判定する。

- HTTPステータス
- JSONレスポンスの有無
- APIから返されたmessage
- validation error
- CSRFエラー
- サーバー側エラー
- セッション期限切れ

ブラウザが通信そのものを開始できない場合と、サーバーがエラーを返した場合を区別できる構成とする。

---

## 17. CORSエラー時の扱い

本アプリでは同一サイト通信を基本とする。

そのため、通常の本番利用ではCORSを必要としない。

`origin: null` となるような利用方法を正式な利用方法として扱わない。

CORSエラーが発生した場合は、まず以下を確認する。

- Apache経由でindex.phpを開いているか
- `file://` で開いていないか
- 現在表示しているindex.phpと通信先が異なるサイトになっていないか
- 開発用URLが本番画面へ残っていないか

本番コードにCORSを無条件に許可する処理を追加して、問題を隠蔽してはならない。

## 18. 設定取得API

設定画面の初期表示ではサーバー側のsettings.jsonを正規データとして使用する。

画面側へ設定値をハードコードしない。

パスワードについては設定済みかどうかだけを返す。

例：

    {
      "success": true,
      "mail": {
        "smtp_server": "smtp.example.com",
        "smtp_port": 587,
        "security": "STARTTLS",
        "username": "user@example.com",
        "from_address": "survey@example.com",
        "from_name": "アンケート事務局",
        "password_configured": true,
        "configured": true,
        "verified": true
      }
    }

## 19. メール設定の接続確認

「送信設定を確認」操作を用意する。

保存済み設定を使用してSMTPサーバーへの接続を確認する。

接続確認と設定保存は別操作とする。

接続確認に成功した場合は、

    接続確認済み

とする。

メール設定を変更した場合は、

    接続確認未実施

に戻す。

接続確認に失敗した場合は、

    接続できませんでした

と表示する。

認証情報やパスワードはエラー画面に表示しない。

---

## 20. メール設定状態

メール設定には以下の状態を持たせる。

- 未設定
- 設定済み
- 接続確認済み
- 接続エラー

「設定済み」と「接続確認済み」を同一状態として扱わない。

設定内容を変更した場合は、以前の接続確認結果を無効にする。

## 21. kintone設定

設定項目は以下とする。

- kintone利用先
- 顧客管理アプリID
- ログイン名
- パスワード
- プロキシ設定

APIトークンは使用しない。

認証はkintoneのログイン名・パスワードを使用する。

---

## 22. kintoneプロキシ

プロキシは任意設定とする。

入力形式は、

    host:port

とする。

プロキシを使用するすべてのkintone通信で同じ設定を利用できる構成とする。

プロキシ設定値は各kintone通信処理へ渡せるものとする。

プロキシ設定が空の場合はプロキシなしとして通信する。

プロキシ設定がある場合は、

- proxy
- request_fulluri=true

を適用する。

---

## 23. kintone URL

利用先について以下の入力を許容する。

    example

    https://example.cybozu.com

    example.cybozu.com

どの場合でも正しいkintone URLを生成する。

`https://` や `.cybozu.com` の重複付与を行わない。

URL生成処理はアプリ内で統一する。

---

## 24. kintone通信

kintone通信ではcURLを使用しない。

以下を使用する。

- stream_context_create
- file_get_contents

SSL証明書検証は無効固定とする。

設定画面からSSL検証の有効・無効を変更する項目は設けない。

---

## 25. kintone GET

GET通信ではパラメータをURLへ付与する。

クエリ文字列生成には、

    http_build_query($params, '', '&', PHP_QUERY_RFC3986)

を使用する。

GET通信でリクエスト本文を送信してはならない。

---

## 26. kintone POST / PUT

POST / PUTではJSON形式でデータを送信する。

JSON生成時は、

    json_encode($data, JSON_UNESCAPED_UNICODE)

を使用する。

Content-Typeは、

    application/json

とする。

---

## 27. kintone接続確認

「接続設定を確認」を押すと、保存済み設定を使用して実際にkintone APIへ接続する。

接続確認には以下のいずれかを使用する。

    /k/v1/apps.json?limit=1

または、

    /k/v1/app.json?id={app_id}

顧客管理アプリIDが設定されている場合は、可能な限り対象アプリの確認を優先する。

---

## 28. kintone認証

認証ヘッダーは、

    X-Cybozu-Authorization

を使用する。

Base64化する文字列は、

    trim(ログイン名) . ":" . trim(パスワード)

とする。

APIトークンは使用しない。

認証情報をログへ出力しない。

認証失敗時もパスワードやBase64化した認証情報を画面へ返さない。

---

## 29. kintoneエラー

kintoneからエラーが返った場合は、可能な範囲で以下を画面へ表示する。

- HTTPステータス
- kintoneエラーコード
- kintoneメッセージ
- 利用者が確認すべき設定

以下は表示しない。

- パスワード
- Authorization情報
- CSRFトークン
- セッション情報
- Base64化された認証情報

---

## 30. 顧客情報

顧客情報はkintoneの顧客管理アプリから取得する。

最低限以下を取得する。

- 顧客ID
- 顧客名
- メールアドレス

その他の顧客情報を取得する場合も、アプリ内部で利用する項目を明確に定義する。

顧客情報を取得できない場合は、kintone設定を確認できるようにする。

---

## 31. customers.json

kintoneから取得した顧客情報をアプリ内で利用する場合は、

    data/customers.json

へ保存する。

保存時には取得日時を記録する。

基本形式：

    {
      "updated_at": "2026-09-24T12:00:00+09:00",
      "customers": [
        {
          "id": "1",
          "name": "顧客名",
          "email": "customer@example.com"
        }
      ]
    }

顧客情報の取得に失敗した場合、取得失敗を最新の顧客一覧として保存してはならない。

アンケート状態は以下の3種類に統一する。

    draft

画面表示は以下とする。

- draft → 下書き

## 33. surveys.json

各アンケートには最低限以下を保持する。

- ID
- アンケート名
- 説明
- 状態
- 作成日時
- 更新日時
- 公開開始日時
- 公開終了日時
- 質問番号形式
- グループ
- 質問
- 選択肢
- 必須／任意
- 分岐設定

## 34. アンケートID

アンケートIDは一意であること。

新規作成時に既存アンケートと重複しないIDを発行する。

質問ID、選択肢ID、グループIDについても、必要な単位で一意性を確保する。

表示上の質問番号と保存データ上の質問IDを分離する。

質問の並べ替え・削除によって質問番号が変わっても、質問自体を識別できるようにする。

---

## 35. 質問形式

回答形式は以下に限定する。

- single
- multiple
- free

single：

単一選択。

multiple：

複数選択。

free：

自由記述。

許可されていない回答形式を保存してはならない。

---

## 36. 選択肢

singleまたはmultipleの場合は、1個以上の選択肢を必須とする。

選択肢には一意なIDを持たせる。

選択肢IDは表示順と分離する。

選択肢の並べ替えによってIDを変更してはならない。

---

## 37. 分岐設定

単一選択質問について、選択肢ごとに以下を設定できる。

- 分岐なし
- 次の質問
- 指定した質問
- アンケート終了

分岐先として存在しない質問IDを保存してはならない。

質問削除後に分岐先が存在しなくなった場合は保存を拒否する。

公開前に分岐設定を再検証する。

分岐によって到達不能となる質問が発生する場合は、公開前に検証する。

循環する分岐を公開してはならない。

---

## 38. アンケート保存

アンケート保存ではサーバー側で以下を確認する。

- CSRF
- アンケートID
- アンケート名
- 説明
- 状態
- 公開期間
- 質問番号形式
- グループ
- 質問
- 回答形式
- 選択肢
- 必須設定
- 分岐設定
- データ型
- IDの一意性

画面側だけで検証を完了させてはならない。

---

## 39. アンケート公開

公開時にはサーバー側で再検証する。

少なくとも以下を確認する。

- アンケート名が存在する
- グループが存在する
- 質問が存在する
- 質問文が存在する
- 回答形式が許可された値である
- single / multipleでは選択肢が存在する
- 必須設定が正しい
- 分岐先が存在する
- 分岐循環がない
- 公開期間が正しい
- アンケート構造が正常である

検証に失敗した場合は公開しない。

---

## 40. 公開期間

公開開始日時と公開終了日時を保存する。

公開終了日時は公開開始日時より前に設定できない。

日時形式を統一する。

公開状態と公開期間の関係をサーバー側で確認する。

画面表示だけで公開中と判断してはならない。

---

## 41. 回答データ

回答は、

    data/responses.json

へ保存する。

回答データには最低限以下を保持する。

- 回答ID
- アンケートID
- 回答日時
- 回答者識別情報
- 回答内容
- 回答完了状態
- 送信識別情報

質問ごとの回答には質問IDを保存する。

回答内容だけで質問を識別してはならない。

---

## 42. 回答者識別情報

顧客一覧に登録されていない回答者も保存できる。

顧客一覧に登録されていないことを理由として回答を拒否しない。

回答者識別情報は、業務上必要な範囲だけ保存する。

不要な個人情報を保存しない。

---

## 43. 回答者画面

回答者画面には運営者向けメニューを表示しない。

以下を表示しない。

- 運営者向けヘッダーメニュー
- 設定画面へのリンク
- 管理画面への戻るボタン
- 管理用操作ボタン

公開中のアンケートだけ回答可能とする。

下書き・終了済みアンケートには回答できない。

---

## 44. 回答のサーバー側検証

ブラウザ側だけではなくサーバー側でも回答内容を検証する。

必須質問が未回答の場合は保存しない。

回答形式と異なる値が送信された場合は保存しない。

存在しない質問IDが送信された場合は保存しない。

存在しない選択肢IDが送信された場合は保存しない。

multipleでは許可された選択肢だけを受け付ける。

freeでは最大文字数を設定する。

アンケート公開後に質問内容が変更された場合でも、保存済み回答との対応関係が壊れないようにする。

---

## 45. 回答の二重送信

同じ回答を二重登録しない。

回答送信時には一意な回答IDまたは送信識別情報を使用する。

同一の送信識別情報が既に保存されている場合は、同じ回答を再登録しない。

二重送信と判定した場合は、既存回答を破壊しない。

画面の再送信や通信再試行によって同じ回答が複数件登録されないようにする。

---

## 46. 回答集計

回答結果は保存済みの回答データから集計する。

singleでは、

- 選択肢ごとの回答数
- 割合

を表示する。

multipleでは、

- 選択肢ごとの選択回数
- 割合

を表示する。

freeでは回答内容を一覧表示する。

顧客一覧に登録されていない回答者も集計対象とする。

回答完了状態ではないデータを正式回答として集計しない。

---

## 47. メール送信

メール送信は保存済みメール設定を使用する。

送信前にサーバー側で以下を確認する。

- アンケートが存在する
- アンケートが公開中である
- メール設定が存在する
- SMTP設定が必要項目を満たしている
- 送信対象者が1名以上いる
- 各送信先メールアドレスが妥当である
- 件名が入力されている
- 本文が入力されている

メール設定が未完了の場合は送信処理を開始しない。

---

## 48. メール送信対象者

送信対象者は画面側で選択できる。

ただし、送信処理開始時にサーバー側でも対象者を再確認する。

存在しない顧客IDを送信対象として受け付けない。

メールアドレスが不正な対象者については送信処理前にエラーとして扱う。

---

## 49. メール送信結果

メール送信後は以下を記録する。

- 送信ID
- アンケートID
- 送信日時
- 送信対象者数
- 成功数
- 失敗数
- 失敗した対象者
- エラー内容

以下は保存しない。

- SMTPパスワード
- SMTP認証情報
- Authorization情報
- CSRFトークン

---

## 50. mail_logs.json

メール送信履歴は、

    data/mail_logs.json

へ保存する。

送信処理が途中で失敗した場合も、実際の送信結果と一致するように記録する。

画面上の「送信成功」という表示だけを根拠として送信履歴を作成してはならない。

---

## 51. 設定変更後の接続状態

メール設定またはkintone設定を変更した場合は、以前の接続確認結果をそのまま有効として扱わない。

設定変更後は、

    verified = false

とする。

変更後に改めて接続確認を行い、成功した場合だけ、

    verified = true

とする。

---

## 52. 保存成功の定義

本アプリでは「画面上で値が変わった」ことを保存成功とはしない。

保存成功とは、

    サーバー側でデータ保存が完了し、
    保存後のデータを正常に読み取ること

とする。

この条件を満たさない場合は保存成功として扱わない。

---

## 53. 設定保存と接続確認の分離

設定保存は、設定値をJSONへ保存する処理とする。

接続確認は、保存済み設定を使用して外部サービスへ接続する処理とする。

「保存できた」ことと「外部サービスへ接続できた」ことを同一の成功条件として扱わない。

---

## 54. localStorage

サーバーで管理すべき情報をlocalStorageへ保存してはならない。

以下をlocalStorageへ保存しない。

- SMTPパスワード
- kintoneパスワード
- CSRFトークン
- セッション情報
- 認証情報
- アンケート正式データ
- 回答正式データ
- 顧客正式データ

localStorageを使用する場合は、画面表示上の一時状態だけに限定する。

---

## 55. エラー時の入力保持

サーバー通信に失敗した場合、画面上の入力内容を消去しない。

保存失敗時にも入力内容を保持する。

ただし、パスワードをブラウザへ永続保存してはならない。

---

## 56. JSONエラー

API処理ではJSONレスポンスを返す。

JSONではなくHTMLが返った場合、画面側で異常として扱えるようにする。

PHPの警告、Notice、Fatal Error等によってJSONレスポンスへHTMLが混入しないようにする。

API処理ではJSONレスポンスを出力した後、必ず処理を終了する。

---

## 57. XSS対策

PHPからHTMLへ値を出力する場合は共通のエスケープ処理を使用する。

安全な文字列エスケープ関数を定義して使用する。

JavaScriptでDOMへ値を表示する場合は原則としてtextContentを使用する。

innerHTMLを使用する場合は、表示する値が安全に処理されたものだけを使用する。

    X-Content-Type-Options: nosniff

## 61. 機密情報

    file_get_contents()

`$http_response_header` を直接参照しない。

## 64. ボタン処理

- データ型
- 最大長
- 最小値
- 最大値
- 許可された値
- IDの存在
- IDの一意性
- 関連データの存在
- データ構造

## 71. 回答データとアンケート定義の整合性

回答保存時には、対象アンケートの現在の公開定義を確認する。

回答に含まれる質問IDがアンケートに存在することを確認する。

選択肢IDについても、対象質問に存在することを確認する。

回答保存後にアンケート定義を変更しても、既存回答の質問ID・選択肢IDから元の回答内容を識別できる構造とする。

---

## 72. アンケート削除

削除できるのは下書き状態のアンケートだけとする。

公開中または終了済みのアンケートを物理削除してはならない。

回答データが存在するアンケートを削除して回答との関連を失わせてはならない。

必要に応じて下書き削除とデータ非表示を区別する。

---

## 73. アンケート終了

公開中のアンケートだけ終了できる。

終了後は回答受付を行わない。

終了済みアンケートは再度回答可能な状態へ戻さない。

終了処理はサーバー側で状態を確認してから実行する。

---

## 74. 公開処理の排他

公開処理中に別の保存処理が行われても、不完全なアンケートが公開状態にならないようにする。

公開直前にサーバー側でアンケート全体を再検証する。

---

## 75. 回答受付の状態確認

回答送信時には、画面を表示した時点の状態だけを信用しない。

サーバー側で、

- アンケートが存在する
- 状態がopenである
- 公開期間内である
- 質問定義が正常である

ことを確認する。

確認に失敗した場合は回答を保存しない。

---

## 76. データ整合性

各JSON間の関連情報について、存在しないIDを参照するデータを新規保存してはならない。

特に以下を確認する。

- 回答から参照するアンケートID
- 回答から参照する質問ID
- 回答から参照する選択肢ID
- メール履歴から参照するアンケートID
- メール履歴から参照する顧客ID
- 分岐設定から参照する質問ID

---

## 77. 初期データ

初回起動時にJSONファイルが存在しない場合は、定義された空データを作成する。

ただし既存ファイルの内容を無条件に初期値へ戻してはならない。

既存ファイルが存在する場合は、その内容を正規データとして扱う。

PHP 8.4 / 8.5で動作すること。

## 81. UTF-8

アプリ全体をUTF-8で統一する。

## 82. 保存処理の共通ルール

以下の処理をすべてのJSON保存処理で共通化する。

    JSON読み込み
      ↓
    JSON構造確認
      ↓
    入力値確認
      ↓
    データ変更
      ↓
    排他制御
      ↓
    一時保存
      ↓
    保存結果確認
      ↓
    保存後再読み込み
      ↓
    正常性確認

途中で失敗した場合は、既存の正常なデータを破壊しない。

---

## 83. 設定変更後の画面表示

保存成功後に表示する設定値は、画面上の入力値をそのまま正式データとして扱わない。

保存成功後はサーバー側へ保存されたデータを取得し、その結果を画面へ反映する。

localStorage等に残っている古い値をサーバー保存値より優先してはならない。

---

## 84. バージョン変更時

同じURLでindex.phpを差し替えた場合でも、古いブラウザ状態が新しい仕様へ不用意に影響しないようにする。

localStorageを使用する場合はアプリ固有のキーを使用する。

古い画面状態を正式な保存データとして自動採用してはならない。

サーバー側JSONを正式なデータとする。

- 回答状況を確認できる
- 回答結果を集計できる

### セキュリティ

- CSRF対策がすべての状態変更処理に適用されている
- XSS対策が適用されている
- 機密情報が画面・ログ・APIレスポンスへ漏れない
- セッション領域がアプリ固有になっている
- fetchの二重送信を防止できる

### 通信

- Apache経由で正常に画面を表示できる
- Apache経由で保存APIを呼び出せる
- `file://` 利用を前提としない
- 本アプリ自身への通信で不要なCORSを発生させない
- 別ホストを固定したAPI URLを使用しない
- APIレスポンスがJSONとして正常に返る
- JSONレスポンス後にHTMLが混入しない

### 環境

- PHP 8.4 / 8.5で動作する
- cURLを使用しない
- HTML / CSS / JavaScript / PHPが1つのindex.phpにまとまっている
- JSONファイルだけで永続データを管理できる
- Windows / UnixのApache 2.4環境で動作する

## 86. 特に重要なメール設定保存フロー

メール設定保存は、以下の一連の処理が成立して初めて「保存成功」とする。

    画面入力
      ↓
    入力内容確認
      ↓
    保存ボタンを即時無効化
      ↓
    ローディング表示
      ↓
    同一アプリのindex.phpへPOST
      ↓
    CSRF検証
      ↓
    サーバー側入力検証
      ↓
    settings.json読み込み
      ↓
    mail設定だけを更新
      ↓
    JSON保存
      ↓
    保存後JSONを再読み込み
      ↓
    保存結果確認
      ↓
    JSONレスポンス
      ↓
    画面へ保存成功表示
      ↓
    ボタン再有効化
      ↓
    ローディング解除

この途中で失敗した場合は保存成功として扱わない。

## 87. 特に重要な通信前提

本アプリは、

    Apache
      ↓
    index.php
      ↓
    ブラウザ

というWebアプリとして利用する。

保存処理は、

    ブラウザ
      ↓
    同じindex.php
      ↓
    JSONファイル

という経路で行う。

`file://` からWebサーバーへ直接通信する構成は正式な動作対象としない。

別オリジンからの通信を前提としない。

不要なCORS許可によってセキュリティ上の問題を作らない。

## 90. 最終原則

本アプリでは、画面上の表示を正規データとしない。

正規データはサーバー側のJSONファイルとする。

画面表示、ブラウザ上の一時データ、localStorageの内容よりもサーバー側データを優先する。

状態変更は必ずサーバー側で再検証する。

保存成功は、サーバー側への保存と保存後の読み取り確認が完了した場合だけ成立する。

外部サービス通信は、保存処理とは分離して扱う。

本アプリ自身への通信は同一サイトで完結させ、`file://` や別オリジンからの利用を前提としない。

すべての実装は、本実装要件、業務要件、モックの3者で業務上の動きが一致することを確認したうえで行う。

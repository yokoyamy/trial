# アンケート業務運営アプリ 実装要件

## 1. 基本方針

本アプリは、アンケート運営に必要な以下の業務を一つのアプリで管理する。

- アンケートの作成・編集・削除
- アンケートの公開・終了
- 顧客一覧の取得
- アンケートのメール送信
- 回答受付
- 回答状況の確認
- 回答結果の集計
- メール送信設定
- kintone接続設定

動作環境は以下とする。

- Apache 2.4
- PHP 8.4 / 8.5
- Windows / Unix
- データベースは使用しない
- HTML / CSS / JavaScript / PHP は1つの `index.php` に格納する
- 永続データはアプリルート配下のJSONファイルへ保存する
- 文字コードはUTF-8とする

---

## 2. データ保存

### 2.1 保存ファイル

以下のJSONファイルを使用する。

    data/
    ├─ customers.json
    ├─ settings.json
    ├─ surveys.json
    └─ responses.json

必要なディレクトリ・ファイルが存在しない場合は、アプリ初回起動時に安全に作成できるものとする。

JSONファイルはUTF-8で保存する。

### 2.2 保存時の基本ルール

JSONへの保存は、複数の処理が同時に実行されてもデータが壊れないようにする。

保存処理では以下を必須とする。

- 排他制御を行う
- JSONとして正しく保存する
- 保存途中で既存データが壊れないようにする
- 保存失敗時は既存データを破壊しない
- 保存成功後に保存結果を確認する
- 保存失敗時は画面に原因を表示できる情報を返す
- パスワード等の機密情報をレスポンスに含めない

---

## 3. settings.json

メール送信設定とkintone設定を1つの設定データとして保存する。

基本構造は以下とする。

    {
      "mail": {
        "smtp_server": "",
        "smtp_port": 587,
        "security": "STARTTLS",
        "username": "",
        "password": "",
        "from_address": "",
        "from_name": "",
        "configured": false,
        "verified": false,
        "updated_at": ""
      },
      "kintone": {
        "domain": "",
        "app_id": "",
        "login_name": "",
        "password": "",
        "proxy_host_port": "",
        "proxy_enabled": false,
        "ssl_verify": false,
        "configured": false,
        "verified": false,
        "updated_at": ""
      }
    }

実際の保存形式では、パスワードを画面やAPIレスポンスへ返してはならない。

画面再表示時には保存済みパスワードを表示しない。

設定画面のパスワード欄を空欄にした場合、既存パスワードを不用意に消去しない。

パスワードを変更する場合だけ新しい値を保存する。

---

## 4. メール送信設定

### 4.1 設定項目

以下を設定できる。

- SMTPサーバ
- ポート番号
- 接続方式
- 認証ユーザー名
- 認証パスワード
- 送信元メールアドレス
- 送信元名

接続方式は以下とする。

- なし
- STARTTLS
- SSL/TLS

### 4.2 必須項目

以下は必須とする。

- SMTPサーバ
- ポート番号
- 送信元メールアドレス

SMTP認証を使用する場合は、認証ユーザー名と認証パスワードを必須とする。

### 4.3 メール設定の保存

「設定を保存」を押した場合は、画面上だけを変更して保存完了としてはならない。

必ずサーバー側へ保存要求を行う。

保存要求が成功した場合だけ、

- 設定保存済み
- メール送信設定済み

として画面へ反映する。

サーバーへの保存要求が失敗した場合は、保存成功として表示してはならない。

### 4.4 メール設定保存API

メール設定保存は、現在の `index.php` に対するPOSTリクエストで処理する。

リクエストには操作内容を識別できる `action` を含める。

例：

    {
      "action": "save_mail_settings",
      "csrf_token": "...",
      "settings": {
        "smtp_server": "smtp.example.com",
        "smtp_port": 587,
        "security": "STARTTLS",
        "username": "user@example.com",
        "password": "********",
        "from_address": "survey@example.com",
        "from_name": "アンケート事務局"
      }
    }

実際のパスワードを画面表示用の値やエラー情報として返してはならない。

### 4.5 メール設定保存APIの成功条件

以下をすべて満たした場合だけ成功とする。

1. CSRF検証に成功している
2. リクエスト形式が正しい
3. 必須項目が入力されている
4. ポート番号が有効な範囲である
5. メールアドレスが正しい形式である
6. 接続方式が許可された値である
7. 設定ファイルを正常に読み込める
8. 設定ファイルへ正常に保存できる
9. 保存後のJSONを正常に読み取れる

保存成功時は、保存完了を示す成功レスポンスを返す。

### 4.6 メール設定保存失敗時

保存処理の途中で失敗した場合は、保存成功レスポンスを返してはならない。

利用者には原因に応じて以下のようなメッセージを表示できるようにする。

- 入力内容を確認してください。
- メール設定を保存できませんでした。
- セッションの有効期限が切れています。
- サーバー側で設定を保存できませんでした。

内部エラーの詳細や機密情報は表示しない。

---

## 5. メール設定の接続確認

「送信設定を確認」操作を用意する。

保存済み設定を使用してSMTPサーバーへ接続できるか確認する。

接続確認と設定保存は別操作とする。

接続確認に成功した場合は、

    接続確認済み

と表示する。

メール設定を変更した場合は、

    接続確認未実施

に戻す。

接続確認に失敗した場合は、

    接続できませんでした

と表示し、利用者が確認すべき設定項目を表示する。

パスワードや認証情報はエラー画面に表示しない。

---

## 6. メール設定状態

メール設定には以下の状態を持たせる。

- 未設定
- 設定済み
- 接続確認済み
- 接続エラー

「設定済み」と「接続確認済み」を同一状態として扱わない。

アンケート送信画面では、メール送信に必要な設定が存在しない場合、

    メール送信設定が未完了です

と表示する。

設定変更後に接続確認が必要な構成の場合は、その状態も表示する。

---

## 7. kintone設定

### 7.1 設定項目

以下を設定できる。

- kintone利用先
- 顧客管理アプリID
- ログイン名
- パスワード
- プロキシ設定

APIトークンは使用しない。

認証はkintoneのログイン名・パスワードを使用する。

### 7.2 プロキシ

プロキシは任意設定とする。

設定する場合は、

    host:port

形式で入力する。

プロキシ設定値は、kintoneへの通信処理で常に受け取れる構成とする。

---

## 8. kintone URL

利用先の入力値について、

    https://

および

    .cybozu.com

の重複付与が発生しないようにする。

URL生成処理はアプリ内で統一する。

以下の入力を許容する。

    example
    https://example.cybozu.com
    example.cybozu.com

いずれの場合でも正しいkintone URLを生成する。

---

## 9. kintone通信

kintone通信にはcURLを使用しない。

以下を使用する。

- stream_context_create
- file_get_contents

SSL証明書検証は無効固定とする。

設定画面からSSL検証の有効・無効を変更できる項目は設けない。

### 9.1 共通通信設定

kintoneへの全通信処理は、同じ通信共通処理を使用する。

プロキシ設定値は各kintone通信処理へ渡せるようにする。

プロキシ設定が入力されている場合は、

- proxy
- request_fulluri = true

を必ず適用する。

プロキシ設定が空の場合は、プロキシを使用しない通信として正常に処理する。

---

## 10. kintone接続確認

「接続設定を確認」を押すと、保存済み設定を使用して実際にkintoneへ接続する。

接続確認では、単なる設定値チェックではなく、kintone APIへ実際にアクセスする。

接続確認には以下のいずれかを使用する。

    /k/v1/apps.json?limit=1

または顧客管理アプリが設定されている場合、

    /k/v1/app.json?id={app_id}

を使用する。

接続確認成功後は、

    接続確認済み

とする。

---

## 11. kintone認証

認証ヘッダーは、

    X-Cybozu-Authorization

を使用する。

Base64化する文字列は、

    trim(ログイン名) . ":" . trim(パスワード)

とする。

APIトークンは使用しない。

認証情報をログへ出力してはならない。

認証失敗時もパスワードやBase64化した認証情報を画面へ返してはならない。

---

## 12. kintone API GET

GET通信ではパラメータをURLへ付与する。

クエリ文字列生成には、

    http_build_query($params, '', '&', PHP_QUERY_RFC3986)

を使用する。

GET通信でリクエスト本文を送信してはならない。

stream_context_createのHTTPオプションへGET用の `content` を設定してはならない。

---

## 13. kintone API POST / PUT

POST / PUTではJSON形式でデータを送信する。

JSON生成時は、

    json_encode($data, JSON_UNESCAPED_UNICODE)

を使用する。

Content-Typeは、

    application/json

とする。

---

## 14. kintone APIレスポンス

kintoneから返されたHTTPステータスを取得する。

PHP 8.4 / 8.5互換性のため、`$http_response_header` を直接参照しない。

レスポンスヘッダー取得は安全な共通処理を使用する。

通信失敗時は、kintoneから返されたレスポンスボディをJSONとして解析する。

以下の値が存在する場合は取得する。

- code
- message
- errors

---

## 15. kintoneエラー

kintoneからエラーが返った場合は、可能な範囲で以下を画面へ表示する。

- HTTPステータス
- kintoneのエラーコード
- kintoneのメッセージ
- 利用者が確認すべき設定

ただし以下の情報は画面・ログへ出力しない。

- パスワード
- 認証情報
- CSRFトークン
- セッション情報
- Authorizationヘッダー

---

## 16. 顧客情報

顧客情報はkintoneの顧客管理アプリから取得する。

少なくとも以下を取得する。

- 顧客名
- メールアドレス

その他の顧客管理情報も取得できる構成とする。

顧客情報を取得できない場合は、kintone設定を確認できるようにする。

---

## 17. customers.json

kintoneから取得した顧客情報をアプリ内で利用する場合は、

    data/customers.json

へ保存する。

保存時には取得日時を記録する。

例：

    {
      "updated_at": "2026-09-24T12:00:00+09:00",
      "customers": [
        {
          "id": "1",
          "name": "顧客名",
          "email": "customer@example.com",
          "company": "会社名"
        }
      ]
    }

顧客情報を更新した場合は、古い一覧を最新情報として扱わない。

---

## 18. surveys.json

アンケート情報を保存する。

各アンケートには最低限以下を保持する。

- ID
- アンケート名
- 説明
- 状態
- 作成日時
- 更新日時
- 公開開始日時
- 公開終了日時
- グループ
- 質問
- 選択肢
- 必須／任意
- 分岐設定

状態は以下とする。

    draft
    open
    closed

---

## 19. アンケートID

アンケートIDは一意であること。

新規作成時に既存アンケートと重複しないIDを発行する。

質問やグループにも必要に応じて一意なIDを持たせる。

質問番号は保存データそのものの固定IDとは分離する。

質問の並べ替え・削除によって表示番号が変わっても、質問自体を識別できるようにする。

---

## 20. 分岐設定

単一選択質問について、選択肢ごとに以下を設定できる。

- 次の質問
- 指定した質問
- アンケート終了
- 分岐なし

分岐先として存在しない質問IDが保存されないようにする。

質問削除・並べ替え後に分岐先が存在しなくなった場合は保存時にエラーとする。

分岐設定に循環が発生する場合は、公開前に検出してエラーとする。

---

## 21. アンケート保存API

アンケートの保存はサーバー側で行う。

保存時には以下を確認する。

- CSRF
- アンケートID
- アンケート名
- 質問内容
- 回答形式
- 選択肢
- 必須設定
- 分岐設定
- 状態
- 日付
- データ構造

画面側だけで検証を完了させてはならない。

---

## 22. アンケート公開

公開時にはサーバー側で再検証する。

少なくとも以下を確認する。

- アンケート名が存在する
- グループが存在する
- 質問が存在する
- 質問文が存在する
- 回答形式が許可された値である
- 単一選択・複数選択では選択肢が存在する
- 必須設定が正しい
- 分岐先が存在する
- 不正な分岐循環がない

検証に失敗した場合は公開しない。

---

## 23. 回答データ

回答は、

    data/responses.json

へ保存する。

回答データには最低限以下を保持する。

- 回答ID
- アンケートID
- 回答日時
- 回答者識別情報
- 質問ID
- 回答内容
- 回答完了状態

顧客一覧に登録されていない回答者も保存できる。

顧客一覧に登録されていないことを理由として回答を拒否しない。

---

## 24. 回答の二重送信

同じ回答を二重登録しない。

回答送信時には一意な回答IDまたは送信識別情報を使用する。

送信済みと判断された回答を再登録しない。

---

## 25. 回答者画面

回答者画面には運営者向けメニューを表示しない。

以下を表示しない。

- 運営者向けヘッダーメニュー
- 設定画面へのリンク
- 管理画面への戻るボタン

公開中のアンケートだけ回答可能とする。

下書き・終了済みアンケートには回答できない。

---

## 26. 回答入力のサーバー側検証

ブラウザ側だけではなくサーバー側でも回答内容を検証する。

必須質問が未回答の場合は保存しない。

回答形式と異なる値が送信された場合は保存しない。

存在しない選択肢IDが送信された場合は保存しない。

複数選択では許可された選択肢だけを受け付ける。

自由記述については適切な長さ制限を設ける。

---

## 27. 回答集計

回答結果は保存済みの回答データから集計する。

単一選択では、

- 選択肢ごとの回答数
- 割合

を表示する。

複数選択では、

- 選択肢ごとの選択回数
- 割合

を表示する。

自由記述では回答内容を一覧表示する。

顧客一覧に登録されていない回答者も集計対象とする。

---

## 28. メール送信

メール送信は保存済みメール設定を使用する。

送信前に以下を確認する。

- アンケートが公開中である
- メール設定が存在する
- SMTP設定が必要項目を満たしている
- 送信対象者が1名以上いる
- 送信先メールアドレスが正しい
- 件名が入力されている
- 本文が入力されている

メール設定が未完了の場合は、送信処理を開始しない。

---

## 29. メール送信結果

メール送信後は以下を記録する。

- アンケートID
- 送信日時
- 送信対象者数
- 成功数
- 失敗数
- 失敗した対象者
- エラー内容

パスワードやSMTP認証情報は送信結果へ保存しない。

---

## 30. API共通仕様

すべての状態変更処理はPOSTで受け付ける。

操作を識別するため、リクエストに `action` を持たせる。

例：

    save_mail_settings
    test_mail_settings
    save_kintone_settings
    test_kintone_connection
    save_survey
    delete_survey
    publish_survey
    close_survey
    send_survey
    save_response

---

## 31. JSON APIレスポンス

APIレスポンスは必ずJSON形式とする。

成功時：

    {
      "success": true,
      "message": "処理が完了しました。"
    }

失敗時：

    {
      "success": false,
      "message": "入力内容を確認してください。",
      "errors": {
        "field": "エラー内容"
      }
    }

JSONレスポンスではHTMLを返さない。

JSONレスポンス出力後は処理を終了する。

既存の出力バッファが存在する場合は、JSONレスポンス出力前に破棄する。

---

## 32. HTTPステータス

API処理では内容に応じてHTTPステータスを設定する。

- 200: 正常終了
- 400: 入力不正
- 401: 認証失敗
- 403: CSRF等による拒否
- 404: 対象データなし
- 409: データ競合
- 500: サーバー内部エラー
- 502: 外部サービス通信エラー

HTTPステータスだけでなく、画面に表示可能な日本語メッセージも返す。

---

## 33. CSRF対策

状態変更を伴うすべての操作でCSRF対策を行う。

セッション開始時にアプリ固有のセッション領域へCSRFトークンを保存する。

CSRFトークンは十分な長さのランダム値とする。

セッション領域は他アプリと衝突しない固有キーを使用する。

例：

    $_SESSION['yokoyamy_newapp']['csrf_token']

状態変更APIでは、送信されたCSRFトークンとセッション内の値を検証する。

CSRF検証に失敗した場合は処理を実行しない。

---

## 34. CSRFトークンと画面再生成

同じアプリの画面を再表示・再生成しただけでは、CSRFトークンを毎回変更しない。

以下の場合は新しいCSRFトークンを発行する。

- セッションが新規作成された場合
- セッションIDを明示的に再生成した場合
- セキュリティ上の理由で現在のトークンを無効化した場合

画面を再描画しただけでCSRFトークンを無効化してはならない。

複数タブで同じ画面を開いていても、正常な操作ができるようにする。

---

## 35. ブラウザ側の状態管理

メール設定・kintone設定・アンケートデータなど、サーバーで管理すべき情報をlocalStorageへ保存して正式なデータの保存先としてはならない。

localStorageを利用する場合は、画面表示上の一時的な状態だけに限定する。

特に以下はlocalStorageへ保存しない。

- SMTPパスワード
- kintoneパスワード
- CSRFトークン
- セッション情報
- 認証情報

---

## 36. index.php差し替え時のブラウザ状態

同じURLでindex.phpを別バージョンへ差し替えた場合でも、以前の画面で保存されたlocalStorage等の値が新しい画面へ意図せず混入しないようにする。

localStorageを使用する場合は、アプリ固有のキーを使用する。

必要に応じてアプリの仕様バージョンをキーへ含める。

例：

    yokoyamy_newapp_v1_*
    yokoyamy_newapp_v2_*

新しいバージョンでは、旧バージョンの画面状態を自動的に正式な設定値として採用してはならない。

サーバーに保存されたJSONを正式なデータとする。

旧バージョンのlocalStorageが残っていることだけを理由として、保存済み設定を上書きしてはならない。

---

## 37. JavaScript通信

fetchによる通信を行う場合は、通信開始前に対象ボタンを無効化する。

処理開始時には必ず以下の順序とする。

1. 対象ボタンをdisabled=trueにする
2. ローディング表示を付ける
3. fetchを開始する

通信終了時には必ず、

1. 成功・失敗を判定する
2. メッセージを表示する
3. finallyでdisabled=falseにする
4. ローディング表示を解除する

とする。

通信中の二重送信を防止する。

---

## 38. fetchエラー

fetchが失敗した場合、単に、

    サーバーとの通信に失敗しました。

だけを表示して終了させない。

可能な範囲で以下を判定する。

- HTTPステータス
- JSONレスポンスの有無
- APIから返されたmessage
- validation error
- CSRFエラー
- サーバー側エラー

サーバーからJSONが返らない場合は、通信失敗として利用者へ分かりやすく表示する。

特にメール設定保存では、HTTPレスポンスがエラーの場合に「メール設定が未完了」とだけ表示せず、保存APIから返された具体的なエラーを優先して表示する。

---

## 39. メール設定保存時の必須処理

「設定を保存」ボタンでは、以下の順序を必須とする。

1. 入力内容を取得する
2. 画面側で入力チェックする
3. ボタンを即座に無効化する
4. ローディング表示を開始する
5. CSRFトークンを付けてサーバーへ送信する
6. サーバー側で再度入力チェックする
7. settings.jsonへ保存する
8. 保存後のデータを読み込んで保存結果を確認する
9. JSONレスポンスを返す
10. 画面側で成功・失敗を表示する
11. 通信終了時にボタンを再度有効化する
12. ローディング表示を解除する

「画面上のJavaScript変数を書き換えただけ」で保存完了としてはならない。

---

## 40. メール設定保存時の画面状態

保存に成功するまで、現在画面に入力されている値は保持する。

保存失敗時にも入力内容を失わない。

ただし、サーバー保存に成功していない場合は、

    保存しました

と表示してはならない。

保存成功後に画面を再表示した場合は、localStorageではなくサーバー側に保存された設定を読み込んで表示する。

## 41. 設定取得API

設定画面の初期表示では、サーバー側のsettings.jsonを正規データとして使用する。

画面側に設定値をハードコードしない。

パスワードについては設定済みかどうかだけを画面へ伝え、実際のパスワードは返さない。

例：

        "password_configured": true,

      }
    }

## 42. 入力値検証

入力値は画面側とサーバー側の両方で検証する。

メールアドレスはメールアドレスとして妥当か確認する。

ポート番号は数値として妥当な範囲か確認する。

アプリIDは数値として妥当か確認する。

ドメインは許可された形式であるか確認する。

文字列には適切な最大長を設定する。

許可されていない値を受信した場合は保存しない。

## 43. JSONデータ検証

JSONファイルを読み込む際は、JSONとして正しく解析できることを確認する。

以下の場合はデータ破損として扱う。

- JSONとして解析できない
- 必須項目が存在しない
- 配列であるべき値が配列ではない
- オブジェクトであるべき値がオブジェクトではない
- 不正な型が保存されている

破損したJSONをそのまま上書き保存してはならない。

## 44. XSS対策

PHPからHTMLへ値を出力する場合は共通のエスケープ処理を使用する。

以下の関数を使用する。

    function h(?string $str): string {
        return htmlspecialchars($str ?? '', ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
    }

JavaScriptでDOMへ値を表示する場合は原則としてtextContentを使用する。

innerHTMLを使用する場合は、表示する値が安全に処理されたものだけを使用する。

## 54. 保存成功の定義

本アプリでは「画面上で値が変わった」ことを保存成功とはしない。

保存成功とは、

    サーバー側でデータ保存が完了し、
    保存後のデータを正常に読み取れること

と定義する。

この条件を満たさない場合は保存成功として扱わない。

---

## 55. データの正規性

以下の優先順位でデータを扱う。

1. サーバー側JSONファイル
2. サーバーから取得したAPIレスポンス
3. 現在画面に入力されている未保存データ
4. ブラウザに残っている一時データ

localStorage等に残っている過去の画面状態を、サーバー側に保存された設定より優先してはならない。

---

## 56. エラー表示

利用者向けエラーは、原因を推測できる内容とする。

メール設定保存で失敗した場合は、例えば以下のように表示できるようにする。

    メール設定を保存できませんでした。
    入力内容またはサーバーの保存状態を確認してください。

セッション期限切れの場合は、

    セッションの有効期限が切れています。
    画面を再読み込みしてもう一度お試しください。

とする。

JSONではなくHTMLが返ってきた場合や、サーバーから正常なレスポンスを受信できなかった場合も、利用者へ原因が分かるようにする。

---

## 57. エラー時の入力保持

サーバー通信に失敗した場合、画面上の入力内容を消去しない。

ただし、パスワードについてはブラウザ側に永続保存しない。

再送信時は利用者が必要に応じてパスワードを再入力できるようにする。

---

## 58. APIレスポンス出力

API処理では、既存の出力バッファを破棄してからJSONレスポンスを出力する。

レスポンスは、

    Content-Type: application/json; charset=utf-8

とする。

JSON出力後は必ず処理を終了し、後続のHTMLを出力しない。

---

## 59. メール設定保存とCSRF

メール設定保存は状態変更処理なので、CSRF検証を必須とする。

CSRF検証に失敗した場合はsettings.jsonを変更してはならない。

CSRFエラーはHTTP 403として扱う。

画面側ではCSRFエラーと通常の通信失敗を区別して表示できるようにする。

---

## 60. 設定保存と同時実行

同じ設定を複数の画面から同時に保存してもJSONファイルが壊れないようにする。

保存時には排他制御を行う。

保存対象以外の設定を不用意に消去しない。

例えばメール設定だけを保存する場合、kintone設定を初期値へ戻してはならない。

同様にkintone設定だけを保存する場合、メール設定を初期値へ戻してはならない。

---

## 61. 設定更新の部分保存

設定保存APIは、更新対象以外の設定を保持する。

メール設定保存：

    mailだけを更新
    kintone設定は保持

kintone設定保存：

    kintoneだけを更新
    mail設定は保持

設定ファイル全体を読み込み、変更対象だけを更新してから保存する。

---

## 62. メール設定の既存パスワード保持

メール設定を更新する際、パスワード欄が空欄の場合は既存パスワードを保持する。

明示的にパスワードを変更した場合だけ更新する。

画面へ返す設定情報には実際のパスワードを含めない。

---

## 63. kintone設定の既存パスワード保持

kintone設定を更新する際、パスワード欄が空欄の場合は既存パスワードを保持する。

明示的にパスワードを変更した場合だけ更新する。

画面へ返す設定情報には実際のパスワードを含めない。

---

## 64. 設定変更後の接続状態

メール設定またはkintone設定を変更した場合は、以前の接続確認結果をそのまま有効として扱わない。

設定内容が変更された時点で、

    verified = false

とする。

変更後に改めて接続確認を行い、成功した場合だけ、

    verified = true

とする。

---

## 65. 設定保存と接続確認の分離

設定保存は、設定値をJSONへ保存する処理とする。

接続確認は、保存済み設定を使用して外部サービスへ接続する処理とする。

「保存できた」ことと「外部サービスへ接続できた」ことを同一の成功条件として扱わない。

ただし、業務上メール送信を実行する際には、必要な設定が保存されていることを確認する。

---

## 66. メール送信前チェック

メール送信開始前に、サーバー側で以下を再確認する。

- 対象アンケートが存在する
- 対象アンケートが公開中である
- メール設定が存在する
- 必須メール設定が存在する
- 送信対象者が存在する
- 各送信先メールアドレスが妥当である

画面側のチェックだけを信用して送信処理を行ってはならない。

---

## 67. 実装完了条件

以下をすべて満たした状態を実装完了とする。

- メール設定を保存できる
- ページを再読み込みしてもメール設定が保持される
- 保存したメール設定がsettings.jsonに存在する
- 保存失敗時に保存成功と表示されない
- メール設定の状態を正しく表示できる
- SMTP接続確認ができる
- kintone設定を保存できる
- kintone接続確認ができる
- kintoneから顧客一覧を取得できる
- アンケートを保存できる
- アンケートを公開できる
- 顧客を選択してメール送信できる
- 送信結果を確認できる
- 回答を保存できる
- 回答を二重登録しない
- 回答結果を集計できる
- CSRF対策がすべての状態変更処理に適用されている
- XSS対策が適用されている
- 機密情報が画面・ログ・APIレスポンスへ漏れない
- fetchの二重送信を防止できる
- PHP 8.4 / 8.5で動作する
- cURLを使用しない
- HTML / CSS / JavaScript / PHPが1つのindex.phpにまとまっている

## 68. 特に重要なメール設定保存フロー

メール設定保存は、以下の一連の処理が成立して初めて「保存成功」とする。

    画面入力
      ↓
    入力内容確認
      ↓
    保存ボタンを即時無効化
      ↓
    ローディング表示
      ↓
    CSRFトークン付きPOST
      ↓
    PHP受信
      ↓
    CSRF検証
      ↓
    サーバー側入力検証
      ↓
    settings.json読み込み
      ↓
    mail設定だけを更新
      ↓
    JSON保存
      ↓
    保存後JSONを再読み込み
      ↓
    保存結果確認
      ↓
    JSONレスポンス
      ↓
    画面へ保存成功表示
      ↓
    ボタン再有効化
      ↓
    ローディング解除

この一連の処理の途中で失敗した場合は「保存成功」として扱わない。

「サーバーとの通信に失敗しました」という画面表示だけで処理を終了せず、サーバー側が返したエラー情報を利用者へ適切に表示する。

## 69. 本番コード作成時の方針

本番用 `index.php` は、現在のコードを部分修正するのではなく、

- 業務要件
- モック
- 本実装要件

を基準として全体を再構成する。

メール設定保存だけを局所的に修正して、他の画面・機能との整合性を失わせてはならない。

画面、保存処理、API処理、JSONデータ、エラー処理、セキュリティ対策を一体として実装する。

---

index.phpを再作成するとき、

localStorage に保存している旧版のアプリデータは引き継がない。

新しい index.php を初回表示した際、旧版の保存データを検出したら破棄する。

特に、CSRFトークンを localStorage に保存しない。CSRFトークンはサーバー側セッションを正とする。

メール設定など、サーバー側のJSONに保存済みの正式な設定は、localStorage ではなくサーバー側のデータを読み込む。

localStorage を使う必要がある画面状態については、アプリのバージョン識別子を持たせる。

index.php を差し替えてバージョンが変わったら、旧バージョンの localStorage をクリアして、新しい状態から開始する。

ただし、サーバー側の data/settings.json に保存済みのメール設定まで消してはいけない。

---


PHP + HTML + CSS + JavaScript を全部 index.php 1ファイルにまとめる前提でも、かなりの行数を出せます。

目安としては：

500〜1,000行：余裕

1,000〜3,000行：問題なく対応可能

3,000〜5,000行：可能。ただし一度に出すより分割推奨

5,000〜10,000行以上：可能な場合もありますが、1回で全部出すと途中で切れるリスクが高い

10,000行超：複数回に分けて作るのが安全

特に index.php 1ファイルなら、例えば、

<?php
// PHP
?>

<!DOCTYPE html>
<html>
<head>
    <style>
        /* CSS */
    </style>
</head>
<body>

    <!-- HTML -->

    <script>
        // JavaScript
    </script>
</body>
</html>

という構成で、数千行規模の完成品も作れます。

もし「かなり大規模なWebアプリを1枚の index.php に全部入れたい」という話なら、最初から3,000〜5,000行程度を想定して設計して、必要なら続きを追加していくのが現実的です。

なので、"</head>"までと、それ以降に分割して出す。

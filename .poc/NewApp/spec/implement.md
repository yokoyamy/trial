# 実装要件

## 1. 基本方針

本システムは、アンケートの作成、配信、回答、集計、顧客管理を一体で行うWebアプリケーションとする。

実装は、業務要件、操作要件、参照モック、実装要件の整合を保つ。

画面上で可能な操作と、サーバー側APIで可能な操作は一致させる。

画面側の制御だけで業務ルールを成立させてはならず、最終的な判定は必ずサーバー側で行う。

---

# 2. 実行環境

- Apache 2.4
- PHP 8.4 / 8.5
- データベースは使用しない
- データはJSONファイルで管理する
- 画面とAPIの入口は同一のindex.php
- 外部HTTP通信はPHP標準機能を使用する
- kintone通信にcURLを使用しない
- CORSによる回避を行わない

PHP 8.5で動作すること。

PHPのHTTPレスポンスヘッダー取得では$GLOBALS['http_response_header']に依存せず、http_get_last_response_headers()を使用する。

曖昧な関数定義や実装時の都合によるフォールバックは設けない。

---

# 3. データ保存

アプリケーションルートに以下のJSONファイルを配置する。

- surveys.json
- customers.json
- responses.json
- answer_tokens.json
- send_logs.json
- settings.json
- kintone_mapping.json
- kintone_sync_logs.json

データ構造はJSONとして明確に定義する。

JSONファイルの読み込みに失敗した場合は空データとして扱わない。

JSONが壊れている場合は、その内容を上書きして消失させない。

書き込み時は排他制御を行う。

可能な限り一時ファイルへ書き込み、正常終了時のみ本ファイルへ反映する。

途中失敗によって既存の正常なJSONを壊してはならない。

---

# 4. セッション・CSRF・セキュリティ

管理画面操作に必要なセッションを使用する。

POST APIにはCSRF対策を実装する。

セッションCookieはHttpOnlyを有効にする。

SameSiteはLaxとする。

画面表示時にはHTMLエスケープを行う。

JavaScriptで文字列を表示する場合はtextContentを基本とする。

外部入力をHTML文字列として直接挿入しない。

パスワードをAPIレスポンス、画面表示、ログへ出力しない。

kintone認証情報をAPIレスポンス、画面表示、ログへ出力しない。

X-Cybozu-Authorizationの実値を画面やエラーに表示しない。

サーバー内部の物理パスを利用者へ表示しない。

---

# 5. アンケート

アンケートは以下の項目を保持する。

- id
- name
- description
- status
- startAt
- endAt
- numberingFormat
- groups
- createdAt
- updatedAt

statusは以下のみとする。

- draft
- published
- closed

公開時にはアンケート全体をサーバー側で再検証する。

画面上で入力済みでも、公開APIで再検証に失敗した場合は公開しない。

---

# 6. グループ

グループについて以下の操作を提供する。

- 追加
- 編集
- 削除
- 並べ替え

削除されたグループを質問や分岐が参照している状態を残さない。

---

# 7. 質問

質問について以下の操作を提供する。

- 追加
- 編集
- 削除
- 並べ替え

質問タイプは以下とする。

- text
- single
- multiple

質問IDはアンケート内で一意とする。

質問の並び順は保存値を正本とする。

---

# 8. 選択肢

singleおよびmultipleの選択肢について以下を必須とする。

- choiceIdは一意
- 表示名は必須
- 空文字を禁止
- 重複choiceIdを禁止
- 削除済みchoiceIdを分岐先として残さない

選択肢変更後も既存回答との整合性を壊さない。

---

# 9. 分岐

分岐を設定できるのはsingle質問のみとする。

textおよびmultiple質問には分岐を設定しない。

分岐先は以下のみ許可する。

- next
- question:<questionId>
- end

サーバー側で以下を検証する。

- 参照先質問が存在する
- 削除済み質問を参照していない
- choiceIdが存在する
- 不正な分岐形式ではない
- 自分自身への分岐がない
- 循環がない
- end到達後に別の質問へ進まない

公開時にも再検証する。

分岐によって到達しない質問を必須回答エラーにしてはならない。

---

# 10. アンケート期間

startAtおよびendAtはサーバー側で検証する。

- 日付形式が正しい
- startAtがendAtより後でない
- 公開状態と矛盾しない
- 回答期間外は回答を受け付けない
- 終了後は回答を受け付けない

画面上の表示状態だけで期間判定を行わない。

---

# 11. 顧客

customers.jsonに顧客を保存する。

最低限以下を保持する。

- customerId
- name
- email
- status
- createdAt
- updatedAt
- kintoneRecordId
- kintoneUpdatedAt
- syncStatus
- syncError

kintoneとの同期ではメールアドレスを主キーとして使用しない。

kintoneRecordIdを外部レコード識別子として利用する。

同一kintoneRecordIdが複数の顧客に存在する場合は異常として扱う。

メールアドレスが変更されても、同じkintoneRecordIdであれば同一顧客として更新する。

---

# 12. kintone接続設定

settings.jsonに以下を保持する。

- subdomain
- appId
- login
- password
- proxyHostPort
- verifySsl

kintone認証はX-Cybozu-Authorizationを使用する。

生成時はloginとpasswordの前後空白を除去する。

認証情報の実値は画面、API応答、ログに出力しない。

GETではJSON本文を送信しない。

クエリパラメータはRFC3986形式でエンコードする。

POSTおよびPUTはJSONで送信する。

proxyHostPortが設定されている場合はstream contextのproxyを使用する。

プロキシ利用時はrequest_fulluriを使用する。

SSL証明書検証は設定値に従う。

現行要件ではデフォルトを検証OFFとする。

---

# 13. kintone接続確認

設定画面にkintone接続確認を用意する。

接続確認は単なる通信確認ではなく、設定されたアプリを利用できることまで確認する。

エラーは以下を区別して扱う。

- 接続先不正
- 認証失敗
- アプリID不正
- アプリへのアクセス権不足
- 通信失敗
- kintone APIエラー

結果はブラウザコンソールではなく、通常の画面上に明示する。

成功時は一般利用者が理解できる日本語で成功を表示する。

失敗時も一般利用者が原因を判断できる日本語で表示する。

X-Cybozu-Authorizationの値は絶対に表示しない。

---

# 14. kintone顧客アプリ同期

kintone顧客アプリは外部顧客マスタとして扱う。

顧客同期は以下の手順を必須とする。

1. kintone接続設定を確認する
2. 対象アプリを確認する
3. kintoneのフィールド定義を取得する
4. フィールド定義を画面に表示する
5. 本システムの顧客項目とkintoneフィールドをマッピングする
6. マッピングをサーバー側で検証する
7. マッピングを保存する
8. 最新のフィールド定義との整合性を確認する
9. 同期前プレビューを実行する
10. 同期を実行する
11. 同期結果を記録する

フィールド定義を取得せずに同期を開始してはならない。

フィールド名を推測して同期してはならない。

保存済みの古いマッピングだけを利用して同期してはならない。

---

# 15. kintoneフィールド定義取得

対象アプリのフィールド定義を取得するAPIを実装する。

使用するAPIは以下とする。

GET /k/v1/app/form/fields.json

入力として対象appIdを必要とする。

取得する項目には少なくとも以下を含める。

- field code
- field type
- field label
- 必須設定
- 選択肢
- 同期可否判断に必要な設定

画面上ではfield labelを分かりやすく表示する。

マッピングの保存識別子としてはfield codeを使用する。

フィールド定義取得結果はkintone_mapping.jsonへ保存できるようにする。

---

# 16. フィールド定義の保存

kintone_mapping.jsonには以下を保持する。

- appId
- fetchedAt
- schemaHash
- fields
- mappings
- syncKey
- mappingVersion
- updatedAt

schemaHashはフィールド構成から決定的に生成する。

少なくとも以下をハッシュ対象とする。

- field code
- field type
- 必要なフィールド設定
- 選択肢

業務上フィールド名の変更も確認対象とする場合はfield labelも含める。

---

# 17. kintoneフィールドマッピング

マッピングは以下の形式とする。

本システム顧客項目
→
kintone field code

画面上はfield labelを表示して利用者が選択できるようにする。

内部的にはfield codeを保存する。

マッピングには対象appIdも保存する。

異なるappIdのフィールドを保存済みmappingとして使用してはならない。

---

# 18. 必須マッピング

同期に必要な本システム側顧客項目について、対応するkintoneフィールドが存在しない場合は同期不可とする。

少なくとも顧客名およびメールアドレスを同期対象とする業務仕様の場合、両項目を必須マッピングとして扱う。

必須項目は実装時に画面表示でも明示する。

---

# 19. フィールド型バリデーション

マッピング保存前に、kintone field typeを検証する。

本システムで対応していない型を自動変換しない。

読み取り専用フィールドを更新対象にしない。

ルックアップ等により値が決まるだけで通常更新できないフィールドを更新対象にしない。

対応不能なfield typeはマッピング候補として確定できないようにする。

値変換仕様が定義されていない型は同期不可とする。

---

# 20. 自動マッピング

自動マッピングを行う場合でも、最終確定は利用者が確認できるようにする。

自動推測だけで同期を開始してはならない。

候補判定の優先順位は以下とする。

1. 完全一致するfield code
2. 保存済みの明示的mapping
3. 候補として表示するのみ

field labelの一致だけで自動確定しない。

---

# 21. マッピング変更検知

同期開始前に最新のkintoneフィールド定義を取得する。

以下の場合は同期を停止する。

- mapping対象field codeが存在しない
- field codeに対応する型が変わった
- mapping対象フィールドが利用できなくなった
- 必須マッピング対象が存在しない
- schemaHashが保存値と一致しない
- 対象appIdが保存値と一致しない

schemaHashが変更された場合は旧mappingをそのまま使用せず、フィールド定義再取得とmapping再確認を要求する。

変更後のフィールドへ自動で付け替えない。

---

# 22. 同期前プレビュー

同期前に以下を表示する。

- 対象件数
- 新規件数
- 更新件数
- 変更なし件数
- 同期対象外件数
- エラー件数
- マッピングエラー
- 値変換エラー
- 必須値不足

重大なエラーがある場合は同期実行不可とする。

プレビューAPIでは原則としてcustomers.jsonを書き換えない。

プレビュー後にkintoneの構成が変わった場合は、そのまま同期せず再確認を要求する。

---

# 23. kintoneレコード取得

顧客件数が少ない場合だけを前提とした実装にしない。

大量データ取得を前提とする。

1回のAPI取得結果だけで全顧客と判断しない。

500件を超える取得では分割して取得する。

10,000件を超える大量取得ではoffset方式だけに依存せず、カーソル方式を使用する。

取得対象は同期に必要なfield codeを中心とする。

途中取得で失敗した場合は全体同期を成功扱いにしない。

---

# 24. kintone同期の同一性

顧客同一性の判定はkintoneRecordIdを基準とする。

新規条件:

- kintoneRecordIdが本システムに存在しない

更新条件:

- kintoneRecordIdが本システムに存在する

メールアドレス一致だけで別レコードを統合しない。

同じメールアドレスを持つ複数のkintoneRecordIdを自動統合しない。

---

# 25. 同期内容

マッピングされた項目だけを更新する。

マッピングされていない本システム側の項目は保持する。

kintone側の空値も業務上反映対象である場合は明示的に反映する。

空値を無条件に「変更なし」と扱わない。

メールアドレスなど形式検証が必要な項目は同期時にも検証する。

---

# 26. kintone側削除

kintoneから顧客レコードが削除された場合でも、本システムの顧客を履歴ごと物理削除しない。

過去のアンケート配信、回答、集計との整合性を保持する。

必要に応じて顧客状態を非アクティブとして管理する。

既存回答データが顧客削除によって参照不能にならないようにする。

---

# 27. 同期の途中失敗

同期途中で1件でも重大なエラーが発生した場合は、全体を成功扱いにしない。

エラー内容を同期ログへ記録する。

可能な限り、書き込み前に取得・検証・変換を完了させる。

customers.json更新中に失敗しても既存の正常データを破壊しない。

---

# 28. 同期の二重実行防止

同期処理はサーバー側で排他制御する。

複数ブラウザから同時に同期を開始しても、同じ同期を二重実行できないようにする。

同期中は画面上で実行中状態を表示する。

ボタンを複数回押しても二重実行されない。

---

# 29. 同期ログ

kintone_sync_logs.jsonに同期履歴を保存する。

最低限以下を記録する。

- syncId
- startedAt
- finishedAt
- appId
- schemaHash
- mappingVersion
- totalCount
- createdCount
- updatedCount
- unchangedCount
- inactiveCount
- skippedCount
- errorCount
- status
- errorSummary

パスワード、認証ヘッダー、その他秘密情報をログに保存しない。

必要以上の個人情報をログへ保存しない。

---

# 30. API共通形式

成功レスポンスは以下の構造とする。

{
  "ok": true,
  "data": {}
}

失敗レスポンスは以下の構造とする。

{
  "ok": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "利用者向けメッセージ",
    "fields": {}
  }
}

画面ではerror.codeをそのまま利用者向け文章として表示せず、一般利用者が理解できる日本語へ変換する。

# 32. kintone API

## kintone_test

目的:

- 接続先確認
- 認証確認
- appId確認
- アプリ利用可否確認

## kintone_fields

目的:

- 最新フィールド定義取得

入力:

- appId

出力:

- appId
- fetchedAt
- schemaHash
- fields

## kintone_mapping_validate

目的:

保存前のmappingを検証する。

検証:

- field code存在
- appId一致
- field type
- 必須マッピング
- 書き込み可否
- 未対応field type
- 不正な重複割当
- 不正な値変換

## kintone_mapping_save

目的:

検証済みmappingを保存する。

保存直前にもサーバー側で再検証する。

## kintone_sync_preview

目的:

同期結果を事前確認する。

customers.jsonを確定更新しない。

## kintone_sync_execute

目的:

検証済みmappingを利用して顧客同期を実行する。

開始直前に最新フィールド定義を取得する。

保存済みschemaHashと一致しない場合は同期を中止する。

# 34. SMTP

SMTP設定は以下を保持する。

- host
- port
- encryption
- username
- password
- fromEmail
- fromName

encryptionは以下とする。

- none
- ssl
- tls

SMTP接続確認結果はコンソールではなく画面上に表示する。

成功時はSMTP接続と認証が成功したことを明示する。

失敗時はSMTP接続失敗として明示し、一般利用者が原因を把握できる範囲で詳細を表示する。

パスワードは表示しない。

メール送信時は以下を検証する。

- SMTP設定
- 宛先
- 差出人
- アンケート状態
- 配信対象
- 二重送信状態

同一対象への重複送信を防止する。

失敗した配信を再送できる。

---

# 35. 回答トークン

answer_tokens.jsonに以下を保存する。

- tokenId
- surveyId
- customerId
- email
- issuedAt
- usedAt

トークンは十分なランダム性を持つ値とする。

回答URLは現在のindex.phpを基準として生成する。

発行時点でアンケート状態および期間を確認する。

---

# 36. 回答画面

回答ページは管理画面から独立して利用できる。

トークンについて以下を検証する。

- 存在する
- 対象アンケートが存在する
- published状態である
- 回答期間内である
- 未使用である

いずれかを満たさない場合は回答を受け付けない。

---

# 37. 回答登録

サーバー側で必ず以下を検証する。

- surveyId
- token
- survey status
- 回答期間
- token未使用
- 必須回答
- 回答到達可能性
- 選択肢妥当性
- text最大文字数
- single選択数
- multiple重複
- multiple選択肢妥当性

ブラウザ側の検証だけを信用しない。

---

# 38. 分岐と回答

分岐によって到達しなかった質問はスキップ扱いとする。

到達していない質問を必須未回答として扱わない。

集計でも未到達質問を未回答として誤集計しない。

回答対象質問をブラウザから送信させる場合でも、その値をそのまま信用せず、サーバー側で分岐経路を再計算する。

---

# 39. 回答二重登録防止

同一トークンで回答が二重登録されないこと。

トークン使用済み更新と回答保存が競合した場合でも二重回答にならないよう排他制御する。

「使用済みだけ更新されて回答がない」「回答だけ保存されてトークンが未使用」の不整合を防止する。

---

# 40. 集計

以下を集計可能とする。

- 回答数
- 送信数
- 配信成功数
- 回答率
- 未回答数
- 日別回答数
- 対象者状態

未到達質問は未回答として集計しない。

---

# 41. アンケート状態

draft:

編集可能。

published:

公開中。

回答受付対象とする。

回答データとの整合性を壊す構造変更を無制限に許可しない。

closed:

回答受付終了。

過去回答を保持する。

---

# 42. バリデーション

入力値はすべてサーバー側で検証する。

必須文字列は空文字を許可しない。

必要に応じて前後空白を正規化する。

文字数上限を超える入力は拒否する。

型が違うJSON値は拒否する。

配列は配列であることを確認する。

要素数上限を確認する。

重複を確認する。

NULLや異常なデータ構造を拒否する。

# 54. 実装完了の判断

実装完了とは、単にkintoneへ接続できる状態ではない。

以下の一連の業務操作が完結できることを実装完了とする。

「kintone接続設定」
→
「kintone接続確認」
→
「顧客アプリのフィールド定義取得」
→
「フィールド定義確認」
→
「本システム項目とのマッピング」
→
「マッピング検証」
→
「マッピング保存」
→
「最新フィールド定義との一致確認」
→
「同期プレビュー」
→
「同期実行」
→
「同期結果確認」

この一連の流れについて、画面側だけでなくサーバー側でも業務ルールが成立していること。

特に、フィールド定義を取得していない状態、マッピングが未確定の状態、フィールド定義が変更された状態では顧客同期を実行できないこと。

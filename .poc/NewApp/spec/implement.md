# アンケート業務運営アプリ 実装要件
## 全差し替え版

---

## 1. 目的

本アプリは、アンケート運営者が以下の業務を一連の流れとして管理できるWebアプリとする。

- アンケートの作成
- アンケートの編集
- アンケートの保存
- アンケート内容の確認
- アンケートの公開
- アンケートの終了
- 顧客一覧の確認
- 顧客一覧の更新
- 送信対象者の選択
- メール内容の作成
- メール送信前確認
- メール送信
- 送信結果の確認
- 失敗者への再送
- 回答受付
- 回答状況の確認
- 回答結果の集計
- メール送信設定
- kintone接続設定

モックで画面上だけ変更されている値についても、本番版では正式なデータとしてサーバー側へ保存する。

画面表示が変更されたことだけをもって、保存・公開・送信・回答完了等が成立したとは扱わない。

---

# 2. 動作環境

以下を正式な動作環境とする。

- Apache 2.4
- PHP 8.4 / 8.5
- Windows / Unix
- データベースなし
- HTML / CSS / JavaScript / PHPを1つのindex.phpへ格納
- UTF-8
- 永続データはアプリルート配下のJSONファイルへ保存
- PHPからの外部HTTP通信ではcURLを使用しない
- kintone通信にはstream_context_createおよびfile_get_contentsを使用する

---

# 3. 本番実行環境とプレビュー環境

## 3.1 本番実行環境

本番利用では、index.phpをApacheから以下のいずれかで直接提供する。

- http://
- https://

JavaScriptから本アプリ自身のAPIを呼び出す場合は、現在表示しているindex.php自身を通信先とする。

本番コードへ特定の本番ホスト名を固定記述してはならない。

例として、

    https://n11-1041/...

のような固定URLをJavaScriptへ埋め込まない。

---

## 3.2 アプリ管理ツールのプレビュー環境

アプリ管理ツールのプレビュー領域は、本番実行環境とは別の環境として扱う。

プレビューでは、

- file://
- data:
- blob:
- sandbox iframe
- Origin: null
- その他のopaque origin

が発生する可能性がある。

これらの環境から、本番サーバー上のindex.phpへ状態変更APIを直接呼び出してはならない。

---

## 3.3 Origin:nullへの対応

Origin:nullを解消する目的で、以下のCORS設定を本番アプリへ追加してはならない。

    Access-Control-Allow-Origin: *
    Access-Control-Allow-Origin: null

また、任意のOriginを許可するCORS設定も行わない。

セッション付き状態変更APIを外部Originから利用可能にしてはならない。

---

## 3.4 プレビューから本番APIを操作する場合

アプリ管理ツールのプレビューで本番APIとの通信確認を必要とする場合は、プレビュー環境側で以下のいずれかを提供する。

- 本番APIと同一Originとなるプレビュー提供方式
- 管理ツール側が提供する安全な同一Origin通信機構
- 管理ツール側のサーバー中継機構

本番アプリ側でOrigin:nullを許可することでプレビュー通信を成立させてはならない。

プレビュー環境から本番APIへ直接fetchすることを、本番アプリの正式な動作条件としてはならない。

---

# 4. 同一Origin通信

本アプリ内部APIは同一Origin通信を基本とする。

JavaScriptからAPIを呼び出す場合は、現在表示されているindex.phpを基準としてURLを生成する。

固定ホスト名、固定ポート、固定スキームをAPI URLとしてJavaScriptへ記述しない。

状態変更処理では、

- セッション
- CSRFトークン

を利用する。

---

# 5. API通信の基本ルール

状態変更を伴うAPIはPOSTとする。

参照のみのAPIはGETを使用できる。

APIは必ずJSONを返す。

HTMLページとJSON APIを同一リクエストで混在させない。

API処理終了後は必ず処理を終了する。

# 8. APIレスポンス形式

## 8.1 成功

    {
      "success": true,
      "message": "処理が完了しました。"
    }

必要に応じて、

    {
      "success": true,
      "message": "処理が完了しました。",
      "data": {}
    }

とする。

## 8.2 失敗

    {
      "success": false,
      "message": "入力内容を確認してください。",
      "errors": {}
    }

errorsには利用者が修正可能な項目単位のエラーだけを含める。

パスワード、認証情報、CSRFトークン、セッション情報等を含めない。

---

# 9. HTTPステータス

基本的に以下を使用する。

- 200 正常終了
- 400 入力不正
- 401 認証失敗
- 403 CSRF・権限等による拒否
- 404 対象データなし
- 409 データ競合・二重実行
- 422 業務ルール違反
- 500 サーバー内部エラー
- 502 外部サービス通信エラー

---

# 10. APIレスポンス出力

JSON APIでは以下の順序を厳守する。

1. 既存出力バッファを破棄する
2. Content-Typeを設定する
3. JSONを出力する
4. exitまたはdieで処理を終了する

Content-Type：

    application/json; charset=utf-8

APIレスポンスへHTMLを混在させない。

PHP Warning等がJSONの前に出力されないようにする。

---

# 11. セッション

セッションはアプリ固有領域を使用する。

例：

    $_SESSION['yokoyamy_newapp']

ルート直下に以下のような汎用キーを作成しない。

    $_SESSION['csrf_token']

セッションCookieには、

- HttpOnly
- SameSite=Lax

を適用する。

---

# 12. CSRF

状態変更を伴うすべてのAPIでCSRF検証を行う。

対象：

- save_mail_settings
- test_mail_settings
- save_kintone_settings
- test_kintone_connection
- refresh_customers
- save_survey
- delete_survey
- publish_survey
- close_survey
- prepare_survey_send
- send_survey
- prepare_resend
- resend_survey
- save_response

CSRFトークンは、

    bin2hex(random_bytes(32))

等の十分な長さのランダム値とする。

CSRFトークンはアプリ固有セッション領域へ保存する。

検証失敗時は処理を実行せずHTTP 403を返す。

---

# 13. CSRFトークン再発行

同じセッションで単に画面を再表示しただけではCSRFトークンを変更しない。

以下の場合に再発行する。

- 新規セッション
- セッションID再生成
- セキュリティ上の理由による無効化

複数タブで同じ画面を使用しても正常に操作できること。

---

# 14. PHP名前空間

PHPファイル先頭には以下のアプリ固有名前空間を使用する。

    namespace yokoyamy\trial\newapp;

汎用名前空間は使用しない。

---

# 15. 共通エスケープ

PHPからHTMLへ値を出力する場合は以下の関数を使用する。

    function h(?string $str): string {
        return htmlspecialchars(
            $str ?? '',
            ENT_QUOTES | ENT_SUBSTITUTE,
            'UTF-8'
        );
    }

JavaScriptからDOMへ値を表示する場合は原則としてtextContentを使用する。

innerHTMLを使用する場合は、表示する値が安全に処理されていることを保証する。

---

# 16. JavaScript実行

すべてのJavaScript処理は、

    document.addEventListener('DOMContentLoaded', ...)

の内部で実行する。

イベントリスナー登録前には対象要素の存在を確認する。

対象要素が存在しない場合、その処理だけを行わず後続処理を継続する。

---

# 17. 非同期通信

fetch開始前に必ず以下の順序で処理する。

1. 対象ボタンをdisabled=trueにする
2. ローディング表示を付ける
3. fetchを開始する

通信終了時にはfinallyで、

1. disabled=false
2. ローディング表示を解除する

を行う。

---

# 18. fetch通信エラー

fetchが失敗した場合に、

    サーバーとの通信に失敗しました

だけを表示して終了してはならない。

可能な範囲で以下を判定する。

- HTTPステータス
- JSONレスポンスの有無
- API message
- validation error
- CSRFエラー
- 認証エラー
- 業務ルールエラー
- サーバーエラー

JSONが返らない場合は、

    サーバーから正しい応答を受け取れませんでした。

等、原因を切り分けられるメッセージを表示する。

Origin:null等のブラウザ側通信エラーについては、サーバー側APIエラーと混同しない。

---

# 19. 入力保持

通信失敗時に入力内容を消去しない。

保存失敗時にも入力内容を保持する。

パスワードをlocalStorage等へ保存しない。

---

# 20. localStorage

localStorageは正式なデータ保存先として使用しない。

正式データはサーバー側JSONとする。

localStorageへ以下を保存してはならない。

- SMTPパスワード
- kintoneパスワード
- CSRFトークン
- セッション情報
- Authorization情報
- 認証情報

一時的な画面状態に限定して使用する。

---

# 21. HTTPヘッダー

以下を出力する。

    X-Frame-Options: SAMEORIGIN
    X-Content-Type-Options: nosniff

JSON APIでは、

    Content-Type: application/json; charset=utf-8

を使用する。

---

# 22. セキュリティ情報の非表示

以下を画面、JSONレスポンス、エラーメッセージ、ログへ出力しない。

- SMTPパスワード
- kintoneパスワード
- CSRFトークン
- セッションID
- Authorizationヘッダー
- Base64認証情報
- プロキシ認証情報
- その他の認証秘密情報

---

# 23. データ保存構成

アプリルート配下に以下を保存する。

    data/
      settings.json
      customers.json
      surveys.json
      responses.json
      mail_logs.json

必要に応じて、

    data/tmp/
    data/backup/

等を使用できる。

---

# 24. JSON直接アクセス防止

data配下のJSONファイルはブラウザから直接取得できないようにする。

特に、

    settings.json

には認証情報が含まれるため、外部から直接参照できてはならない。

JSONファイルへの直接アクセスを防止する仕組みは、Apache設定またはアプリ配置方法を含めて本番環境で保証する。

---

# 25. JSON保存

JSON更新時には以下を保証する。

- 排他制御
- 正しいJSON形式
- 保存途中で既存ファイルを破壊しない
- 保存失敗時に既存データを維持
- 保存後に再読み込みして確認

複数リクエストが同時に更新してもJSONが破損しないこと。

---

# 26. JSON破損

JSON読み込み時に以下を検出した場合はデータ破損として扱う。

- JSON解析失敗
- 必須項目不足
- 型不正
- 配列であるべき値が配列ではない
- オブジェクトであるべき値がオブジェクトではない
- 想定外の状態値
- 重複ID

破損したJSONを正常データとして上書きしない。

利用者には安全なメッセージを表示する。

例：

    データを読み込めませんでした。
    管理者へ確認してください。

内部データを画面へ表示しない。

---

# 27. JSON更新競合

JSONファイル単位の保存だけではなく、業務データの更新競合を考慮する。

以下には更新版情報を持たせる。

- アンケート
- メール設定
- kintone設定
- 顧客情報
- メール送信処理

画面表示時の版と保存時の版が異なる場合は、

    409 Conflict

として保存を拒否する。

古い画面からの更新で他の利用者の変更を無条件に上書きしてはならない。

---

# 28. 日時

日時はサーバー側で統一して保存する。

保存形式にはタイムゾーンを明示する。

例：

    2026-09-24T12:34:56+09:00

以下で異なる日時基準を使用しない。

- 作成日時
- 更新日時
- 公開開始日時
- 公開終了日時
- 回答日時
- メール送信日時

画面表示時だけ必要に応じて日本時間へ整形する。

---

    {

      },
      "kintone": {
        "domain": "",

        "proxy_host_port": "",
        "proxy_enabled": false,
        "configured": false,
        "verified": false,
        "updated_at": "",
        "version": 1
      }

画面表示用データにはパスワードを含めない。

---

# 30. パスワード保持

設定更新時にパスワード欄が空欄の場合、既存パスワードを保持する。

空欄を理由として既存パスワードを削除してはならない。

パスワード変更時のみ新しいパスワードへ更新する。

画面再表示時には実際のパスワードを表示しない。

画面には、

    変更する場合のみ入力してください。

等を表示する。

---

# 31. メール設定

設定項目：

- SMTPサーバ
- ポート番号
- 接続方式
- SMTP認証を使用するか
- 認証ユーザー名
- 認証パスワード
- 送信元メールアドレス
- 送信元名

接続方式は以下だけを許可する。

- なし
- STARTTLS
- SSL/TLS

---

# 32. メール設定必須項目

必須：

- SMTPサーバ
- ポート番号
- 送信元メールアドレス

SMTP認証を使用する場合：

- 認証ユーザー名
- 認証パスワード

を必須とする。

SMTP認証を使用しない場合は認証情報を要求しない。

---

# 33. メール設定入力制限

サーバー側で必ず検証する。

- SMTPサーバ
- ポート番号
- 接続方式
- メールアドレス
- 送信元名
- ユーザー名
- 各項目の最大文字数
- 改行文字
- 制御文字
- 不正な入力

SMTPサーバ名には改行を許可しない。

メールアドレスには改行を許可しない。

送信元名にも改行を許可しない。

メールヘッダーインジェクションにつながる入力を許可しない。

---

# 34. メール設定ポート番号

ポート番号は、

    1～65535

の整数だけを許可する。

---

# 35. メール設定状態

メール設定は以下の状態を区別する。

- 未設定
- 設定済み
- 接続確認済み
- 接続エラー

設定保存成功だけでは接続確認済みとしない。

設定変更時には、

    verified = false

とする。

実際の接続確認成功後だけ、

    verified = true

とする。

---

# 36. save_mail_settings

保存成功条件：

1. CSRF検証成功
2. JSON形式が正しい
3. 入力値が正しい
4. 必須項目が正しい
5. settings.jsonを正常に読み込める
6. mailだけを更新する
7. kintone設定を変更しない
8. JSON保存成功
9. 保存後JSONを再読み込みできる
10. 保存内容を確認できる

保存失敗時には既存設定を保持する。

---

# 37. test_mail_settings

test_mail_settingsはsave_mail_settingsとは別処理とする。

「メール送信設定を確認」では、実際のSMTP接続確認を行う。

入力値だけを確認して成功としてはならない。

確認対象：

- SMTPサーバ
- ポート
- 接続方式
- TLS接続
- 認証の成否
- タイムアウト

パスワードをレスポンスへ含めない。

---

# 38. SMTP通信

SMTP通信処理では、

- 接続先
- ポート
- TLS
- 認証
- タイムアウト
- 通信失敗

を区別して扱う。

失敗時は利用者が再確認できる安全な情報を返す。

認証情報や内部通信情報を返さない。

---

# 39. kintone設定

設定項目：

- kintone利用先
- 顧客管理アプリID
- ログイン名
- パスワード
- プロキシ

APIトークンは使用しない。

認証にはkintoneログイン名とパスワードを使用する。

---

# 40. kintone利用先

以下を受け付ける。

    example
    example.cybozu.com
    https://example.cybozu.com

内部では、

    https://example.cybozu.com

として統一する。

https://の二重付与を行わない。

.cybozu.comの二重付与を行わない。

URL生成処理はアプリ内で統一する。

---

# 41. kintone通信

cURLは使用しない。

以下を使用する。

- stream_context_create
- file_get_contents

SSL証明書検証はkintone通信について無効固定とする。

画面からSSL証明書検証を変更できる項目を設けない。

---

# 42. kintoneプロキシ

プロキシは任意設定とする。

入力形式：

    host:port

プロキシ設定がある場合、kintoneへのすべての通信で同一設定を使用する。

プロキシ通信時には、

    proxy

および

    request_fulluri = true

を必ず適用する。

プロキシが空の場合は通常通信とする。

プロキシ認証は使用しない。

---

# 43. プロキシ入力検証

proxy_host_portはサーバー側でも検証する。

許可形式：

    hostname:port

または必要に応じて、

    IPv4:port

を許可する。

以下を拒否する。

- 改行
- 制御文字
- 認証情報を含むURL
- scheme付きURL
- 不正なポート
- 空のホスト
- 空のポート
- 65535を超えるポート

---

# 44. kintone認証

認証ヘッダーは、

    X-Cybozu-Authorization

を使用する。

Base64化する文字列は、

    trim(ログイン名) . ":" . trim(パスワード)

とする。

認証情報を画面、ログ、APIレスポンスへ出力しない。

---

# 45. kintone API GET

GETではリクエスト本文を送信しない。

パラメータはURLへ付与する。

クエリ生成には、

    http_build_query(
        $params,
        '',
        '&',
        PHP_QUERY_RFC3986
    )

を使用する。

GET通信でcontentを設定しない。

---

# 46. kintone API POST / PUT

POST / PUTではJSON形式で送信する。

JSON生成：

    json_encode(
        $data,
        JSON_UNESCAPED_UNICODE
    )

Content-Type：

    application/json

---

# 47. kintone接続確認

「接続設定を確認」は実際にkintone APIへアクセスする。

顧客管理アプリIDが設定されている場合：

    /k/v1/app.json?id={app_id}

を使用する。

アプリID未設定時の接続確認：

    /k/v1/apps.json?limit=1

を使用する。

入力値の形式確認だけで成功扱いにしない。

---

# 48. kintoneエラー

kintoneからエラーが返った場合、可能な範囲で以下を取得する。

- HTTPステータス
- code
- message
- errors

利用者には原因を判断できる安全な範囲だけを表示する。

表示禁止：

- パスワード
- Authorization
- Base64認証情報
- CSRF
- セッション情報
- プロキシ認証情報

---

# 49. 顧客項目対応

顧客情報はkintone顧客管理アプリから取得する。

最低限必要な情報：

- 顧客ID
- 顧客名
- メールアドレス

その他の表示項目についてはkintone項目コードとの対応を設定できるようにする。

最低限、以下の項目コードを明示的に設定できること。

- 顧客ID項目
- 顧客名項目
- メールアドレス項目

対応設定が未完了の場合、顧客取得成功として扱わない。

---

# 50. 顧客情報の形式

customers.jsonの顧客データは、画面表示用に正規化する。

例：

    {
      "customer_id": "123",
      "name": "山田太郎",
      "email": "example@example.com",
      "company": "",
      "source_record_id": "123"
    }

顧客IDは文字列として保持できる構造とする。

kintoneのレコード番号だけをアプリ内部の一意IDとして依存しない。

---

# 51. 顧客一覧取得

kintoneの取得件数だけで全顧客取得完了と判断してはならない。

ページングを行い、必要な全対象データを取得する。

途中で1回でも失敗した場合、customers.jsonを更新しない。

全件取得成功後に一括して保存する。

---

# 52. customers.json

最低限以下を保存する。

    {
      "version": 1,
      "updated_at": "",
      "source": "kintone",
      "count": 0,
      "customers": []
    }

画面では更新日時と件数を確認できるようにする。

取得失敗時には古いデータを「最新取得成功データ」として表示しない。

---

# 53. アンケート状態

アンケート状態は以下の3種類だけを使用する。

- draft
- open
- closed

`end`、`finished`、`complete`等の別名を使用しない。

画面表示：

- draft → 下書き
- open → 公開中
- closed → 終了

データと画面で状態値を統一する。

---

# 54. アンケートID

アンケートIDは一意とする。

質問ID、選択肢ID、グループIDもそれぞれ一意とする。

表示番号と内部IDを分離する。

質問の並べ替え・削除で表示番号が変わっても質問IDは変更しない。

---

# 55. アンケート基本データ

最低限以下を保持する。

- survey_id
- name
- description
- status
- created_at
- updated_at
- published_at
- closed_at
- start_at
- end_at
- numbering
- version
- groups

---

# 56. 質問グループ

グループは以下を保持する。

- group_id
- name
- sort_order
- questions

グループ追加は末尾に追加する。

グループ並べ替え後はsort_orderを更新する。

---

# 57. 質問

質問は以下を保持する。

- question_id
- display_number
- text
- type
- required
- sort_order
- options
- branch

回答形式：

- free
- single
- multiple

これ以外を許可しない。

---

# 58. 選択肢

選択肢は以下を保持する。

- option_id
- label
- sort_order

選択肢IDは表示文字列と分離する。

選択肢文言を変更してもoption_idは変更しない。

---

# 59. 自由記述

freeの場合、optionsは空配列とする。

自由記述に選択肢を保存してはならない。

---

# 60. 単一選択・複数選択

single / multipleの場合、選択肢を1個以上必須とする。

選択肢IDはアンケート内で一意とする。

---

# 61. 必須設定

requiredはbooleanで保持する。

サーバー側でも必須チェックを行う。

画面側だけのrequired属性を信用しない。

---

# 62. 質問番号

numberingには以下だけを使用する。

- global
- group

global：

    Q1
    Q2
    Q3

group：

    Q1-1
    Q1-2
    Q2-1

並べ替え後にはサーバー側でも表示番号を再計算できる構造とする。

表示番号そのものを質問の識別子として使用しない。

---

# 63. 分岐

分岐はsingle質問の選択肢単位で設定する。

分岐先：

- next
- question
- END

分岐なしはnextとして扱う。

存在しないquestion_idを保存してはならない。

削除・並べ替え後にも分岐先の整合性を再確認する。

---

# 64. 分岐循環

公開前にサーバー側で分岐を検証する。

循環する分岐を公開してはならない。

自己参照も循環として扱う。

---

# 65. 公開期間

公開開始日時と公開終了日時を保存する。

開始日時を設定した場合、その日時より前は回答受付を行わない。

終了日時を設定した場合、その日時以降は回答受付を行わない。

開始日時と終了日時を両方設定する場合、

    start_at < end_at

を必須とする。

---

# 66. 公開状態と公開期間

status=openだけでは回答可能とは限らない。

回答可能条件：

1. アンケートが存在する
2. status=open
3. 現在日時が公開開始日時以降
4. 公開終了日時が未設定、または現在日時が終了日時より前

終了操作後は公開終了日時に関係なく回答受付を終了する。

---

# 67. アンケート保存

save_surveyではサーバー側で全項目を再検証する。

検証対象：

- アンケート名
- 説明
- 状態
- 公開期間
- numbering
- グループ
- 質問
- 回答形式
- 選択肢
- 必須設定
- 分岐
- ID重複
- 並び順

---

# 68. 公開前検証

publish_survey実行時には、保存済みデータをサーバー側から再読み込みして検証する。

最低限：

- アンケート名
- グループ
- 質問
- 質問文
- 回答形式
- 選択肢
- 必須設定
- 分岐
- 公開期間

を確認する。

不備があれば公開しない。

---

# 69. 公開処理

公開操作はPOSTとする。

公開成功条件：

1. 対象アンケートが存在
2. 現在のversionが一致
3. draft状態
4. 公開前検証成功
5. 保存成功
6. 再読み込み確認成功

成功後にのみstatusをopenとする。

---

# 70. 終了処理

close_surveyはPOSTとする。

対象がopenの場合だけ終了可能とする。

終了成功後：

    status = closed

とする。

closedアンケートは回答受付を行わない。

---

# 71. 下書き削除

原則としてdraftのみ物理削除可能とする。

回答データまたはメール送信履歴が存在するアンケートを物理削除してはならない。

関連データがある場合は削除拒否する。

---

# 72. 公開中アンケート編集

open状態のアンケートについて、回答データとの整合性を壊す変更を無条件に許可しない。

特に以下は原則として禁止する。

- 回答済み質問の削除
- 回答済み選択肢の削除
- 回答形式の変更
- 分岐先の変更

変更が必要な場合は、別アンケートとして作成する運用を基本とする。

公開中アンケートを編集可能とする場合は、回答データへ影響しない項目だけを許可する。

---

# 73. 回答者用URL

公開アンケートには回答者用URLを発行する。

URLにはアンケートIDだけをそのまま推測できる形式を使用しない。

十分な長さのランダムな公開キーを使用する。

例：

    public_token

public_tokenはアンケートごとに一意とする。

---

# 74. 回答者用URLのアクセス条件

回答者用URLから以下へアクセスできない。

- draft
- closed
- 公開期間外

公開キーが存在しない場合は404として扱う。

---

# 75. 回答者画面

回答者画面には運営者向け機能を表示しない。

表示禁止：

- 運営者メニュー
- 設定画面
- 顧客一覧
- kintone設定
- メール設定
- 管理画面への戻る導線

回答者画面から管理画面へ移動できる導線を設けない。

---

# 76. 回答者識別

顧客一覧に存在する回答者については、以下を関連付ける。

- survey_id
- customer_id
- send_log_id
- response_id

顧客一覧に存在しない回答者からの回答も許可する。

顧客一覧に存在しないことだけを理由に回答を拒否しない。

---

# 77. 回答者情報

回答者識別情報は必要最小限だけ保持する。

メールアドレス等の個人情報を回答URLへ直接埋め込まない。

回答者用公開キーから顧客情報を推測できない構造とする。

---

# 78. 回答データ

responses.jsonには最低限以下を保持する。

- response_id
- survey_id
- public_token
- submitted_at
- respondent_identifier
- customer_id
- send_log_id
- completed
- answers
- survey_snapshot
- version

---

# 79. 回答時点スナップショット

回答データには、回答時点の質問・選択肢を識別できる情報を保持する。

現在のアンケート定義だけを参照して過去回答を復元してはならない。

最低限、

- question_id
- question_text
- question_type
- option_id
- option_label

を必要に応じて保存する。

---

# 80. 回答保存検証

save_responseではサーバー側で以下を検証する。

- アンケート存在
- 公開状態
- 公開期間
- public_token
- 質問存在
- 必須回答
- 回答形式
- 選択肢存在
- 複数選択値
- 不正question_id
- 不正option_id
- 自由記述長
- 回答件数
- 回答構造

画面側の入力チェックだけを信用しない。

---

# 81. 自由記述

自由記述の最大文字数をサーバー側で定義する。

最大文字数を超えた回答は保存しない。

HTML、JavaScript、タグ等をHTMLとして解釈しない。

画面表示時は文字列として表示する。

---

# 82. 回答二重送信

回答送信には一意な送信識別子を使用する。

同一送信識別子が再送された場合、回答を重複登録しない。

ネットワーク障害による再送でも二重登録されないこと。

---

# 83. 回答完了

サーバー側保存成功後だけcompleted=trueとする。

保存失敗時は回答完了として扱わない。

完了画面は保存成功後だけ表示する。

---

# 84. 回答結果集計

集計はresponses.jsonから行う。

顧客一覧に存在しない回答者も集計対象とする。

質問ごとに必要に応じて、

- 回答数
- 未回答数
- 割合

を表示する。

---

# 85. 回答率

回答率：

    回答完了者数 ÷ 回答対象者数 × 100

回答対象者数は、実際に送信処理で確定した対象者数を使用する。

送信対象外の顧客を母数へ含めない。

自発的な回答者は回答数には含めるが、メール送信対象者数を増加させない。

---

# 86. 単一選択集計

singleでは選択肢ごとに、

- 回答数
- 割合

を表示する。

割合の母数は、その質問への有効回答者数とする。

---

# 87. 複数選択集計

multipleでは選択肢ごとの選択回数を集計する。

一人が複数選択した場合、それぞれ1回として集計する。

割合：

    選択肢の選択回数
    ÷
    複数選択質問への有効回答者数

---

# 88. 自由記述集計

freeでは回答内容を一覧表示する。

回答内容をHTMLとして解釈しない。

JavaScriptを実行しない。

---

# 89. メール送信対象

送信対象者はcustomers.jsonから選択する。

画面では、

- 顧客検索
- 複数選択
- 選択解除
- 選択者確認

を行える。

送信実行前に対象者数と対象者一覧を確認する。

---

# 90. 送信対象者の確定

画面上の選択状態だけを送信対象として信用しない。

メール送信開始時にサーバー側で顧客IDを再取得する。

以下を確認する。

- 顧客IDが存在する
- 顧客が現在の顧客一覧に存在する
- メールアドレスが妥当
- 重複対象がない
- 送信対象者数が1以上

送信処理中に対象者が変更されないよう、送信処理単位で対象者を確定する。

---

# 91. メール内容

送信前に、

- 件名
- 本文
- 回答用案内

を確認・編集できる。

件名・本文には改行や制御文字等の不正入力を適切に処理する。

回答用URLはサーバー側で生成する。

---

# 92. 回答用URLの生成

回答用URLは送信対象者ごとに生成する。

回答URLへ顧客のメールアドレスや氏名を直接埋め込まない。

送信対象者と回答URLの対応をサーバー側で保持する。

---

# 93. メール送信前確認

送信前確認では以下を表示する。

- アンケート名
- 送信対象者数
- 送信対象者
- 件名
- 本文
- 回答用案内

確認画面から送信実行を行う。

確認画面表示だけでは送信処理を開始しない。

---

# 94. メール送信事前検証

send_surveyではサーバー側で以下を再検証する。

- アンケート存在
- status=open
- 公開期間内
- メール設定存在
- SMTP設定有効
- 送信対象者1名以上
- メールアドレス妥当
- 件名入力済み
- 本文入力済み
- 対象者が現在も有効
- 対象者重複なし

いずれかに問題があれば送信処理を開始しない。

---

# 95. メール送信二重実行

送信ボタンは通信開始前にdisabled=trueとする。

ただしブラウザ側だけで二重送信を防止したことにしてはならない。

サーバー側でも送信処理の重複を防止する。

送信要求には一意なsend_request_idを付与する。

同一send_request_idが再送された場合、同一送信処理を二重実行しない。

---

# 96. メール送信履歴

mail_logs.jsonへ送信履歴を保存する。

最低限：

- send_log_id
- send_request_id
- survey_id
- created_at
- sent_at
- target_count
- success_count
- failure_count
- recipients
- subject
- result

を保持する。

パスワード、Authorization、CSRFトークン等は保存しない。

---

# 97. 対象者ごとの送信結果

recipientsには対象者ごとに、

- customer_id
- name
- email
- status
- sent_at
- error_category
- error_message

を保持する。

status：

- success
- failed

失敗理由は利用者が再送判断できる範囲だけ保存・表示する。

---

# 98. メール送信失敗

一部失敗しても成功者を失敗扱いにしない。

対象者単位で成功・失敗を記録する。

送信処理全体の結果と対象者単位の結果を分離する。

---

# 99. メール送信成功後の履歴保存

メール送信結果を取得した後、送信履歴を保存する。

送信結果の保存に失敗した場合でも、既に送信されたメールを再送してはならない。

送信済み状態と履歴保存状態を区別して扱う。

---

# 100. 再送

再送は過去の送信履歴を上書きしない。

新しいsend_log_idを発行する。

過去に成功した対象者は、明示的に再送対象として選択されない限り再送しない。

原則として失敗者だけを再送候補とする。

---

# 101. 再送対象確認

再送前に、

- アンケート状態
- 対象者
- 前回結果
- 件名
- 本文

を再確認する。

再送対象者数と一覧を表示する。

---

# 102. 送信履歴の表示

送信履歴では、

- 送信日時
- 対象者数
- 成功数
- 失敗数

を確認できる。

失敗者を抽出できる。

失敗者だけを再送対象として選択できる。

---

# 103. 顧客更新と送信履歴

顧客一覧を更新しても過去の送信履歴を書き換えない。

送信履歴には送信時点の、

- customer_id
- name
- email

を保存する。

これにより顧客情報が後から変更されても過去履歴を確認できるようにする。

---

# 104. データ関連性

以下の関連を維持する。

    survey
      ↓
    send_log
      ↓
    recipient
      ↓
    response

同じ顧客が複数回送信された場合も、それぞれを別送信として識別できること。

---

# 105. 顧客一覧に存在しない回答

顧客一覧に存在しない回答者についても、

- response_id
- survey_id
- submitted_at
- respondent_identifier

を保存できる。

顧客IDが存在しないことをエラーにしない。

---

# 106. 回答と送信履歴の関連

メールから回答した場合は可能な範囲で、

- survey_id
- public_token
- customer_id
- send_log_id

を関連付ける。

自発的回答の場合はsend_log_idを必須としない。

---

# 107. 認証

運営者向け機能は運営者以外が利用できないこと。

認証方式が既存Apache認証の場合は、それを利用する。

独自認証を実装してはならない。

認証方式が未決定の場合、本番実装前に確定する。

---

# 108. 回答者と運営者の分離

回答者用URLから運営者画面へ移動できないこと。

運営者向けAPIを回答者が利用できないこと。

回答者用APIと運営者用APIを権限上区別する。

---

# 109. 権限確認

CSRF検証だけで権限確認を完了したことにしてはならない。

運営者向け状態変更APIでは、

1. 認証
2. 権限
3. CSRF
4. 入力検証
5. 業務ルール検証
6. 保存・実行

の順で確認する。

---

# 110. HTTPレスポンスヘッダー取得

コード全体で、

    $http_response_header

を直接参照しない。

PHP 8.4 / 8.5対応として、安全な共通処理を使用する。

---

# 111. kintone通信エラー

kintone通信では、

- 通信失敗
- HTTPエラー
- JSON解析失敗
- 認証失敗
- アプリ不存在
- 権限不足
- プロキシ接続失敗
- タイムアウト

を区別する。

利用者には次に確認すべき内容を表示する。

---

# 112. 外部通信タイムアウト

外部通信にはタイムアウトを設定する。

無期限に処理を待たせない。

タイムアウト時には利用者が再実行できるメッセージを表示する。

---

# 113. kintone通信とプロキシ

kintoneへのすべての通信で、保存済み設定を共通利用する。

一部のkintone APIだけプロキシを使用しない状態を作らない。

プロキシ設定変更後は、次回通信から新設定を使用する。

---

# 114. エラーメッセージ

利用者向けエラーは、次に確認すべきことが分かる内容とする。

例：

    メール設定を保存できませんでした。
    入力内容または保存状態を確認してください。

    セッションの有効期限が切れています。
    画面を再読み込みしてもう一度お試しください。

    kintoneへ接続できませんでした。
    接続先、ログイン情報、プロキシ設定を確認してください。

内部例外の詳細をそのまま表示しない。

---

# 115. エラーログ

エラーログへ以下を出力しない。

- パスワード
- Authorization
- Base64認証情報
- CSRF
- セッションID
- メール本文に含まれる個人情報
- プロキシ認証情報

エラー原因の特定に必要な最小限の情報だけを記録する。

---

# 116. バックアップ

JSON更新時に既存データを破壊しない。

バックアップを作成する場合、外部から直接取得できない場所へ保存する。

バックアップにも、

- パスワード
- 認証情報
- CSRF
- セッション情報

が含まれることを前提として保護する。

---

# 117. データ保持期間

以下について保存期間を決定する。

- アンケート
- 回答
- 顧客一覧
- メール送信履歴

保存期間を超えて削除する場合は、

- 対象
- 条件
- 実行時期
- 集計結果への影響

を明確にする。

回答を削除すると集計結果が変わるため、回答削除を自動化する場合は特に注意する。

---

# 118. モックとの対応

本番版ではモックの以下の業務フローを維持する。

- アンケート一覧
- アンケート作成
- アンケート編集
- アンケート内容確認
- 顧客一覧
- 設定
- メール設定
- kintone設定
- 顧客選択
- メール送信確認
- メール送信
- 送信結果
- 回答状況
- 回答結果
- 公開
- 終了

ただし、モック上でJavaScript変数だけを変更している処理については、本番版では正式なサーバー処理へ置き換える。

# 119. モック上の仮成功表示

モックで、

    メール送信が完了しました

と表示しているだけの処理は、本番版では送信成功の根拠として扱わない。

本番版では実際のSMTP送信結果を取得し、対象者単位で記録する。

---

# 120. モック上の状態値

モックでは画面上の状態値を変更できても、本番版ではサーバー側の状態を正式値とする。

状態値は、

- draft
- open
- closed

に統一する。

---

# 121. アンケート編集画面

アンケート作成・編集は1画面で行う。

同じ画面で、

- 基本情報
- グループ
- 質問
- 選択肢
- 必須設定
- 分岐
- 並び順

を編集できる。

質問ごとに別画面へ移動しない。

---

# 122. 並べ替え

グループを並べ替えられる。

質問を並べ替えられる。

グループ追加はグループ末尾。

質問追加はグループ内末尾。

並べ替え後に質問番号を自動更新する。

---

# 123. 未保存変更

アンケート編集中に未保存変更がある場合、画面上で知らせる。

未保存状態で別画面へ移動する場合は確認を行う。

利用者が意図せず変更内容を失わないこと。

---

# 124. 設定画面

設定画面では、

- メール設定
- kintone設定

を分けて表示する。

メール設定保存によってkintone設定を初期化してはならない。

kintone設定保存によってメール設定を初期化してはならない。

---

# 125. 保存結果

保存成功時には、サーバー側保存が成功したことを明示する。

画面上の値だけを変更した状態を保存成功として表示しない。

保存失敗時には入力値を保持する。

---

# 126. APIの一貫性

画面側の関数名、action名、サーバー側action処理を一致させる。

実装要件に記載されているactionが未実装の状態を許容しない。

特に以下は必須とする。

- test_mail_settings
- send_survey

API一覧に存在するだけでなく、サーバー側処理を実装する。

---

# 127. API action不正

未知のactionが指定された場合、

    HTTP 404

とする。

成功レスポンスを返さない。

---

# 128. HTTPメソッド不正

POSTが必要なactionへGETでアクセスされた場合は、

    HTTP 405

とする。

GETが必要な参照APIへ不正な状態変更リクエストを送らない。

---

# 129. Content-Type

JSON POSTでは、

    Content-Type: application/json

を使用する。

JSONとして解析できない本文を受信した場合はHTTP 400とする。

JSON以外の入力を暗黙に受け入れない。

---

# 130. JSON入力サイズ

リクエスト本文には適切な最大サイズを設ける。

過大なJSONを無制限に受け付けない。

特に、

- アンケート
- 回答
- メール本文

について上限を明確にする。

---

# 131. 入力文字数

最低限、以下の上限を定義する。

- アンケート名
- アンケート説明
- グループ名
- 質問文
- 選択肢
- SMTPサーバ
- kintoneドメイン
- メール件名
- メール本文
- 自由記述回答

画面側とサーバー側で同じ上限値を使用する。

---

# 132. 配列件数

アンケートについて以下の最大件数を定義する。

- グループ数
- グループあたり質問数
- 質問あたり選択肢数

制限を超えたデータを保存しない。

回答についても質問数・選択数の上限を設ける。

---

# 133. ID検証

クライアントから送信されたIDをそのまま信用しない。

以下をサーバー側で確認する。

- 対象survey_idが存在する
- 対象question_idが対象アンケートに存在する
- option_idが対象質問に存在する
- group_idが対象アンケートに存在する
- customer_idが顧客一覧に存在する

---

# 134. ID改ざん

利用者がブラウザの開発者ツール等でIDを変更しても、他のアンケートや顧客のデータを操作できないこと。

対象データの所有関係をサーバー側で確認する。

---

# 135. 回答URL改ざん

public_tokenを変更して別アンケートへアクセスできる構造にしない。

公開キーとアンケートの対応をサーバー側で確認する。

---

# 136. メール送信URL改ざん

送信APIへ任意のsurvey_idやcustomer_idを送信しても、権限のないデータを送信対象にできないこと。

サーバー側で対象者とアンケートの関連を再確認する。

---

# 137. kintone顧客取得の整合性

顧客取得に失敗した場合、取得途中のデータをcustomers.jsonへ保存しない。

全件取得成功後に置き換える。

---

# 138. 設定保存の部分更新

save_mail_settingsではmailだけを更新する。

save_kintone_settingsではkintoneだけを更新する。

片方の設定を保存した結果、もう片方が空になる状態を許可しない。

---

# 139. APIと画面状態

API成功後にだけ画面上の正式状態を更新する。

API失敗時に成功したような表示へ変更しない。

特に、

- 保存
- 公開
- 終了
- 送信
- 回答完了

について厳守する。

---

# 140. ローディング制御

通信を伴うボタンは通信開始前に、

    disabled = true

を設定する。

同時にCSSローディングクラスを付与する。

通信終了時にはfinallyで解除する。

通信失敗時も必ず解除する。

---

# 141. イベントリスナー

イベントリスナー登録時には対象要素の存在を確認する。

存在しない要素に対してaddEventListenerを実行してJavaScript全体を停止させてはならない。

---

# 142. DOM描画

DOM描画ではtextContentを基本とする。

HTMLを生成する必要がある場合は、動的データを安全にエスケープする。

顧客名、メールアドレス、アンケート名、質問文、自由記述回答、メール本文等を未処理のままHTMLへ挿入しない。

---

# 143. URL表示

回答者URLを画面へ表示する場合、URL自体をHTMLとして解釈しない。

リンクとして表示する場合は、許可されたアプリ内URLだけを使用する。

---

# 144. 外部URL

JavaScriptへ本番ホスト名を固定記述しない。

アプリ内部APIは現在のindex.phpを基準にする。

kintone URLはサーバー側で正規化して生成する。

---

# 145. Origin:nullと今回の障害

今回確認された、

    Access to fetch ... from origin 'null' has been blocked by CORS policy

は、Origin:nullのプレビュー環境から実サーバーAPIへアクセスしていることが原因として扱う。

本番アプリ側でOrigin:nullを許可することで解決してはならない。

本番実行時はHTTP/HTTPSの同一Originからindex.phpを表示し、そのindex.php自身へAPIリクエストする。

プレビュー環境から実サーバーAPIを操作する必要がある場合は、プレビュー環境側の同一Origin通信機構を使用する。

---

# 146. 本番API URL生成

JavaScriptではAPI URLを、

    new URL(window.location.href)

等、現在表示中のindex.phpを基準として生成する。

本番ホスト名を固定しない。

配置場所が変わっても自身のAPIを呼び出せること。

---

# 147. API通信のCredentials

本アプリ自身への通信では必要なセッションCookieを送信する。

外部Originへセッション付き通信を行う構成を作らない。

CORSを利用したセッション共有を前提としない。

---

# 148. 参照API

参照APIでは状態変更を行わない。

例：

- load_settings
- load_customers
- load_surveys
- load_survey
- load_public_survey
- load_mail_logs
- aggregate_responses

参照APIでPOSTを必須とする必要がない場合はGETとする。

---

# 149. load_settings

画面表示用設定にはパスワードを含めない。

例：

    {
      "mail": {
        "smtp_server": "...",
        "smtp_port": 587,
        "security": "STARTTLS",
        "configured": true,
        "verified": true
      },
      "kintone": {
        "domain": "...",
        "app_id": "...",
        "login_name": "...",
        "proxy_enabled": true,
        "configured": true,
        "verified": true
      }
    }

パスワードの存在有無が必要な場合も、実際の値を返さない。

---

# 150. 接続確認結果

接続確認結果は設定保存状態と分離する。

保存成功：

    configured = true

接続確認成功：

    verified = true

設定変更後：

    verified = false

---

# 151. 保存版情報

以下の状態変更データにはversionを持たせる。

- settings
- survey
- customers
- mail_log

versionは保存成功ごとに更新する。

---

# 152. 競合時の画面表示

HTTP 409の場合は、

    他の画面でデータが更新されています。
    最新の状態を読み込んでからもう一度操作してください。

等を表示する。

古い入力内容を自動的に上書き保存しない。

---

# 153. 保存失敗時

保存失敗時に画面の入力内容をサーバー側最新値へ勝手に置き換えない。

利用者が入力した内容を保持する。

必要に応じて「最新データを再読み込み」操作を提供する。

---

# 154. データ削除

物理削除を行う場合、関連データの存在を確認する。

回答またはメール送信履歴が存在するデータを物理削除しない。

削除後に参照できなくなるデータについて、関連性を壊さない。

---

# 155. 集計データ

集計値を正式データとして別JSONへ二重保存しないことを基本とする。

responses.jsonを正式データとし、集計画面では必要に応じて都度集計する。

集計結果をキャッシュする場合は、元データとの差異を検出できること。

---

# 156. メール送信と回答率

回答率の母数は「顧客一覧の総件数」ではない。

実際に送信対象として確定した人数を使用する。

送信対象者が10人、成功送信8人の場合など、送信失敗者を母数へ含めるかどうかを明確にする。

本アプリでは、原則として「メール送信対象として確定した人数」を母数とする。

---

# 157. メール送信失敗者の扱い

送信失敗者は回答率の母数には含める。

ただし送信失敗者が回答した場合は回答数へ反映する。

再送成功後も同一顧客を二重に母数へ加算しない。

---

# 158. 再送後の回答

同一アンケートについて同一顧客へ再送しても、回答者数を二重計上しない。

回答完了者数は回答者単位で集計する。

送信回数ではなく回答者数を基準とする。

---

# 159. 同一顧客の複数回答

同一アンケートについて同一顧客が複数回回答できるかを明確化する。

原則として、1顧客1アンケート1完了回答とする。

同一顧客からの再回答を許可する場合は、別途明示的な再回答ルールを設ける。

---

# 160. 回答者識別なしの場合

顧客識別ができない自発的回答については、回答URL単位または送信識別子単位で二重送信を防止する。

---

# 161. メール本文

メール本文には回答者用URLを正しく埋め込む。

HTMLメールを採用するかプレーンテキストメールを採用するかを明確にする。

未決定の場合は、本番実装前に確定する。

---

# 162. SMTP送信形式

SMTP送信では、

- From
- To
- Subject
- Body
- Content-Type
- TLS
- 認証

を適切に設定する。

メールヘッダーへ利用者入力を直接連結しない。

---

# 163. メール送信件数

大量送信時に1リクエストで無制限に処理しない。

対象件数の上限を定義する。

上限を超える場合の処理方法を明確にする。

---

# 164. 大量送信

対象者数が多い場合、

- 処理時間
- タイムアウト
- 部分成功
- 再送

を考慮する。

1人の送信失敗によって全対象者を失敗扱いにしない。

---

# 165. 外部通信のログ

kintoneやSMTPへの通信ログを残す場合、認証情報を含めない。

URLに認証情報を含めない。

リクエスト本文にパスワードが含まれる場合、その本文をログへ出力しない。

---

# 166. PHP 8.4 / 8.5互換性

PHP 8.4 / 8.5で動作する構成とする。

暗黙的なnullable型指定を使用しない。

関数引数・戻り値の型を明確にする。

PHP 8.4 / 8.5で問題となる非推奨機能を使用しない。

---

# 167. HTTPレスポンスヘッダー取得

以下を直接使用しない。

    $http_response_header

HTTPレスポンスヘッダー取得は共通関数へ集約する。

---

# 168. JSONエンコード

JSONエンコード失敗を無視しない。

UTF-8不正データを適切に処理する。

JSONレスポンスではUTF-8を使用する。

---

# 169. UTF-8

HTML、CSS、JavaScript、PHP、JSONすべてUTF-8で統一する。

Shift-JISを前提とした処理を追加しない。

外部データを取り込む場合は文字コードを確認する。

---

# 170. ファイル保存

JSON保存時のファイルパスは固定されたアプリルート配下だけを使用する。

利用者入力をそのままファイルパスとして使用しない。

ディレクトリトラバーサルを許可しない。

---

# 171. ファイルロック

JSON更新では排他ロックを使用する。

読み込み・変更・保存の競合を考慮する。

---

# 172. 保存途中の破損防止

JSONファイルへ直接上書きするだけの保存を行わない。

一時ファイルへ完全なJSONを書き込み、正常性を確認した後に正式ファイルへ置き換える方式を基本とする。

---

# 173. バックアップと復旧

保存前データを復元可能な状態にする。

保存失敗時に空ファイルや途中までのJSONが正式データとして残らないこと。

---

# 174. 画面遷移

モックと同じ業務上の流れを維持する。

特に、

    一覧
      ↓
    アンケート選択
      ↓
    内容 / 送信 / 回答状況 / 回答結果

という流れを維持する。

# 175. アンケート一覧

一覧には以下を表示する。

- アンケート名
- 状態
- 作成日
- 公開期間
- 回答数
- 最終更新日

一覧上に個別アンケートの詳細ダッシュボードを常時表示しない。

# 176. 個別アンケート管理

アンケート選択後に、

- アンケート内容
- 送信
- 回答状況
- 回答結果

を利用できる。

---

# 177. 回答状況

回答状況では必要に応じて、

- 回答数
- 回答率
- 未回答数
- 送信済み人数
- 公開期間
- 回答状況推移

を確認できる。

表示値は正式データから算出する。

モックの固定値を使用しない。

# 178. 回答結果

回答結果では、

- 質問別回答数
- 未回答数
- 割合
- 単一選択結果
- 複数選択結果
- 自由記述一覧

を表示する。

---

# 179. モック固定値の扱い

モックに存在する、

- 固定回答数
- 固定送信数
- 固定回答率
- 固定グラフ値
- 固定送信成功数

を本番版で正式データとして使用してはならない。

すべてサーバー側データから算出する。

- Origin:nullを本番アプリ側で許可しない
- プレビューから本番APIへの直接状態変更通信を正式動作としない
- プレビュー環境で通信確認が必要な場合は同一Originの中継方式を使用する
- プレビュー環境と本番実行環境の違いを利用者に分かるようにする

## 環境

- Apache 2.4で動作する
- PHP 8.4 / 8.5で動作する
- Windows / Unixで動作する
- データベースを使用しない
- JSONファイルへ保存する
- HTML / CSS / JavaScript / PHPを1つのindex.phpへ格納する
- cURLを使用しない
- UTF-8で統一する

# 181. 本実装における最重要制約

本番実装では、画面上の見た目やJavaScript上の状態だけで業務処理の成立を判断してはならない。

以下は必ずサーバー側の正式処理とする。

- 保存
- 公開
- 終了
- 顧客更新
- メール送信
- 送信履歴
- 再送
- 回答保存
- 回答完了
- 集計

また、アプリ管理ツールのプレビューで発生するOrigin:nullについては、本番APIのCORS緩和によって解決しない。

本番利用ではHTTP/HTTPSでindex.phpを直接表示し、同一Originで本アプリAPIを利用する。

プレビュー環境から本番APIを操作する必要がある場合は、プレビュー環境側で安全な同一Origin通信を提供する。

この方針を本番実装の前提条件とする。

# アンケート業務運営アプリ 実装要件
## 全差し替え版

### 1. 実行環境

- Apache 2.4
- PHP 8.5
- データベースは使用しない
- アプリケーションは `index.php` 1ファイルで構成する
- PHP / HTML / CSS / JavaScript は `index.php` に含める
- アンケート、顧客、回答、送信状態、設定等の永続データはJSONファイルに保存する
- 文字コードはUTF-8
- PHPからの外部HTTP通信でcURLは使用しない
- kintone通信は `stream_context_create()` と `file_get_contents()` を使用する

---

### 2. 画面とAPIの実行方式

画面表示とAPI処理は同じ `index.php` で処理する。

APIはクエリー文字列で識別する。

例：

    index.php?api=bootstrap
    index.php?api=save_survey
    index.php?api=publish
    index.php?api=close
    index.php?api=submit_answer

ブラウザからPHP APIへ通信する際、開発環境のホスト名やディレクトリを固定してはならない。

API送信先は、現在表示している `index.php` を基準に決定する。

---

### 3. file:// で直接開かれた場合

`index.php` が `file://` から直接開かれている場合、PHP APIへの通信を実行しない。

画面にはApache経由で開く必要があることを表示する。

`file://` から別originのPHPへ通信することでCORSを回避する方式は採用しない。

通常の実行時は、画面とAPIが同一originになる構成とする。

CORSを解決するためだけに `Access-Control-Allow-Origin` を追加する実装は行わない。

---

### 4. データ保存

アプリケーションルート配下に以下のJSONファイルを使用する。

    data/
      surveys.json
      customers.json
      responses.json
      answer_tokens.json
      send_logs.json
      settings.json

ファイルが存在しない場合は初回起動時に作成する。

JSONファイルが破損している場合、空データとして扱って既存データを上書きしてはならない。

JSONの読み書きではファイルロック等を使用し、同時アクセスによるデータ破損を防止する。

---

### 5. アンケートデータ

1アンケートにつき以下を保持する。

    id
    name
    description
    status
    startAt
    endAt
    numberingFormat
    groups
    createdAt
    updatedAt

statusは以下の3種類とする。

    draft
    published
    closed

---

### 6. グループ

各アンケートは複数の質問グループを持つ。

グループは以下を保持する。

    id
    name
    questions

グループの配列順を表示順とする。

グループの追加、削除、並び替えを可能とする。

グループ削除時に質問が存在する場合、その質問も削除対象となる。

---

### 7. 質問

質問は以下を保持する。

    id
    text
    type
    required
    choices
    branches

typeは以下の3種類に限定する。

    text
    single
    multiple

質問について追加、編集、削除、並び替えを可能とする。

---

### 8. 選択肢

`single` と `multiple` の質問のみ選択肢を持つ。

選択肢は以下を保持する。

    id
    label

同一質問内で選択肢IDを一意とする。

選択肢の追加、編集、削除、並び替えを可能とする。

空の選択肢は保存不可とする。

同一質問内に同じ選択肢を重複して保存しない。

---

### 9. 質問番号

質問番号形式は以下の2種類とする。

    global
    group

globalの場合：

    Q1
    Q2
    Q3
    Q4

groupの場合：

    Q1-1
    Q1-2
    Q2-1
    Q2-2

質問番号は固定値として永続保存せず、現在のグループ・質問の配列順から算出する。

グループや質問の追加、削除、並び替えに応じて自動更新する。

---

### 10. 分岐

分岐は `single` の質問のみ設定可能とする。

各選択肢から以下のいずれかへ分岐できる。

    next
    question:<question_id>
    end

意味：

    next
      通常の次の質問へ進む

    question:<question_id>
      指定された質問へ移動する

    end
      回答を終了する

分岐が設定されていない場合は通常の次の質問へ進む。

---

### 11. 分岐の検証

保存時および公開時に分岐設定を検証する。

以下は不正として扱う。

- `single` 以外の質問に分岐が設定されている
- 存在しない選択肢に分岐が設定されている
- 存在しない質問を分岐先に指定している
- 削除済み質問を参照している
- 不正な分岐値が設定されている
- 循環分岐が発生する

例：

    Q1 → Q3
    Q3 → Q2
    Q2 → Q1

このような循環は保存・公開不可とする。

質問の削除や並び替えによって分岐先が不整合になった場合は、編集画面で警告を表示し、修正対象を明示する。

---

### 12. アンケート保存

アンケート保存時にはサーバー側で以下を検証する。

- アンケート名
- 公開開始日時
- 公開終了日時
- グループ
- 質問
- 質問形式
- 必須設定
- 選択肢
- 分岐
- 各IDの重複
- 分岐先
- 循環分岐
- データ型
- 入力サイズ

JavaScript側のチェックだけでは保存を許可しない。

---

### 13. 公開前検証

公開処理では保存済みデータを再検証する。

以下に問題がある場合は公開しない。

- アンケート名が未入力
- 質問文が未入力
- 必須項目の不備
- 選択肢の不備
- 分岐先の不備
- 循環分岐
- 公開期間の不整合

保存時に問題がなくても、公開時に再検証する。

---

### 14. 公開期間

公開開始日時と終了日時を保持する。

回答可能条件は以下をすべて満たすこと。

    status = published
    startAt <= 現在日時
    現在日時 <= endAt

現在日時はPHP側のサーバー時刻を基準とする。

ブラウザ側の現在時刻だけで公開期間を判定してはならない。

---

### 15. 公開・終了・削除

#### 公開

下書き状態から公開中へ変更する。

公開時には公開前検証を実行する。

#### 終了

公開中のアンケートを終了状態へ変更する。

終了後は新しい回答を受け付けない。

既存の回答データは保持する。

#### 削除

下書きのみ削除可能とする。

公開中および終了状態のアンケートは削除不可とする。

下書き削除時には、そのアンケートに紐付く回答データ、回答トークン、送信ログ等も整合性を保って削除する。

他のアンケートのデータを削除してはならない。

---

### 16. 回答者識別

メール送信対象者ごとに推測困難な回答トークンを発行する。

回答URLは現在の `index.php` を基準として生成する。

例：

    index.php?answer=<surveyId>&token=<token>

回答トークンには少なくとも以下を保持する。

    tokenId
    surveyId
    customerId
    email
    issuedAt
    usedAt

連番や顧客IDだけで回答者を識別してはならない。

---

### 17. 回答者画面

回答者用画面は管理画面とは独立した画面とする。

回答者画面には以下を表示する。

- アンケートタイトル
- 説明文
- 質問
- 回答入力欄
- 送信ボタン
- 完了画面

管理者向けヘッダーメニューや管理画面への戻るリンクを表示しない。

---

### 18. 回答者画面へのアクセス制御

以下の場合は回答フォームを表示せず、適切なメッセージを表示する。

- アンケートが存在しない
- tokenが存在しない
- tokenが対象アンケートのものではない
- tokenが使用済み
- アンケートが下書き
- アンケートが終了
- 公開期間外

---

### 19. 回答受付

回答送信時にはサーバー側で以下を確認する。

- アンケートの存在
- 公開状態
- 公開期間
- 回答トークンの存在
- 回答トークンとアンケートの一致
- 回答トークンの未使用
- 回答内容の形式
- 必須回答
- 分岐による到達可能性
- 選択肢の正当性

---

### 20. 必須回答と分岐

分岐によって表示対象外となった質問は、必須回答チェックの対象にしない。

例えば、

    Q1 = 「参加しない」
    → end

の場合、Q2以降が必須であっても回答を要求しない。

回答受付APIでも同じルールを適用する。

ブラウザ側だけでスキップ判定を行ってはならない。

---

### 21. 回答形式別バリデーション

#### text

文字列として受け取る。

最大文字数を設定し、サーバー側で超過を拒否する。

HTMLやJavaScriptとして解釈しない。

#### single

1件の選択肢だけを受け取る。

登録されていない選択肢は拒否する。

#### multiple

配列として受け取る。

すべて登録済み選択肢であることを確認する。

同一選択肢の重複を拒否する。

---

### 22. 回答データ

回答は以下を保持する。

    id
    surveyId
    tokenId
    customerId
    customerName
    customerEmail
    answeredAt
    answers

customerIdは任意とする。

kintoneの顧客一覧に存在しない回答者からの回答も受け付ける。

---

### 23. 重複回答防止

同じ回答トークンによる複数回の回答を防止する。

回答保存が成功した後にトークンを使用済みにする。

ブラウザの戻る操作や再送信によって二重回答されないよう、サーバー側で必ず確認する。

---

### 24. 回答状況

個別アンケートの回答状況画面では以下を表示する。

- 総回答件数
- メール送信数
- 到達数
- 回答率
- 未回答者数
- 日別回答件数
- 送信済み対象者
- 回答済み対象者
- 未回答対象者

回答率の計算対象を明確にし、送信対象者数を基準とする。

kintone顧客ではない外部回答者については、総回答件数には含めるが、送信対象者ベースの回答率とは区別して扱う。

---

### 25. 回答結果

質問ごとに回答を集計する。

#### single

- 選択肢ごとの回答数
- 選択肢ごとの割合

#### multiple

- 選択肢ごとの選択件数
- 選択肢ごとの割合

#### text

- 回答テキスト一覧

回答データがない場合は、回答が存在しない旨を表示する。

---

### 26. 分岐回答の集計

分岐によって回答対象外となった質問を「未回答」として集計してはならない。

質問ごとに実際にその質問へ到達した回答者を母数として割合を計算する。

例えばQ1の回答によってQ2がスキップされた場合、その回答者はQ2の未回答数にもQ2の割合計算の母数にも含めない。

---

### 27. 顧客データ

顧客データとして少なくとも以下を保持する。

    id
    name
    email
    company
    updatedAt

顧客一覧では氏名、メールアドレス等を表示・検索できる。

氏名およびメールアドレスによる絞り込み検索を可能とする。

---

### 28. kintone連携

kintone顧客管理アプリから顧客データを取得できる。

接続情報：

- サブドメイン
- アプリID
- ログイン名
- パスワード
- 顧客名のフィールドコード
- メールアドレスのフィールドコード
- プロキシホスト:ポート

APIトークンは使用しない。

プロキシ認証は使用しない。

SSL証明書検証は業務要件に従いデフォルト無効とする。

---

### 29. kintone URL

kintone接続先は設定されたサブドメイン等から正規化して生成する。

以下のような重複を発生させない。

    https://https://example.cybozu.com
    https://example.cybozu.com.cybozu.com

最終的に正しいkintone URLを生成する。

---

### 30. kintone通信

kintoneへのHTTP通信は以下を使用する。

    stream_context_create()
    file_get_contents()

cURLは使用しない。

プロキシ設定がある場合はHTTPコンテキストへ反映し、必要な場合は `request_fulluri` を使用する。

GETでは不要な `content` を送信しない。

クエリー文字列は適切にURLエンコードする。

JSONを送信するPOST/PUTでは、

    Content-Type: application/json

を設定する。

---

### 31. kintone認証

kintoneログイン情報を使用して認証する。

認証ヘッダーには、

    X-Cybozu-Authorization

を使用する。

認証情報そのものを画面やAPIレスポンスへ返さない。

---

### 32. kintone接続確認

kintone設定画面に接続確認機能を設ける。

接続確認では、軽量なkintone APIを使用する。

例：

    /k/v1/apps.json?limit=1

または対象アプリが設定済みの場合、

    /k/v1/app.json?id=<appId>

を使用する。

kintoneから返される `code`、`message`、`errors` 等を確認し、利用者が原因を判断できる範囲のエラー情報を表示する。

---

### 33. 顧客同期

「キントーンから最新情報を取得」操作により、kintoneの顧客データを取得する。

同期処理で既存データを不正に削除しない。

顧客情報をアンケート回答データと混在させない。

---

### 34. SMTP設定

以下を設定できる。

- SMTPホスト
- SMTPポート
- 暗号化方式
- 認証ユーザー名
- 認証パスワード
- 送信元メールアドレス
- 送信元表示名

暗号化方式：

    none
    ssl
    tls

パスワードは画面上で非平文表示とする。

APIレスポンスにパスワードを返さない。

---

### 35. SMTP接続確認

SMTP接続確認機能を実装する。

以下を確認できる。

- サーバーへ接続できるか
- SSL/TLS接続が成立するか
- 認証が成功するか
- 設定値が正しいか

エラー時には利用者が修正可能な範囲で原因を表示する。

---

### 36. 送信対象者

アンケートの「送信」画面では、kintoneから同期した顧客を送信対象として選択できる。

以下を可能とする。

- 氏名検索
- メールアドレス検索
- 個別選択
- 全選択
- 全選択解除
- 選択済み対象者確認

---

### 37. メール内容

送信メールについて以下を編集できる。

- 件名
- 本文

本文へ回答専用URLを差し込める。

回答URLは現在の `index.php` を基準として生成する。

固定ホスト名をメール本文へ埋め込まない。

送信前に実際のメール内容をプレビューできる。

---

### 38. 送信前確認

送信実行前に確認画面または確認ダイアログを表示する。

最低限以下を確認できる。

- 送信対象者数
- 件名
- 本文プレビュー

確認後に送信を実行する。

---

### 39. メール送信記録

送信記録を `send_logs.json` に保存する。

最低限以下を保持する。

    id
    surveyId
    customerId
    email
    name
    status
    sentAt
    answeredAt
    error

statusの例：

    pending
    sent
    failed
    answered

---

### 40. 二重送信防止

メール送信開始前に通常送信操作を二重実行できないようにする。

ブラウザ側で送信ボタンを即時無効化する。

サーバー側でも同一対象者への通常送信済み状態を確認する。

ブラウザの二重クリックだけを防止策としてはならない。

---

### 41. 送信結果

送信完了後に以下を表示する。

- 総対象者数
- 成功件数
- 失敗件数
- 送信日時

失敗した対象者がいる場合は一覧表示する。

---

### 42. 再送

送信失敗者のみを対象に再送できる。

成功済み対象者を再送対象にしない。

再送時にもサーバー側で送信状態を再確認する。

---

### 43. API

以下のAPIを実装する。

GET：

    ?api=bootstrap
    ?api=answer_bootstrap

POST：

    ?api=save_survey
    ?api=delete_survey
    ?api=publish
    ?api=close
    ?api=save_settings
    ?api=kintone_test
    ?api=sync_customers
    ?api=smtp_test
    ?api=send_mail
    ?api=resend_failed
    ?api=submit_answer

---

### 44. APIの権限確認

管理系APIは管理用セッションとCSRF検証を要求する。

対象：

    save_survey
    delete_survey
    publish
    close
    save_settings
    kintone_test
    sync_customers
    smtp_test
    send_mail
    resend_failed

回答送信APIは回答トークンを検証する。

URLパラメータを知っているだけで管理操作を実行できる構造にしない。

---

### 45. CSRF

状態変更を行う管理系POST APIではCSRF対策を実施する。

CSRFトークンはセッションに保存する。

リクエストヘッダー等で送信されたCSRFトークンをPHP側で検証する。

CSRF検証に失敗した場合は処理しない。

CSRFトークン自体をログや通常レスポンスへ不用意に出力しない。

---

### 46. セッション

PHPセッションを使用する。

セッションCookieは少なくとも以下を設定する。

    HttpOnly
    SameSite=Lax

セッションキーにはアプリ固有の名称を使用する。

---

### 47. XSS対策

HTML表示時は必ずエスケープする。

PHPでは以下の共通関数を使用する。

    h(?string $str): string

内部ではUTF-8を指定した `htmlspecialchars` を使用する。

JavaScriptでは原則として `textContent` を使用する。

ユーザー入力値を未加工で `innerHTML` に埋め込まない。

---

### 48. セキュリティヘッダー

可能な範囲で以下を設定する。

    X-Frame-Options: SAMEORIGIN
    X-Content-Type-Options: nosniff

---

### 49. JavaScript

すべてのJavaScript処理は `DOMContentLoaded` 後に実行する。

イベントリスナー登録時には対象要素の存在を確認する。

存在しない要素に対してイベントを登録しない。

通信処理では、開始前に対象ボタンを無効化し、ローディング状態を表示する。

通信終了時は成功・失敗にかかわらず操作状態を復旧する。

---

### 50. 編集中データ

アンケート編集画面では未保存変更を検知する。

変更を保存せずに別画面へ移動する場合は確認を表示する。

保存後は未保存状態を解除する。

通信失敗時に編集中の内容が消えないようにする。

---

### 51. APIエラー

APIエラーはJSON形式で返す。

例：

    {
      "ok": false,
      "error": {
        "code": "VALIDATION_ERROR",
        "message": "入力内容を確認してください",
        "fields": {}
      }
    }

最低限、以下のエラー区分を用意する。

    INVALID_REQUEST
    CSRF_ERROR
    NOT_FOUND
    VALIDATION_ERROR
    INVALID_STATE
    OUT_OF_PERIOD
    INVALID_TOKEN
    TOKEN_USED
    DUPLICATE_RESPONSE
    STORAGE_ERROR
    KINTONE_ERROR
    SMTP_ERROR
    SEND_ERROR

内部の物理パス、パスワード、認証情報、PHPの詳細エラー等は利用者向けレスポンスへ返さない。

---

### 52. PHP 8.5対応

PHP 8.4 / 8.5で問題となる古いHTTPレスポンスヘッダー取得方法を使用しない。

以下の直接参照は禁止する。

    $GLOBALS['http_response_header']

HTTPレスポンスヘッダーが必要な場合は、PHP 8.5で利用可能な適切な方法を使用する。

---

### 53. データ整合性

複数のJSONファイルを更新する処理では、途中失敗による不整合を可能な限り防止する。

特に以下を考慮する。

- 回答保存とtoken使用済み更新
- メール送信結果と送信ログ
- アンケート削除と関連データ削除
- 顧客同期
- ID生成

同時アクセスによるID重複やJSON破損を防止する。

### 54. 入力サイズ制限

悪意のある巨大データを受け取らないようにする。

少なくとも以下には上限を設ける。

- APIリクエストサイズ
- アンケート名
- 説明文
- 質問文
- 選択肢
- 自由記述回答
- メール件名
- メール本文

### 55. 秘密情報の扱い

以下をHTML、JavaScript、通常APIレスポンス、画面表示へ平文で出力しない。

- SMTPパスワード
- kintoneパスワード
- 認証情報
- 回答トークン
- CSRFトークンを必要以上に露出する情報
- その他の秘密情報

サーバーログにもパスワードや認証情報を記録しない。

### 56. 回答結果と未回答の扱い

分岐によって質問へ到達しなかった回答者は、その質問の未回答者に含めない。

質問ごとに実際の回答対象者を算出して集計する。

これにより、分岐のあるアンケートでも回答率・選択割合が実際の回答対象者に対して正しく算出されるようにする。

### 57. 空データの扱い

回答が存在しない場合は、空のグラフだけを表示せず、

    現在、回答データはありません。

等の状態を表示する。

開発環境と本番環境で `index.php` をそのまま移動できる構成とする。

---

### 59. APIと画面の責務

JavaScriptは画面操作・入力補助・表示制御を担当する。

PHPは最終的な業務ルール・権限・入力値・状態・データ整合性を検証する。

以下のような構成は禁止する。

    JavaScriptで検証OK
    ↓
    PHPでは検証せず保存

重要な業務ルールは必ずPHP側でも検証する。

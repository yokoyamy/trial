# アンケートアプリ 要件定義書
# 業務要件・実装要件

============================================================
1. 文書の目的
============================================================

Web上でアンケートの作成・公開・送信・回答・集計を一元管理する。

本書では要件を以下の2つに分ける。

1. 業務要件
   利用者・アンケート運営者から見た機能、操作性、業務上の振る舞い。

2. 実装要件
   業務要件を実現するための技術的条件および実行環境上の制約。

実装方式は、本書で指定した事項を除き、業務要件を満たす範囲で選択できる。

本システムはPOCを目的とするため、本書に明記されていない
認証・認可・セキュリティ機能を独自判断で追加しない。

ただし、本書で明示する秘密情報保護、通信結果の正確な判定、
データ破損防止、入力値検証、出力エスケープ等の実装要件は、
POCであっても省略してはならない。


============================================================
2. 業務要件
============================================================

## 2.1 利用者

利用者は「管理者」と「回答者」に分ける。

管理者：
アンケートの作成、公開、送信、集計等を行う運営者。
POCでは管理者ログインを設けない。

回答者：
個別URLまたは公開URLからアンケートへ回答する利用者。
管理者認証を必要としない。

管理者画面と回答者画面は業務上分離する。

POCでは管理者の認証・ログイン・ログアウト・権限管理は行わない。


## 2.2 アンケート管理

アンケート一覧を管理業務の起点とする。

一覧では以下を確認・操作できる。

- タイトル
- 作成日
- 更新日
- アンケート期間
- ステータス
- 回答数
- 確認・編集
- 集計
- 送信
- 複製
- 削除

タイトルによる部分一致検索ができ、Enterキーで検索する。

ステータスで以下を絞り込める。

- すべて
- 公開中
- 下書き
- 停止
- 終了

以下の条件でソートできる。

- 更新日：新しい順 / 古い順
- 回答数：多い順 / 少ない順
- 開始日：新しい順 / 古い順

初期ソートは更新日の新しい順とする。

一覧上では状態変更を行わない。


## 2.3 アンケート作成・編集

以下を設定できる。

- タイトル
- 説明
- 開始日時
- 終了日時
- 質問番号の採番方式

保存操作は「保存して一覧へ」に統一する。

新規作成は下書きとして保存し、既存アンケートの編集では現在の状態を維持する。

キャンセル時は編集内容を破棄する確認を行う。

状態は以下の4種類とする。

- 下書き
- 公開中
- 停止
- 終了

手動で変更できる状態遷移は以下とする。

- 下書き → 公開中
- 公開中 → 停止
- 停止 → 公開中

公開中のアンケートが終了日時を経過した場合のみ、
自動的に終了とする。

下書き・停止は終了日時を経過しても終了へ変更しない。

終了状態からの状態変更はできない。


## 2.4 グループ・質問

グループは以下を操作できる。

- タイトル編集
- 追加
- 削除
- 並び替え

質問は以下を設定・操作できる。

- 質問文
- 回答形式
- 必須 / 任意
- 選択肢
- 条件分岐
- 削除
- 並び替え
- グループ間移動

回答形式は以下の3種類とする。

- 単一選択
- 複数選択
- 自由記述

「1行テキスト」「複数行テキスト」は独立した回答形式としない。

「質問を追加」は各グループ末尾、
「グループを追加」はグループ一覧末尾のみとする。

質問番号は自動採番し、手動編集できない。

採番方式は以下の2種類とする。

- 全体通番：Q1、Q2、Q3...
- グループ単位：Q1-1、Q1-2、Q2-1...

質問・グループの追加、削除、並び替え、移動、
採番方式変更時には質問番号を再計算する。


## 2.5 条件分岐・プレビュー

単一選択質問では、選択肢ごとに次に表示する質問を指定できる。

プレビューでは以下を確認できる。

- 質問順
- 質問番号
- 選択肢
- 必須設定
- 条件分岐
- PC表示
- スマートフォン表示

プレビューでは実際の回答データを保存しない。

プレビューから実際のメール送信等は行わない。


## 2.6 回答

回答者の基本フローは以下とする。

    アンケート回答
        ↓
    回答確認
        ↓
    回答送信
        ↓
    回答完了

必須項目が未回答の場合は次へ進めない。

条件分岐に応じて表示する質問を変更する。

回答確認画面では回答を修正できる。

回答送信が正常に完了したら回答完了画面を表示し、
回答者フローを終了する。

回答完了後に管理者画面へ遷移しない。

回答者画面には管理者向けメニュー、一覧、設定、
集計、送信等を表示しない。


## 2.7 顧客選択・メール送信

送信画面は対象アンケートを特定した状態で表示する。

同一画面で以下を行える。

- 顧客検索・絞り込み
- 顧客選択
- メール件名・本文編集
- 送信内容確認
- 一括送信
- 再送
- リマインド
- 送信結果確認
- 送信履歴確認

メール本文では以下の変数を利用できる。

- {顧客名}
- {アンケートURL}

送信後は別画面へ遷移せず、同じ画面に結果を表示する。

送信履歴も同じ画面で確認し、専用画面は設けない。

送信処理は、SMTP通信の結果が確定してから
送信結果を保存・表示する。

SMTP通信の結果が不明な場合、
送信成功として記録してはならない。


## 2.8 回答集計・分析

集計画面は対象アンケートを特定した状態で表示する。

以下を表示する。

- 対象アンケート
- 送信対象者数
- 回答数
- 未登録回答数
- 未回答数
- 回答率
- 設問別集計
- 個別回答

CSV・PDFで実データを出力できる。

回答0件の場合は
「現在、回答データはありません」
と表示する。

集計画面内で別アンケートを選択できない。

集計対象のアンケートIDは画面表示時および
データ取得時の双方で確定させる。


## 2.9 kintoneによる顧客管理

kintoneを顧客情報の取得元とする。

設定できる項目：

- サブドメイン
- 顧客管理アプリID
- ログイン名
- Proxy
- SSL証明書検証設定

kintoneパスワードは設定項目として扱うが、
値を保存しない。

サブドメインは、
URL付き・ドメインのみ・サブドメインのみの入力を許容する。

Proxyはhost:port形式とし、未入力時は直接接続する。

POCではSSL証明書検証を無効にできる。

ログイン情報にメールアドレス欄は設けない。

以下を独立した操作とする。

- 設定保存
- 接続テスト
- 項目一覧再取得
- 顧客情報同期

接続テストは実際のkintoneへ接続して行う。

接続テストに際してパスワードを入力する。

項目一覧を取得し、以下の顧客情報へマッピングできる。

項目一覧を取得する際にパスワードを入力する。

- 組織名
- 氏名
- メールアドレス
- 部署名
- 電話番号
- 住所

住所は複数項目を指定できる。

同期した顧客情報を顧客選択・メール送信で利用する。

同期する際にパスワードを入力する。

kintoneパスワードは、接続テスト、項目取得、
顧客同期等の処理に必要な場合にのみ使用する。

ブラウザから送信されたパスワードは、
当該処理に必要な範囲でのみサーバー側へ渡し、
画面表示、URL、JavaScript、ログ、エラーメッセージ等へ
再出力しない。


## 2.10 SMTPメール送信

SMTPサーバを利用してメールを送信する。

設定できる項目：

- SMTPサーバ
- SMTPポート
- 暗号化方式（SSL / TLS / なし）
- SMTP認証
- SMTPユーザー名
- 送信元メールアドレス
- 送信元名
- 返信先メールアドレス

SMTPパスワードを使用する場合は、
入力値を保存しない。

接続状態は以下とする。

- 未設定
- 接続確認済み
- 接続できません

以下を独立した操作とする。

- 設定保存
- 接続テスト
- テストメール送信

接続テストでは認証まで確認する。

接続テストに際してパスワードを入力する。

テストメールは実際のSMTPサーバへ送信する。

テストメールを送信する際にパスワードを入力する。

SMTP認証情報は、当該処理に必要な範囲でのみ使用し、
画面、URL、JavaScript、ログ、エラー表示等へ再出力しない。


## 2.11 画面構成

管理者：

- アンケート一覧
- アンケート作成・編集
- プレビュー
- 顧客選択・メール送信
- 回答集計・分析
- kintone設定
- メールサーバ設定

回答者：

- アンケート回答
- 回答確認
- 回答完了

送信履歴専用画面は設けない。


## 2.12 UI・レスポンシブ

確定済みモックのUI・デザインを維持する。

管理者画面はPCを主対象とし、タブレット・スマートフォンにも対応する。

管理者一覧は横スクロール可能とする。

回答者画面はスマートフォンを最優先とし、
入力欄・選択肢・次へ・戻るを操作しやすくする。

基本色、フォント、余白、境界線、角丸、シャドウ等は
現行モックを基準とし、画面ごとに独自デザインを追加しない。


============================================================
3. 実装要件
============================================================

## 3.1 アプリケーション構成

Apache + PHPで動作する。

単一のindex.phpをエントリーポイントとし、
PHP・HTML・CSS・JavaScriptを1ファイルに含める。

画面は物理パスで分割せず、screenパラメータで切り替える。

例：
    index.php?screen=list
    index.php?screen=edit&id=survey-001
    index.php?screen=preview&id=survey-001
    index.php?screen=send&id=survey-001
    index.php?screen=analytics&id=survey-001
    index.php?screen=kintone
    index.php?screen=mail
    index.php?screen=answer&id=survey-001
    index.php?screen=confirm&id=survey-001
    index.php?screen=complete&id=survey-001

集計・送信は対象アンケートIDを必須とする。

POCでは、上記のscreenパラメータによる単一エントリーポイント構成を維持し、
認証処理による画面分岐を追加しない。


## 3.2 実行環境

以下を前提とする。

- Apache 2.4
- PHP 8.5
- データベースなし
- PHP cURLなし

Apache Rewriteによる画面分割を前提としない。

PHP mail()は使用しない。

外部HTTP通信は、PHP cURLが使用できない環境を前提とし、
PHP標準機能で実装する。

外部通信の実装方式は、HTTPステータス、
レスポンス本文、通信エラー、タイムアウトを取得できるものとする。


## 3.3 データ保存

データベースを使用せず、必要なデータをサーバー側ファイルとして永続化する。

対象には以下を含む。

- アンケート
- グループ
- 質問
- 回答
- 顧客
- 送信履歴
- 各種設定

localStorageのみを主要な永続保存先として使用しない。

保存データはWebブラウザから直接取得できないようにする。

同時更新によるデータ破損を防止する。

ファイル保存処理では、
書き込み途中のデータが正式データとして参照されないようにする。

保存失敗時は処理成功として扱わない。

データ保存の完了結果を確認してから、
成功メッセージ表示または画面遷移を行う。


## 3.4 入力検証・出力

ユーザー入力はサーバー側でも検証する。

必須、文字数、形式、数値範囲、日時、メールアドレス、
URL、ID、外部サービス設定値等を適切に検証する。

JavaScriptの入力チェックだけに依存しない。

HTMLへ出力する値は適切にエスケープする。

入力検証は業務データの整合性確保を目的とするものであり、
POCで要求していない認証・認可・CSRF対策を追加することを意味しない。

パスワード等の秘密情報は、
通常の表示用入力値として再利用しない。

秘密情報をエラー本文、デバッグ情報、
HTML属性、JavaScript変数等へ含めない。


## 3.5 セッション

PHPセッションは回答途中データ等の一時的な状態保持に使用する。

GETからPOSTへ状態を引き継ぐ場合は同一セッションを維持する。

通常のGETアクセスだけを理由としてセッションIDを再生成しない。

セッションCookieには以下を設定する。

- HttpOnly
- SameSite=Lax以上
- HTTPS環境ではSecure

セッションIDをURL、HTML、ログへ出力しない。

セッションは回答途中状態等の一時データ保持のために使用するものであり、
認証・認可・CSRF対策のための仕組みとして扱わない。

POCではCSRF対策を実装しない。

CSRFトークンの生成、保存、フォームへの埋め込み、
POST時のトークン検証、CSRFエラー画面等は実装しない。

フォームPOST処理にCSRFトークンを必須条件として追加してはならない。

「セッションの有効期限が切れたか、不正なリクエストです。」
等のCSRF検証を前提とした400エラー処理を設けない。

将来CSRF対策が必要となった場合は、
本要件を変更したうえで別途実装する。


## 3.6 外部通信

kintoneおよびSMTP通信には接続・読み取りタイムアウトを設定する。

外部通信結果はHTTPステータスだけでなく、
レスポンス本文および通信エラーも確認して判定する。

少なくとも以下を区別できる構造とする。

- 正常応答
- 認証エラー
- 設定・入力エラー
- API / SMTPエラー
- HTTPエラー
- リダイレクト
- 接続エラー
- タイムアウト
- レスポンス取得不能

通信結果不明を成功として扱わない。

外部サービスからHTTP 300番台のレスポンスを受信した場合、
明示的に成功と判定できる仕様がない限り成功扱いしない。

特に302および303は成功扱いしない。

外部サービス通信処理は、
HTTPレスポンスを受信して結果を確定する責務を持つ。

外部サービス通信処理から画面遷移を直接実行しない。


## 3.7 POST処理と画面遷移

フォームPOST処理、外部サービス通信、画面遷移を分離する。

基本処理：

    POST受信
      ↓
    入力値検証
      ↓
    業務処理・保存・外部通信
      ↓
    処理結果確定
      ↓
    結果表示または画面遷移

POCではCSRF検証をこの処理フローへ含めない。

外部サービス通信処理からheader("Location: ...")等を実行しない。

外部サービスから302 / 303が返された場合は成功扱いしない。

通信結果を取得できない場合も成功扱いしない。

アプリケーション自身がリダイレクトする場合も、
業務処理および保存結果を確定してから行う。

アプリケーション自身の303リダイレクトは、
POST後の再送防止およびGET画面への遷移を目的とする
PRG（Post/Redirect/Get）としてのみ使用できる。

アプリケーション自身が303を返す場合は、
リダイレクト前に以下を完了させる。

- 入力値検証
- 業務処理
- 外部通信
- 外部通信結果判定
- 必要なデータ保存
- 成否結果の確定
- 必要な画面表示用状態の保存

303自体を外部サービスの成功レスポンスとして扱わない。

外部サービスから受信した302 / 303と、
アプリケーション自身が発行する303を混同しない。

ユーザー入力をそのままリダイレクト先に使用しない。

リダイレクト先はアプリケーション内で定義された
許可済みの画面およびパラメータだけを使用する。

外部通信結果が未確定の状態で303を返してはならない。


## 3.8 kintone API

kintone REST APIは公式仕様に従って実装する。

認証はログイン名・パスワードを使用し、
サーバー側でX-Cybozu-Authorizationを生成する。

APIトークン認証は使用しない。

主要API：

    接続テスト
    /k/v1/app.json?id=nnn

    項目取得
    /k/v1/app/form/fields.json?app=nnn

    顧客同期
    /k/v1/records.json?app=nnn

API通信処理は共通化し、
接続処理と画面処理を分離する。

kintoneのHTTPステータスだけでなく、
エラーコード・エラーメッセージを取得して処理する。

302 / 303は成功として扱わない。

通信結果を取得できない場合は成功として扱わない。

X-Cybozu-Authorizationおよびkintoneパスワードを
ブラウザ、URL、ログへ出力しない。

X-Cybozu-Authorizationはブラウザへ返却する必要がない。

kintoneパスワードはHTMLのvalue属性、
JavaScript変数、data属性、hidden input等へ
保存済みの値を出力しない。

接続テスト、項目取得、顧客同期等でパスワードが必要な場合は、
POSTされた入力値またはサーバー側で保護された保存値を
サーバー側処理にのみ使用する。

kintone APIへのリクエストが失敗した場合、
APIの失敗をアプリケーションの成功として保存・表示しない。

kintoneから返却されたエラー情報は、
秘密情報を除外したうえで利用者に理解可能な内容へ変換する。


## 3.9 SMTP

PHP mail()は使用せず、SMTP接続によって送信する。

接続テストでは認証まで確認する。

テストメールおよび実メール送信は実際のSMTPサーバへ接続する。

SMTP認証情報をブラウザ、URL、ログへ出力しない。

SMTPパスワードはHTML、JavaScript、URLへ出力しない。

SMTP通信が成功したことを確認してから、
テストメールまたは実メールの成功結果を確定する。

SMTP接続、認証、送信のいずれかが失敗した場合は、
送信成功として記録しない。

通信結果が取得できない場合は、
送信成功として扱わない。

SMTP通信処理から直接画面リダイレクトを行わない。

SMTP通信処理は結果を呼び出し元へ返し、
画面処理側が結果に応じて表示または画面遷移を行う。


## 3.10 秘密情報

秘密情報には、kintoneパスワード、
SMTPパスワード等の外部サービス認証情報を含む。

秘密情報の保護方法は、
「アプリケーションが後から元の値を必要とするか」
によって区別する。

アプリケーション側で元の値を取得する必要がないパスワードは、
PHPのpassword_hash() / password_verify()を使用する。

一方、kintoneパスワード、SMTPパスワード等のように
外部サービスへの接続時に元の値が必要となる秘密情報は、
password_hash()による一方向ハッシュ保存を使用しない。

これらの秘密情報は、
サーバー側で復号可能な認証付き暗号化方式により保護する。

秘密情報の保存について以下を必須とする。

- 平文のままファイルへ保存しない
- URLへ保存しない
- Cookieへ保存しない
- localStorageへ保存しない
- sessionStorageへ保存しない
- HTMLへ保存しない
- JavaScriptへ保存しない
- ログへ保存しない
- エラーメッセージへ保存しない
- デバッグ出力へ保存しない

暗号化には認証付き暗号を使用し、
改ざんされた暗号文を正常な秘密情報として復号しない。

暗号化にはAES-256-GCM等の認証付き暗号方式を使用できる。

暗号化に使用する秘密鍵は、
ソースコード、index.phpのパス、PHPバージョン、
固定文字列等から決定論的に生成してはならない。

特に以下のような方式は禁止する。

    hash('sha256', __FILE__ . '|' . PHP_VERSION, true)

暗号鍵はアプリケーションデータとは分離して管理し、
サーバー環境変数等のサーバー側設定から取得する。

暗号鍵そのものをindex.phpへハードコードしてはならない。

暗号鍵が設定されていない場合は、
秘密情報を平文保存へフォールバックしてはならない。

暗号鍵が利用できない場合は処理を失敗として扱い、
秘密情報を保存しない。

暗号化データには、
復号に必要なIV、認証タグ、暗号文等を安全に格納する。

暗号化データの保存形式は、
将来の仕様変更や復号失敗を判別できる構造とする。

復号に失敗した場合は、
保存データを正常なパスワードとして扱わない。

暗号化・復号処理は共通関数化し、
各画面で独自の暗号化方式を実装しない。

パスワード入力欄はtype="password"を使用する。

保存済みパスワードをinputのvalue属性へ設定しない。

保存済みパスワードをhidden inputへ設定しない。

保存済みパスワードをJavaScriptへ渡さない。

ブラウザからサーバーへパスワードをPOSTすること自体は、
HTTPS通信下であればネットワーク上の平文通信を意味しない。

ブラウザの開発者ツールのNetwork Payloadに、
そのリクエストで入力したパスワードが表示されることは、
ブラウザが送信したPOSTデータを表示しているため、
それだけを理由としてサーバー側の平文保存と判定しない。

ただし、本番利用を想定する場合はHTTPSを使用し、
HTTPによる秘密情報送信を前提としない。

POSTされたパスワードは、
対象処理に必要な範囲でのみメモリ上で使用する。

処理完了後に不要となった秘密情報を、
画面表示用データや永続データへコピーしない。

秘密情報を含むPOSTの再表示を行わない。

バリデーションエラー時にも、
パスワード値をフォームへ再設定しない。

エラー表示では、
「認証情報が正しくありません」等の安全なメッセージを使用し、
パスワードそのものを表示しない。

外部サービスの認証情報を含む設定を画面表示する場合は、
パスワード等の秘密値をマスク表示または未入力状態とする。

「保存済み」であることを示す場合も、
元の秘密値をHTMLへ出力しない。

秘密情報を含むリクエストのURL化を行わない。


## 3.13 エラー処理

入力エラー、設定エラー、データエラー、セッションエラー、
通信エラー、認証エラー、タイムアウト、外部サービスエラー、
システムエラー等を適切に処理する。

失敗時はユーザーへ処理結果を通知し、
可能な範囲で原因と対処方法を示す。

内部情報や秘密情報を画面に表示しない。

白画面や「結果不明」のまま処理を終了しない。

POCで実装していない認証・CSRF等を原因とするエラーを
実装済み機能として扱わない。

例外発生時は、エラー表示処理自身が追加の例外を発生させない。

外部サービス通信の例外が発生した場合、
通信成功として処理を継続しない。

タイムアウト、接続失敗、レスポンス取得不能等の場合は、
通信結果不明として成功扱いしない。

HTTP 300～399の外部サービスレスポンスは、
明示的に仕様上成功と定義されていない限り成功扱いしない。

特にHTTP 302 / 303を外部サービスの成功レスポンスとして扱わない。

アプリケーション自身が返すHTTP 303は、
業務処理・保存・外部通信結果が確定した後の
画面遷移としてのみ使用する。

エラー時にアプリケーション自身が303を返す場合も、
エラー結果を確定してからリダイレクトする。

エラー処理では、
パスワード、認証ヘッダー、セッションID、
暗号鍵、秘密設定値等を出力しない。


## 3.14 実装上の禁止事項

- kintone APIトークン認証

- 管理者認証・認可機能の独自追加
- CSRF対策の実装

- CSRFトークンのセッション保存
- CSRFトークンのフォーム埋め込み
- POST時のCSRFトークン検証
- CSRFトークン不一致による400エラー
- 物理パスによる画面分割
- 回答者から管理者画面への導線
- 一覧上の状態変更
- 終了の手動選択
- 終了状態からの状態変更
- 質問番号の手動編集
- 送信履歴専用画面
- 対象アンケート未指定の集計・送信
- 集計・送信画面内でのアンケート選択
- 接続テストと同期処理の一体化
- localStorageのみへの主要データ保存
- 秘密情報のURL保存
- セッションIDのURL・ログ出力
- 外部サービス通信のモック化
- 外部サービスからの302 / 303の成功扱い
- 外部サービス通信結果を確認しない画面遷移
- 外部通信処理からの直接リダイレクト
- 処理結果確定前の302 / 303
- 通信結果不明の成功扱い
- HTTP/HTTPS判定による無限リダイレクト
- ユーザー入力による任意リダイレクト
- 回答完了後の管理者画面への遷移
- 秘密情報の平文保存
- 秘密情報のHTMLへの出力
- 秘密情報のJavaScriptへの出力
- 秘密情報のCookieへの保存
- 秘密情報のlocalStorageへの保存
- 秘密情報のsessionStorageへの保存
- 秘密情報のログ出力
- 保存済みパスワードのinput valueへの再設定
- 保存済みパスワードのhidden inputへの設定
- 保存済みパスワードのJavaScript変数への設定
- 暗号鍵のindex.phpへのハードコード
- 暗号鍵を__FILE__、PHP_VERSION等から生成する方式
- 暗号鍵未設定時の平文保存へのフォールバック
- password_hash()で外部サービス用パスワードを保存し、
  後から元の値を取得できなくする実装
- 外部通信処理からの画面遷移
- 外部通信結果確定前の成功表示
- 通信結果不明を成功として保存する実装

4. 基本画面遷移
============================================================

管理者：

    アンケート一覧
       ├─ 新規作成 → 作成・編集
       ├─ 確認・編集 → 作成・編集
       ├─ プレビュー → プレビュー
       ├─ 集計 → 回答集計・分析
       ├─ 送信 → 顧客選択・メール送信
       ├─ 複製 → 下書きとして一覧
       └─ 削除 → 確認 → 削除

    一覧
       ├─ kintone設定
       └─ メール設定

回答者：

    個別URL / 公開URL
          ↓
    アンケート回答
          ↓
    回答確認
          ↓
    回答送信
          ↓
    回答完了
          ↓
    回答者フロー終了

POSTを伴う管理者操作では、
必要な業務処理・外部通信・保存結果を確定した後に
必要に応じて303でGET画面へ遷移する。

外部サービスから返された302 / 303は、
この画面遷移とは別の通信結果として処理する。

外部サービスの302 / 303を、
画面遷移用の303として流用してはならない。

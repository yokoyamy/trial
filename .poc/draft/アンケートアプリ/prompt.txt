# アンケートアプリ 要件定義書
# 業務要件・実装要件

============================================================
1. 文書の目的
============================================================

Web上でアンケートの作成・公開・送信・回答・集計を一元管理する。

本書では要件を以下の2つに分ける。

1. 業務要件
   利用者・アンケート運営者から見た機能、操作性、業務上の振る舞い。

2. 実装要件
   業務要件を実現するための技術的条件および実行環境上の制約。

実装方式は、本書で指定した事項を除き、業務要件を満たす範囲で選択できる。

本システムはPOCを目的とするため、本書に明記されていない
認証・認可・セキュリティ機能を独自判断で追加しない。


============================================================
2. 業務要件
============================================================

## 2.1 利用者

利用者は「管理者」と「回答者」に分ける。

管理者：
アンケートの作成、公開、送信、集計等を行う運営者。
POCでは管理者ログインを設けない。

回答者：
個別URLまたは公開URLからアンケートへ回答する利用者。
管理者認証を必要としない。

管理者画面と回答者画面は業務上分離する。

POCでは管理者の認証・ログイン・ログアウト・権限管理は行わない。


## 2.2 アンケート管理

アンケート一覧を管理業務の起点とする。

一覧では以下を確認・操作できる。

- タイトル
- 作成日
- 更新日
- アンケート期間
- ステータス
- 回答数
- 確認・編集
- 集計
- 送信
- 複製
- 削除

タイトルによる部分一致検索ができ、Enterキーで検索する。

ステータスで以下を絞り込める。

- すべて
- 公開中
- 下書き
- 停止
- 終了

以下の条件でソートできる。

- 更新日：新しい順 / 古い順
- 回答数：多い順 / 少ない順
- 開始日：新しい順 / 古い順

初期ソートは更新日の新しい順とする。

一覧上では状態変更を行わない。


## 2.3 アンケート作成・編集

以下を設定できる。

- タイトル
- 説明
- 開始日時
- 終了日時
- 質問番号の採番方式

保存操作は「保存して一覧へ」に統一する。

新規作成は下書きとして保存し、既存アンケートの編集では現在の状態を維持する。

キャンセル時は編集内容を破棄する確認を行う。

状態は以下の4種類とする。

- 下書き
- 公開中
- 停止
- 終了

手動で変更できる状態遷移は以下とする。

- 下書き → 公開中
- 公開中 → 停止
- 停止 → 公開中

公開中のアンケートが終了日時を経過した場合のみ、自動的に終了とする。

下書き・停止は終了日時を経過しても終了へ変更しない。

終了状態からの状態変更はできない。


## 2.4 グループ・質問

グループは以下を操作できる。

- タイトル編集
- 追加
- 削除
- 並び替え

質問は以下を設定・操作できる。

- 質問文
- 回答形式
- 必須 / 任意
- 選択肢
- 条件分岐
- 削除
- 並び替え
- グループ間移動

回答形式は以下の3種類とする。

- 単一選択
- 複数選択
- 自由記述

「1行テキスト」「複数行テキスト」は独立した回答形式としない。

「質問を追加」は各グループ末尾、
「グループを追加」はグループ一覧末尾のみとする。

質問番号は自動採番し、手動編集できない。

採番方式は以下の2種類とする。

- 全体通番：Q1、Q2、Q3...
- グループ単位：Q1-1、Q1-2、Q2-1...

質問・グループの追加、削除、並び替え、移動、
採番方式変更時には質問番号を再計算する。


## 2.5 条件分岐・プレビュー

単一選択質問では、選択肢ごとに次に表示する質問を指定できる。

プレビューでは以下を確認できる。

- 質問順
- 質問番号
- 選択肢
- 必須設定
- 条件分岐
- PC表示
- スマートフォン表示

プレビューから実際のメール送信等は行わない。


## 2.6 回答

回答者の基本フローは以下とする。

    アンケート回答
        ↓
    回答確認
        ↓
    回答送信
        ↓
    回答完了

必須項目が未回答の場合は次へ進めない。

条件分岐に応じて表示する質問を変更する。

回答確認画面では回答を修正できる。

回答送信が正常に完了したら回答完了画面を表示し、
回答者フローを終了する。

回答完了後に管理者画面へ遷移しない。

回答者画面には管理者向けメニュー、一覧、設定、
集計、送信等を表示しない。


## 2.7 顧客選択・メール送信

送信画面は対象アンケートを特定した状態で表示する。

同一画面で以下を行える。

- 顧客検索・絞り込み
- 顧客選択
- メール件名・本文編集
- 送信内容確認
- 一括送信
- 再送
- リマインド
- 送信結果確認
- 送信履歴確認

メール本文では以下の変数を利用できる。

- {顧客名}
- {アンケートURL}

送信後は別画面へ遷移せず、同じ画面に結果を表示する。

送信履歴も同じ画面で確認し、専用画面は設けない。


## 2.8 回答集計・分析

集計画面は対象アンケートを特定した状態で表示する。

以下を表示する。

- 対象アンケート
- 送信対象者数
- 回答数
- 未登録回答数
- 未回答数
- 回答率
- 設問別集計
- 個別回答

CSV・PDFで実データを出力できる。

回答0件の場合は
「現在、回答データはありません」
と表示する。

集計画面内で別アンケートを選択できない。


## 2.9 kintoneによる顧客管理

kintoneを顧客情報の取得元とする。

設定できる項目：

- サブドメイン
- 顧客管理アプリID
- ログイン名
- パスワード
- Proxy
- SSL証明書検証設定

サブドメインは、
URL付き・ドメインのみ・サブドメインのみの入力を許容する。

Proxyはhost:port形式とし、未入力時は直接接続する。

POCではSSL証明書検証を無効にできる。

ログイン情報にメールアドレス欄は設けない。

以下を独立した操作とする。

- 設定保存
- 接続テスト
- 項目一覧再取得
- 顧客情報同期

接続テストは実際のkintoneへ接続して行う。

項目一覧を取得し、以下の顧客情報へマッピングできる。

- 組織名
- 氏名
- メールアドレス
- 部署名
- 電話番号
- 住所

住所は複数項目を指定できる。

同期した顧客情報を顧客選択・メール送信で利用する。


## 2.10 SMTPメール送信

SMTPサーバを利用してメールを送信する。

設定できる項目：

- SMTPサーバ
- SMTPポート
- 暗号化方式（SSL / TLS / なし）
- SMTP認証
- SMTPユーザー名
- SMTPパスワード
- 送信元メールアドレス
- 送信元名
- 返信先メールアドレス

接続状態は以下とする。

- 未設定
- 接続確認済み
- 接続できません

以下を独立した操作とする。

- 設定保存
- 接続テスト
- テストメール送信

接続テストでは認証まで確認する。

テストメールは実際のSMTPサーバへ送信する。


## 2.11 画面構成

管理者：

- アンケート一覧
- アンケート作成・編集
- プレビュー
- 顧客選択・メール送信
- 回答集計・分析
- kintone設定
- メールサーバ設定

回答者：

- アンケート回答
- 回答確認
- 回答完了

送信履歴専用画面は設けない。


## 2.12 UI・レスポンシブ

確定済みモックのUI・デザインを維持する。

管理者画面はPCを主対象とし、タブレット・スマートフォンにも対応する。

管理者一覧は横スクロール可能とする。

回答者画面はスマートフォンを最優先とし、
入力欄・選択肢・次へ・戻るを操作しやすくする。

基本色、フォント、余白、境界線、角丸、シャドウ等は
現行モックを基準とし、画面ごとに独自デザインを追加しない。


============================================================
3. 実装要件
============================================================

## 3.1 アプリケーション構成

Apache + PHPで動作する。

単一のindex.phpをエントリーポイントとし、
PHP・HTML・CSS・JavaScriptを1ファイルに含める。

画面は物理パスで分割せず、screenパラメータで切り替える。

例：

    index.php?screen=list
    index.php?screen=edit&id=survey-001
    index.php?screen=preview&id=survey-001
    index.php?screen=send&id=survey-001
    index.php?screen=analytics&id=survey-001
    index.php?screen=kintone
    index.php?screen=mail
    index.php?screen=answer&id=survey-001
    index.php?screen=confirm&id=survey-001
    index.php?screen=complete&id=survey-001

集計・送信は対象アンケートIDを必須とする。

POCでは、上記のscreenパラメータによる単一エントリーポイント構成を維持し、
認証処理による画面分岐を追加しない。


## 3.2 実行環境

以下を前提とする。

- Apache 2.4
- PHP 8.5
- データベースなし
- PHP cURLなし

Apache Rewriteによる画面分割を前提としない。

PHP mail()は使用しない。


## 3.3 データ保存

データベースを使用せず、必要なデータをサーバー側ファイルとして永続化する。

対象には以下を含む。

- アンケート
- グループ
- 質問
- 回答
- 顧客
- 送信履歴
- 各種設定

localStorageのみを主要な永続保存先として使用しない。

保存データはWebブラウザから直接取得できないようにする。

同時更新によるデータ破損を防止する。


## 3.4 入力検証・出力

ユーザー入力はサーバー側でも検証する。

必須、文字数、形式、数値範囲、日時、メールアドレス、
URL、ID、外部サービス設定値等を適切に検証する。

JavaScriptの入力チェックだけに依存しない。

HTMLへ出力する値は適切にエスケープする。

入力検証は業務データの整合性確保を目的とするものであり、
POCで要求していない認証・認可・CSRF対策を追加することを意味しない。


## 3.5 セッション

PHPセッションは回答途中データ等の一時的な状態保持に使用する。

GETからPOSTへ状態を引き継ぐ場合は同一セッションを維持する。

通常のGETアクセスだけを理由としてセッションIDを再生成しない。

セッションCookieには以下を設定する。

- HttpOnly
- SameSite=Lax以上
- HTTPS環境ではSecure

セッションIDをURL、HTML、ログへ出力しない。

セッションは回答途中状態等の一時データ保持のために使用するものであり、
認証・認可・CSRF対策のための仕組みとして扱わない。

POCではCSRF対策を実装しない。

CSRFトークンの生成、保存、フォームへの埋め込み、
POST時のトークン検証、CSRFエラー画面等は実装しない。

フォームPOST処理にCSRFトークンを必須条件として追加してはならない。

「セッションの有効期限が切れたか、不正なリクエストです。」
等のCSRF検証を前提とした400エラー処理を設けない。

将来CSRF対策が必要となった場合は、
本要件を変更したうえで別途実装する。


## 3.6 外部通信

kintoneおよびSMTP通信には接続・読み取りタイムアウトを設定する。

外部通信結果はHTTPステータスだけでなく、
レスポンス本文および通信エラーも確認して判定する。

少なくとも以下を区別できる構造とする。

- 正常応答
- 認証エラー
- 設定・入力エラー
- API / SMTPエラー
- HTTPエラー
- リダイレクト
- 接続エラー
- タイムアウト
- レスポンス取得不能

通信結果不明を成功として扱わない。


## 3.7 POST処理と画面遷移

フォームPOST処理、外部サービス通信、画面遷移を分離する。

基本処理：

    POST受信
      ↓
    入力値検証
      ↓
    業務処理・保存・外部通信
      ↓
    処理結果確定
      ↓
    結果表示または画面遷移

POCではCSRF検証をこの処理フローへ含めない。

外部サービス通信処理からheader("Location: ...")等を実行しない。

外部サービスから302 / 303が返された場合は成功扱いしない。

通信結果を取得できない場合も成功扱いしない。

アプリケーション自身がリダイレクトする場合も、
業務処理および保存結果を確定してから行う。

ユーザー入力をそのままリダイレクト先に使用しない。


## 3.8 kintone API

kintone REST APIは公式仕様に従って実装する。

認証はログイン名・パスワードを使用し、
サーバー側でX-Cybozu-Authorizationを生成する。

APIトークン認証は使用しない。

主要API：

    接続テスト
    /k/v1/app.json?id=nnn

    項目取得
    /k/v1/app/form/fields.json?app=nnn

    顧客同期
    /k/v1/records.json?app=nnn

API通信処理は共通化し、
接続処理と画面処理を分離する。

kintoneのHTTPステータスだけでなく、
エラーコード・エラーメッセージを取得して処理する。

302 / 303は成功として扱わない。

X-Cybozu-Authorizationおよびkintoneパスワードを
ブラウザ、URL、ログへ出力しない。


## 3.9 SMTP

PHP mail()は使用せず、SMTP接続によって送信する。

接続テストでは認証まで確認する。

テストメールおよび実メール送信は実際のSMTPサーバへ接続する。

SMTP認証情報をブラウザ、URL、ログへ出力しない。


## 3.10 秘密情報

アプリケーション側で元の値を取得する必要がないパスワードは、
PHPのpassword_hash() / password_verify()を使用する。

外部サービス接続時に元の値が必要なパスワード、
APIキー、トークン等はSodiumで可逆暗号化して保存する。

暗号化には、

    sodium_crypto_secretbox()

を使用する。

Base64、URLエンコード、独自難読化、MD5、SHA-1、
単純なSHA-256等を暗号化・パスワード保存の代用にしない。


## 3.11 暗号鍵

暗号鍵は暗号化データと分離して管理する。

アンケートアプリの鍵は、

    .secrets/アンケートアプリ/secret.key

に保存する。

鍵は32バイトとし、Web公開領域、Git、index.php、
HTML、JavaScript、URL、通常ログへ出力しない。

鍵ファイルには秘密鍵以外の情報を保存しない。

鍵が存在しない、読み込めない、形式が不正等の場合は
設定エラーとして扱う。

固定値や自動生成した鍵へのフォールバックは行わない。

既存の暗号化データを引き継ぐ場合は同一の鍵を使用し、
鍵を再生成して既存データを復号しない。

暗号文は方式を識別できる形式で保存する。

    ENC:v1:<nonce>:<ciphertext>


## 3.12 秘密情報の表示・ログ

kintoneパスワード、SMTPパスワード、
APIキー、トークン等を平文表示しない。

設定画面では「設定済み」等の状態のみ表示する。

秘密情報をHTML、JavaScript、URL、通常ログ、
エラーメッセージへ出力しない。

復号は外部サービス通信等で実際に必要な場合のみ行う。


## 3.13 エラー処理

入力エラー、設定エラー、データエラー、セッションエラー、
通信エラー、認証エラー、タイムアウト、外部サービスエラー、
システムエラー等を適切に処理する。

失敗時はユーザーへ処理結果を通知し、
可能な範囲で原因と対処方法を示す。

内部情報や秘密情報を画面に表示しない。

白画面や「結果不明」のまま処理を終了しない。

POCで実装していない認証・CSRF等を原因とするエラーを
実装済み機能として扱わない。

例外発生時は、エラー表示処理自身が追加の例外を発生させない。


## 3.14 実装上の禁止事項

以下を禁止する。

- DB依存
- PHP cURL
- PHP mail()
- kintone APIトークン認証
- 管理者ログイン・ログアウト
- 管理者認証によるリダイレクト
- 管理者認証・認可機能の独自追加
- CSRF対策の実装
- CSRFトークンの生成
- CSRFトークンのセッション保存
- CSRFトークンのフォーム埋め込み
- POST時のCSRFトークン検証
- CSRFトークン不一致による400エラー
- 物理パスによる画面分割
- 回答者から管理者画面への導線
- 一覧上の状態変更
- 終了の手動選択
- 終了状態からの状態変更
- 質問番号の手動編集
- 送信履歴専用画面
- 対象アンケート未指定の集計・送信
- 集計・送信画面内でのアンケート選択
- 接続テストと同期処理の一体化
- localStorageのみへの主要データ保存
- 秘密情報のURL保存
- セッションIDのURL・ログ出力
- 外部サービス通信のモック化
- 外部サービスからの302 / 303の成功扱い
- 外部サービス通信結果を確認しない画面遷移
- 外部通信処理からの直接リダイレクト
- 処理結果確定前の302 / 303
- 通信結果不明の成功扱い
- HTTP/HTTPS判定による無限リダイレクト
- ユーザー入力による任意リダイレクト
- 回答完了後の管理者画面への遷移
- 秘密鍵のindex.phpへのハードコード
- 秘密鍵のGit管理
- 秘密情報の平文保存


============================================================
4. 基本画面遷移
============================================================

管理者：

    アンケート一覧
       ├─ 新規作成 → 作成・編集
       ├─ 確認・編集 → 作成・編集
       ├─ プレビュー → プレビュー
       ├─ 集計 → 回答集計・分析
       ├─ 送信 → 顧客選択・メール送信
       ├─ 複製 → 下書きとして一覧
       └─ 削除 → 確認 → 削除

    一覧
       ├─ kintone設定
       └─ メール設定

回答者：

    個別URL / 公開URL
          ↓
    アンケート回答
          ↓
    回答確認
          ↓
    回答送信
          ↓
    回答完了
          ↓
    回答者フロー終了


============================================================
5. 実装完了条件
============================================================

以下を満たすこと。

- 業務要件に記載された各画面・操作が動作する。
- アンケートの状態遷移が要件どおり動作する。
- 質問・グループの並び替えと自動採番が動作する。
- 条件分岐を含む回答フローが動作する。
- 回答完了後に管理者画面へ遷移しない。
- 対象アンケートを固定した送信・集計が動作する。
- kintoneへ実接続して接続テスト・項目取得・顧客同期ができる。
- SMTPへ実接続して接続テスト・テストメール送信ができる。
- 外部サービスの302 / 303を成功扱いしない。
- 通信結果不明を成功扱いしない。
- 外部通信処理と画面遷移処理が分離されている。
- エラー時に白画面にならない。
- 秘密情報が平文・URL・HTML・JavaScript・ログへ漏えいしない。
- 指定された暗号化方式・秘密鍵管理方式を維持する。
- 現行モックのUI・デザイン・レスポンシブ仕様を維持する。
- POCではCSRF対策を実装していない。
- POST処理がCSRFトークンの存在を前提とせず動作する。
- 管理者ログイン等の未要求の認証・認可機能が追加されていない。
- セッションは回答途中データ等の一時状態保持に限定して使用する。
- エラー処理自身の例外によって白画面にならない。

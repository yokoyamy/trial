# アンケートアプリ 要件定義書
# 業務要件・共通要件・実装要件・実行環境要件 分離版

============================================================
1. 文書の目的
============================================================

本書は、Web上でアンケートの作成・公開・送信・回答・集計を
一元管理するアンケートアプリケーションの要件を定義する。

本書では、以下を明確に分離して記載する。

1. 業務要件
   アプリケーションが利用者に提供すべき業務上の機能・振る舞い。

2. 業務ルール
   データ、状態、操作、画面遷移等について守るべき業務上の規則。

3. 共通・セキュリティ要件
   業務機能を安全かつ一貫して提供するための共通要件。

4. 実装要件
   業務要件および共通要件を実現するために
   アプリケーション実装で守るべき条件。

5. 実行環境要件
   アプリケーションを動作させるサーバー・Webサーバー・PHP等の
   環境上の制約。

6. 外部サービス固有要件
   kintone、SMTP等、外部サービスとの連携に固有の要件。

実装方式については、本書で明示的に指定した事項を除き、
業務要件を満たす範囲で適切な方式を選択できるものとする。


============================================================
2. 目的・対象
============================================================

Web上でアンケートの作成・公開・送信・回答・集計を
一元管理する。

対象者は「管理者」と「回答者」に分離する。

------------------------------------------------------------
2.1 管理者
------------------------------------------------------------

管理者はアンケートの運用担当者とする。

POC段階のため、管理者ログインを要求しない。



------------------------------------------------------------
2.2 回答者
------------------------------------------------------------

回答者は個別URLまたは公開URLからアンケートへ回答する利用者とする。

回答者は管理者認証を必要としない。

回答者画面は管理者画面から業務上分離する。


============================================================
3. 業務要件
============================================================

## 3.1 アンケート管理

アンケート一覧を管理業務の起点とする。

一覧では以下を確認・操作できる。

- タイトル
- 作成日
- 更新日
- アンケート期間
- ステータス
- 回答数
- 確認・編集
- 集計
- 送信
- 複製
- 削除

検索：

- タイトル部分一致
- Enterキーで検索

絞り込み：

- すべて
- 公開中
- 下書き
- 停止
- 終了

ソート：

- 更新日：新しい順 / 古い順
- 回答数：多い順 / 少ない順
- 開始日：新しい順 / 古い順

初期ソートは「更新日：新しい順」。

一覧上では状態変更を行わない。


## 3.2 アンケート作成・編集

画面上部に以下を配置する。

[キャンセル] [保存して一覧へ] 状態：[状態 ▼]

その下に以下を配置する。

- アンケートタイトル
- アンケート説明
- 開始日時
- 終了日時
- 質問番号の採番方式

保存：

- 保存操作は「保存して一覧へ」のみとする
- 新規作成時は下書きとする
- 既存編集時は現在状態を維持する
- 保存後は一覧へ戻る

キャンセル：

- 編集内容破棄の確認後、前画面へ戻る

状態変更：

- 下書き → 公開中
- 公開中 → 停止
- 停止 → 公開中
- 状態変更時は確認を行う
- 終了は手動選択不可
- 終了状態では状態変更不可


## 3.3 アンケート状態

状態は以下の4種類とする。

- 下書き
- 公開中
- 停止
- 終了

終了は自動状態とする。

公開中かつ終了日時を経過した場合：

    公開中 → 終了

下書きまたは停止で終了日時を経過しても状態を変更しない。

終了状態では状態変更できない。


## 3.4 質問・グループ

グループ：

- タイトル編集
- 追加
- 削除
- ドラッグ＆ドロップによる並び替え

質問：

- 質問文
- 回答形式
- 必須 / 任意
- 選択肢
- 条件分岐
- 削除
- ドラッグ＆ドロップによる並び替え
- グループ間移動

回答形式は以下の3種類だけとする。

- 単一選択
- 複数選択
- 自由記述

「1行テキスト」「複数行テキスト」は個別の回答形式として設けない。

「質問を追加」は各グループ末尾のみ。

「グループを追加」はグループ一覧末尾のみ。

質問番号は自動採番し、手動編集させない。

採番方式：

- アンケート全体で通番：Q1、Q2、Q3...
- グループ毎に採番：Q1-1、Q1-2、Q2-1...

以下の操作時に質問番号を再計算する。

- 質問追加
- 質問削除
- 質問並び替え
- 質問のグループ間移動
- グループ追加
- グループ削除
- グループ並び替え
- 採番方式変更


## 3.5 条件分岐・プレビュー

単一選択質問について、選択肢ごとに
次に表示する質問を指定できる。

プレビューでは以下を確認できる。

- 質問順
- 質問番号
- 選択肢
- 必須設定
- 条件分岐
- PC表示
- スマートフォン表示

プレビューから実際のメール送信等は行わない。


## 3.6 回答者

回答者画面は管理者画面から業務上完全に分離する。

回答フロー：

    アンケート回答
          ↓
       回答確認
          ↓
       回答完了

回答者画面には以下を表示しない。

- 管理者向けメニュー
- アンケート一覧
- 設定
- 集計
- 送信
- その他管理者向け機能

回答形式：

- 単一選択
- 複数選択
- 自由記述

必須項目未回答の場合は次へ進めない。

条件分岐に応じて表示質問を変更する。

回答確認画面では回答を修正できる。

送信確認後、回答完了画面へ進む。


## 3.7 顧客選択・メール送信

送信画面は必ず対象アンケートを特定した状態で表示する。

画面内で以下を行う。

- 顧客検索
- 顧客絞り込み
- 顧客選択
- メール件名・本文編集
- 送信文確認
- 一括送信
- 再送
- リマインド
- 送信結果確認
- 送信履歴確認

メール変数：

- {顧客名}
- {アンケートURL}

送信後は別画面へ遷移せず、
同じ送信画面に結果を表示する。

送信履歴も同じ画面内で表示する。

「送信履歴」専用画面は存在しない。


## 3.8 回答集計・分析

集計画面は必ず対象アンケートを特定した状態で表示する。

表示：

- 対象アンケート
- 送信対象者数
- 回答数
- 未登録回答数
- 未回答数
- 回答率
- 設問別集計
- 個別回答

出力：

- CSV
- PDF

回答0件の場合：

    現在、回答データはありません

と表示する。


## 3.9 外部サービス連携

外部サービスについて、
設定、接続確認、データ取得・同期、送信等の責務を分離する。

共通業務要件：

- POC機能として一部をモックで代替しない
- 接続確認は実際の外部サービスへ接続して行う
- 接続確認とデータ同期を別操作とする
- 外部サービスの認証情報をブラウザへ公開しない
- 外部サービスの認証情報をURLへ含めない
- 通信失敗時は処理結果をユーザーへ通知する


## 3.10 kintone連携

kintoneを顧客情報の取得元として利用する。

設定項目：

- サブドメイン
入力形式は以下のいずれでも良い。
　https:xxxx.cybozu.com
　xxxx.cybozu.com
　xxxx
- 顧客管理アプリID
- ログイン名
- パスワード
- Proxy
 「host:port」形式で入力する
  サーバとポート番号を別々の入力欄にしない
  未入力の場合はProxyを使用せず直接接続する
- SSL証明書検証設定
  有効 / 無効を設定できる
  POC段階では無効とする

ログイン情報にメールアドレス入力欄は設けない。

認証方式：

- ログイン名・パスワードによる認証
- kintone REST APIへの認証にはX-Cybozu-Authorizationを使用する


以下はそれぞれ別の操作ボタンとする。

1. 設定保存
2. 接続テスト
3. 項目一覧を再取得
4. 顧客情報を同期

接続テストは実際のkintoneへ接続して行う。
接続テスト中はスピナー等で処理中を示し他の操作を受け付けない。

接続テスト結果：

- 接続成功
- 接続失敗
　　失敗した場合は次の対処ができるように詳細情報を表示する。

顧客情報の取得対象：

- 組織名
- 氏名
- メールアドレス
- 部署名
- 電話番号
- 住所

住所マッピングは複数選択可能なチェックボックスとする。



## 3.11 メールサーバ

設定：

- SMTPサーバ
- SMTPポート
- 暗号化方式（SSL / TLS / なし）
- SMTP認証
- SMTPユーザー名
- SMTPパスワード
- 送信元メールアドレス
- 送信元名
- 返信先メールアドレス

接続状態：

- 未設定
- 接続確認済み
- 接続できません

テストメール送信を行える。

メール送信は実際のSMTPサーバへ接続して行う。

以下はそれぞれ別の操作ボタンとする。

1. 設定保存
2. 接続テスト
3. テストメール送信

============================================================
4. 業務ルール・全体整合性
============================================================

## 4.1 管理者と回答者の分離

管理者画面：

- アンケート一覧
- 作成・編集
- プレビュー
- 集計
- 顧客選択・メール送信
- kintone設定
- メールサーバ設定

回答者画面：

- アンケート回答
- 回答確認
- 回答完了

回答者から管理者画面への業務上の導線は存在しない。

テスト段階では管理者認証を行わない。


## 4.2 対象アンケートの固定

一覧上の「集計」「送信」は行単位の操作とする。

    一覧
      ↓
    対象アンケートを特定
      ↓
    集計 または 送信
      ↓
    対象アンケートを固定した業務画面

集計画面・送信画面では別アンケートを選択できない。

対象アンケート未特定では両画面を表示しない。


## 4.3 状態整合性

状態は4種類だが、手動状態変更対象は
下書き・公開中・停止のみ。

終了は、

    公開中
    かつ
    終了日時経過

の場合だけ自動設定する。

したがって、

    下書き + 終了日時経過 → 下書き
    停止   + 終了日時経過 → 停止
    公開中 + 終了日時経過 → 終了

とする。

終了状態から他状態への変更は禁止。


## 4.4 送信履歴

送信履歴は業務上必要だが、独立画面とはしない。

送信画面内で、

    顧客選択・送信
    送信履歴

を切り替えて利用する。

送信後も同じ画面に留まる。

============================================================
6. 共通・セキュリティ要件
============================================================

## 6.1 入力値検証

ユーザーから入力された値はサーバー側でも検証する。

以下について適切に検証する。

- 必須項目
- 文字数
- 形式
- 数値範囲
- 日時
- メールアドレス
- URL
- ID
- その他各設定値

画面側JavaScriptによるチェックだけに依存しない。

HTMLへ出力する値は適切にエスケープする。


## 6.2 エラー処理

処理に失敗した場合は、
ユーザーに処理が失敗したことと
可能な範囲で原因を表示する。

以下を区別して扱う。

- 入力エラー
- 設定エラー
- データエラー
- セッションエラー
- 通信エラー
- 認証エラー
- タイムアウト
- 外部サービスエラー
- システムエラー

システム内部のエラー情報や機密情報を
そのまま画面に表示しない。


## 6.3 管理者認証

POC段階なので不要

## 6.4 セッション

### 目的

PHPセッションは、管理者認証のためではなく、
以下の状態保持を必要とする処理に使用できる。

- 回答途中のデータ
- その他、業務フロー上短期間保持する状態

管理者ログインが存在しないことを理由として、
セッションを不要と判断してはならない。

### セッションのライフサイクル

アプリケーションは、
GETからPOSTへ状態を引き継ぐ必要がある場合、
同一利用者のセッションを維持する。

通常のGETアクセスだけを理由として、
セッションIDを再生成してはならない。

セッションID再生成を行う場合は、
認証状態変更等の明確な理由を持つ処理で行う。

### セッションCookie

セッションCookieには、
実行環境およびアプリケーション公開パスに適した
セキュリティ属性を設定する。

最低限、

- HttpOnly
- SameSite=Lax以上を基本とする

を適用する。

HTTPSで提供する場合はSecure属性を使用する。

Cookie Pathは、
アプリケーションの公開範囲に合わせて一貫して設定する。

### セッションID

- URLへ含めない
- HTMLへ出力しない
- ログへ出力しない




## 6.6 リダイレクト制御

テスト段階では管理者認証を行わない。

したがって、認証状態を理由とする
ログイン画面へのリダイレクトは実装しない。

管理者画面：

- 未認証 / 認証済みという概念を設けない
- 管理者画面へのアクセス時にログイン画面へリダイレクトしない

回答者画面：

- 管理者認証を要求しない
- 管理者ログイン画面へリダイレクトしない
- 回答者画面から管理者画面へ自動リダイレクトしない

以下のリダイレクトループを発生させてはならない。

- 管理者画面 → ログイン → 管理者画面
- 未認証 → ログイン → 未認証
- 回答者画面 → ログイン → 回答者画面
- HTTP → HTTPS → HTTP
- POST → 同じPOSTの無限再実行

アプリケーション側でHTTPS強制リダイレクトを必須としない。

HTTPS強制は実行環境側で実施できる。

リダイレクト先URLにユーザー入力をそのまま使用しない。

外部URLへの任意リダイレクト機能を設けない。


## 6.7 データ保存

アンケート、グループ、質問、回答、顧客、
送信履歴、各種設定等の必要なデータは
サーバー側に永続化する。

ブラウザのlocalStorageのみを
主要データ保存先として使用してはならない。

保存データはWebブラウザから直接アクセスできない場所に配置する。

保存処理では同時更新によるデータ破損を防止する。

可能な場合は一時ファイルへ書き込んでから
原子的に保存先へ反映する。

設定情報に含まれるパスワード等は、
可能な限りWeb表示用データと分離する。


## 6.8 外部通信

外部サービスとの通信には、

- 接続タイムアウト
- 読み取りタイムアウト

を設定する。

通信失敗時に無期限に処理を待機してはならない。

外部サービスの認証情報はURLへ含めない。

外部サービスの認証情報や認証ヘッダーを
ブラウザ側JavaScriptへ渡さない。


============================================================
7. 実装要件
============================================================

## 7.1 画面制御

index.phpを単一エントリーポイントとする。

画面は物理パスで分けず、
クエリー文字列で制御する。

例：

index.php?screen=list
index.php?screen=edit&id=survey-001
index.php?screen=preview&id=survey-001
index.php?screen=send&id=survey-001
index.php?screen=analytics&id=survey-001
index.php?screen=kintone
index.php?screen=mail
index.php?screen=answer&id=survey-001
index.php?screen=confirm&id=survey-001
index.php?screen=complete&id=survey-001

送信履歴専用screenは作らない。

集計・送信ではidを必須とし、
対象アンケートを固定する。

管理者画面では、
POC段階のため認証状態によるアクセス制御を行わない。

回答者画面は管理者認証を要求しない。


## 7.2 データ保持

データベースは使用しない。

アンケート、グループ、質問、回答、顧客、
送信履歴、各種設定等の必要なデータを
サーバー側へファイルとして永続化する。


## 7.3 状態自動判定

対象アンケートを読み込む際、
必要に応じて状態を自動判定する。

以下の場合だけ終了へ変更する。

    survey.status === "published"
    かつ
    survey.endAt が現在日時より過去

この場合：

    survey.status = "ended"

draft / stopped は自動終了させない。

endedの場合は状態変更UIを無効化する。


## 7.4 対象アンケート引き継ぎ

一覧から集計・送信へ遷移するとき、
対象アンケートIDをクエリー文字列に含める。

例：

index.php?screen=analytics&id=survey-001
index.php?screen=send&id=survey-001

遷移先ではIDから対象アンケートを取得し、
タイトル等を表示する。

IDが存在しない場合は、
集計・送信画面を表示せず一覧へ戻す。


## 7.5 確認ダイアログ

以下は共通確認ダイアログで実装する。

- 削除
- 複製
- 公開
- 停止
- 再開
- 一括送信
- 再送
- 編集内容破棄
- 回答送信
- グループ削除
- 質問削除

終了への自動遷移には確認ダイアログを表示しない。


## 7.6 ドラッグ＆ドロップ

HTML5 Drag and Drop等を使用して以下を実現する。

- グループ並び替え
- 質問並び替え
- 質問のグループ間移動

変更後に質問番号を再計算する。


## 7.7 出力

CSV：

- 実データをCSVとして出力する。

PDF：

- 実データをPDFとして出力する。

出力失敗時はユーザーにエラーを表示する。


## 7.8 外部サービス接続

kintoneおよびSMTPは実際のサービスへ接続する。



外部サービスとの通信には
適切な接続・読み取りタイムアウトを設定する。

外部サービスの通信エラーが発生した場合、
原因を可能な範囲でユーザーへ通知する。

外部サービスの認証情報等の機密情報を
画面やログに不用意に出力しない。


## 7.9 セッション実装

セッションの具体的なAPIや内部データ構造は
実装者が選択できる。

ただし、以下を満たすこと。

- GETからPOSTへ必要な状態を引き継げる
- 回答途中データを必要に応じて保持できる
- セッションCookieを適切に設定する
- URLへセッションIDを露出させない
- セッションIDをログへ出力しない
- 通常のGETごとにセッションIDを変更しない

セッションが利用できない場合は、
セッションエラーとして扱う。




============================================================
8. 実行環境要件・制約
============================================================

この章は業務要件ではなく、
本アプリケーションを動作させる実行環境上の制約を定義する。

## 8.1 基本環境

- Apache 2.4
- PHP 8.5
- データベースなし
- PHP cURLなし

上記環境で動作すること。

これらは業務要件ではなく、
現行プロジェクトにおける実行環境上の制約である。


## 8.2 Webアクセス

ApacheのRewrite設定を前提としない。

すべてindex.phpを入口とし、
$_GET['screen']等で画面を切り替える。

Apacheの物理パスによる画面分割を行わない。


## 8.3 PHP

PHPは画面生成およびサーバー側処理に使用する。

PHP cURLは使用しない。

外部通信は、
現在のPHP環境で利用可能な標準機能等を使用する。


## 8.4 HTTPS

アプリケーションは、
単純なHTTP/HTTPS判定だけを理由として
無限リダイレクトを発生させてはならない。

HTTPS強制リダイレクトは、
実行環境側で実施するので、
アプリケーション側でHTTPS強制リダイレクトを
必須機能としない。


## 8.5 セッション保存環境

PHPセッションが正常に保存・復元できる
実行環境を構成する。

セッション保存領域について、

- PHPから読み書きできる
- Webブラウザから直接取得できない
- 不要なユーザーからアクセスできない

ことを確認する。



## 8.6 Cookie

実行環境は、
アプリケーションが設定するセッションCookieを
正常に保持・送信できること。

HTTPS環境ではSecure属性を利用する。

HttpOnlyおよびSameSiteについて、
アプリケーションのセキュリティ要件を満たせる環境とする。

アプリケーションをサブディレクトリへ配置する場合、
Cookie Pathと公開URLの関係が破綻しないよう構成する。


## 8.7 ファイルシステム

サーバー側データ保存領域は、
アプリのWeb公開ディレクトリとする。

PHPプロセスが必要なデータを読み書きできる権限を持つ。

同時更新によるファイル破損を防止できる
ファイルシステム構成とする。


============================================================
9. 外部サービス固有要件
============================================================

## 9.1 kintone

kintoneとの認証および通信方式は、
kintone固有の仕様として扱う。

認証方式：

- ログイン名
- パスワード
- X-Cybozu-Authorization

APIトークン認証は使用しない。

X-Cybozu-Authorizationの生成・設定は
サーバー側で行う。

X-Cybozu-Authorizationを
ブラウザ側JavaScriptへ渡さない。

X-Cybozu-Authorizationおよびkintoneパスワードを
ログやエラー画面へ出力しない。



## 9.2 SMTP

PHP mail()は使用しない。

メール送信はSMTP接続によって行う。

SMTPサーバ、ポート、暗号化、
認証情報等は設定値として扱う。

SMTP認証情報をブラウザへ公開しない。

SMTP認証情報をURLやログへ出力しない。

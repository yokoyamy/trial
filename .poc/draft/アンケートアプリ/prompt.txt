# アンケートアプリ 要件定義書
# 業務要件・実装要件

============================================================
【改訂方針】
============================================================

既存の章立て・業務要件・画面構成・実装方針は維持する。

今回の改訂では、kintone接続について、
「公式仕様に従う」という抽象的な指定だけでは実装者ごとの
解釈差が発生するため、接続方式・認証情報・URL・HTTP通信・
エラー判定を再現可能な実装条件として明文化する。

特に、kintone REST APIのパスワード認証と、
HTTP Basic認証を別の認証方式として明確に区別する。

本改訂は、既存機能を削除・簡略化するものではない。
既存の業務要件、UI、画面遷移、データ保存方式、
秘密情報保護、外部通信結果判定等を維持したまま、
kintone接続の実装条件を具体化するものである。


============================================================
2.9 kintoneによる顧客管理
============================================================

kintoneを顧客情報の取得元とする。

設定できる項目：

- サブドメイン
- 顧客管理アプリID
- ログイン名
- Proxy
- SSL証明書検証設定

kintoneパスワードは設定項目として扱うが、
平文の値を永続保存しない。

サブドメインは、
URL付き・ドメインのみ・サブドメインのみの入力を許容する。

Proxyはhost:port形式とし、未入力時は直接接続する。

POCではSSL証明書検証を無効にできる。

ログイン情報にメールアドレス欄は設けない。

以下を独立した操作とする。

- 設定保存
- 接続テスト
- 項目一覧再取得
- 顧客情報同期

接続テストは実際のkintoneへ接続して行う。

接続テストに際してパスワードを入力する。

項目一覧を取得し、以下の顧客情報へマッピングできる。

- 組織名
- 氏名
- メールアドレス
- 部署名
- 電話番号
- 住所

住所は複数項目を指定できる。

同期した顧客情報を一覧として表示する。
この一覧は顧客選択・メール送信でも利用する。

同期する際にパスワードを入力する。

kintoneパスワードは、接続テスト、項目取得、
顧客同期等の処理に必要な場合にのみ使用する。


------------------------------------------------------------
2.9.1 kintone接続情報の正規化
------------------------------------------------------------

kintone接続先は通常のcybozu.com環境を前提とする。

入力されたサブドメインは、API接続時に以下の正規化を行う。

- `https://` または `http://` が入力されている場合は除去する。
- パス、クエリ、フラグメント等は接続先ホストとして使用しない。
- `.cybozu.com` が既に含まれている場合は重複付加しない。
- 最終的なAPI接続先はHTTPSを使用し、
  `https://<正規化されたホスト>/k/v1/...`
  の形式とする。
- kintone APIのパスをユーザー入力から直接生成しない。
- APIパスはアプリケーションで定義した固定値のみを使用する。

顧客管理アプリIDは正の整数として扱う。

アプリIDをURLへ埋め込む場合は、
URLエンコード等を適切に行い、
ユーザー入力を任意のURLやホストとして解釈しない。


------------------------------------------------------------
2.9.2 kintoneパスワード認証方式
------------------------------------------------------------

kintone REST APIの認証方式は、
本POCでは「ログイン名・パスワードによるパスワード認証」
に固定する。

APIトークン認証を代替方式として実装しない。

認証情報は以下の規則で生成する。

    ログイン名 + ":" + パスワード
        ↓
    Base64エンコード
        ↓
    X-Cybozu-Authorization ヘッダーへ設定

実装上は概念的に以下と同じ結果になること。

    base64_encode($username . ':' . $password)

HTTPリクエストには、生成した値を以下の形式で設定する。

    X-Cybozu-Authorization: <Base64化したログイン名:パスワード>

`X-Cybozu-Authorization` の値そのものを
ブラウザ、HTML、JavaScript、URL、Cookie、ログ、
エラー画面等へ出力してはならない。

Base64は暗号化ではないため、
認証情報を保護する方式としてBase64そのものを扱わない。
Base64化はkintone REST APIが要求する通信形式としてのみ使用する。

認証ヘッダーはサーバー側のkintone通信処理内部で生成し、
必要なAPI通信が終了した後は不要な参照を保持しない。


------------------------------------------------------------
2.9.3 kintone認証とHTTP Basic認証の区別
------------------------------------------------------------

`X-Cybozu-Authorization` とHTTP Basic認証の
`Authorization` ヘッダーを同一の認証情報として扱わない。

kintoneのパスワード認証では、

    X-Cybozu-Authorization:
    Base64(ログイン名:パスワード)

を使用する。

HTTP Basic認証を利用している環境では、

    Authorization:
    Basic Base64(Basic認証ユーザー名:Basic認証パスワード)

を別途使用する。

kintoneのログイン名・パスワードを、
HTTP Basic認証の認証情報として自動的に
`Authorization` ヘッダーへ設定してはならない。

逆に、HTTP Basic認証用の認証情報を
`X-Cybozu-Authorization` に設定してはならない。

本POCの設定項目にはHTTP Basic認証用ユーザー名・
パスワードを設けない。

kintone環境側でBasic認証が必要な場合の扱いは、
本POCの既存Proxy・SSL設定とは別の通信条件として扱い、
既存の業務要件を変更せずに対応できる構造とする。

Basic認証情報を推測、流用、ハードコードしてはならない。


------------------------------------------------------------
2.9.4 kintone REST APIの接続先
------------------------------------------------------------

主要APIは以下に固定する。

接続テスト：

    GET /k/v1/app.json?id=<アプリID>

項目取得：

    GET /k/v1/app/form/fields.json?app=<アプリID>

顧客同期：

    GET /k/v1/records.json?app=<アプリID>

上記APIを呼び出す際は、
共通のkintone HTTP通信処理を使用する。

APIごとに認証処理を個別実装してはならない。

各APIは同一のkintone接続先、
同一の認証方式、
同一のタイムアウト・Proxy・SSL検証条件を使用する。

APIパスを画面処理側で直接組み立てない。

API通信処理は、

    接続先生成
    ↓
    認証ヘッダー生成
    ↓
    HTTPリクエスト
    ↓
    HTTPステータス取得
    ↓
    レスポンス本文取得
    ↓
    通信エラー確認
    ↓
    結果分類
    ↓
    構造化された結果を呼び出し元へ返却

の責務を持つ。

API通信処理から画面リダイレクトを行わない。


============================================================
3.8 kintone API
============================================================

kintone REST APIは公式仕様に従って実装する。

認証はログイン名・パスワードを使用し、
サーバー側でX-Cybozu-Authorizationを生成する。

APIトークン認証は使用しない。

パスワード認証では、
「ログイン名:パスワード」をBase64エンコードし、
その結果をX-Cybozu-Authorizationヘッダーへ設定する。

認証ヘッダーは必ず以下の関係を満たす。

    X-Cybozu-Authorization
        =
    Base64(ログイン名 + ":" + パスワード)

認証ヘッダーに以下を設定してはならない。

- `Basic ` を先頭に付加した値
- HTTP Basic認証用のAuthorizationヘッダーの値
- APIトークン
- ログイン名のみ
- パスワードのみ
- JSON化した認証情報
- URLエンコードした認証情報

HTTP Basic認証が必要な環境では、
`Authorization: Basic ...` はkintoneの
`X-Cybozu-Authorization` とは独立したものとして扱う。

主要API：

    接続テスト
    GET /k/v1/app.json?id=nnn

    項目取得
    GET /k/v1/app/form/fields.json?app=nnn

    顧客同期
    GET /k/v1/records.json?app=nnn

API通信処理は共通化し、
接続処理と画面処理を分離する。

kintone APIへ送信するHTTPメソッドは
API仕様に従い、接続テスト・項目取得・顧客同期では
上記GET APIを使用する。

GET APIに対して不要なJSONリクエストボディを付加しない。

HTTPヘッダーはAPI仕様上必要なものに限定する。

少なくとも認証を必要とするkintone REST APIでは、

    X-Cybozu-Authorization

を使用する。

JSONボディを送信するAPI以外では、
不要なContent-Type指定に依存して処理結果を判定しない。

kintoneのHTTPステータスだけでなく、
エラーコード・エラーメッセージを取得して処理する。

302 / 303は成功として扱わない。

通信結果を取得できない場合は成功として扱わない。

HTTP 2xxであっても、レスポンス本文が期待する
kintone APIの形式でない場合は、
無条件に業務処理成功として扱わない。

kintoneからJSON形式のエラーが返された場合は、
少なくとも以下を取得する。

- code
- message
- id（存在する場合）

エラーコードが存在する場合は、
画面上で原因確認に利用できるようにする。

ただし、以下の秘密情報はエラー表示へ含めない。

- kintoneパスワード
- X-Cybozu-Authorization
- Proxy認証情報
- Cookie
- セッションID
- その他の認証情報

kintone APIのエラーコードが取得できた場合、
単に「HTTPエラー」と置き換えず、
kintoneから返されたエラーコードを保持した
構造化された結果として画面処理へ返す。

例えば、

    {
        ok: false,
        category: "api_error",
        status: 4xx,
        code: "CB_xxxx",
        message: "...",
        body: "..."
    }

のように、
HTTPエラーとkintone APIエラーを区別できる構造とする。

通信処理がHTTPレスポンスを受信した後、
レスポンス本文の解析に失敗した場合も、
成功扱いしてはならない。

kintone APIから返却されたHTTP 300番台については、
Locationヘッダーを自動追従して成功扱いしてはならない。

外部通信処理では原則としてHTTPリダイレクトを
自動追従しない。

特に302 / 303を、
認証成功またはAPI成功と解釈してはならない。

X-Cybozu-Authorizationおよびkintoneパスワードを
ブラウザ、URL、ログへ出力しない。

X-Cybozu-Authorizationはブラウザへ返却する必要がない。

kintoneパスワードはHTMLのvalue属性、
JavaScript変数、data属性、hidden input等へ
保存済みの値を出力しない。

接続テスト、項目取得、顧客同期等で
パスワードが必要な場合は、
POSTされた入力値またはサーバー側で保護された
保存値をサーバー側処理にのみ使用する。

kintone APIへのリクエストが失敗した場合、
APIの失敗をアプリケーションの成功として
保存・表示しない。

外部API通信処理は画面遷移を行わず、
構造化された通信結果を呼び出し元へ返す。


------------------------------------------------------------
3.8.1 kintone接続の再現性に関する固定条件
------------------------------------------------------------

kintone接続実装では、以下を必須条件とする。

1. 接続先

    https://<サブドメイン>.cybozu.com

を基本形とする。

2. APIパス

    /k/v1/

を使用する。

3. 認証方式

    X-Cybozu-Authorization

によるパスワード認証を使用する。

4. 認証値

    Base64(ログイン名:パスワード)

を使用する。

5. Basic認証

    Authorization: Basic ...

と
    X-Cybozu-Authorization

を混同しない。

6. APIトークン

    X-Cybozu-API-Token

は本POCでは使用しない。

7. HTTPメソッド

各APIで公式仕様に定められたHTTPメソッドを使用する。

8. リダイレクト

kintoneからの302 / 303を成功扱いしない。

9. 通信結果

HTTPステータスだけではなく、
レスポンス本文と通信エラーを確認する。

10. エラー

kintoneのJSONエラーに含まれる
code / messageを取得する。

11. タイムアウト

接続タイムアウトと読み取りタイムアウトを設定する。

12. Proxy

Proxy未入力時は直接接続する。

13. SSL

SSL証明書検証設定を通信処理へ反映する。

14. 認証情報

パスワードおよびX-Cybozu-Authorizationを
URL、Cookie、HTML、JavaScript、ログへ保存しない。

15. 画面遷移

kintone通信処理自身からLocationヘッダーを発行しない。

16. 成功確定

kintone HTTP通信、レスポンス本文解析、
必要なデータ検証まで完了してから成功を確定する。


------------------------------------------------------------
3.8.2 kintone接続エラーの判定
------------------------------------------------------------

kintone接続では、少なくとも以下を区別する。

- 入力値不正
- 接続先不正
- DNS / 名前解決エラー
- 接続拒否
- 接続タイムアウト
- 読み取りタイムアウト
- TLS / SSLエラー
- HTTP 300番台リダイレクト
- HTTP 4xxエラー
- HTTP 5xxエラー
- kintone APIエラー
- JSON解析エラー
- レスポンス取得不能
- 結果不明

kintone APIから

    {
        "code": "CB_xxxx",
        "message": "..."
    }

形式のエラーが返された場合は、
HTTPステータスとは別に「kintone APIエラー」として扱う。

例えばCB_IL02等のkintoneエラーコードを、
PHPの例外そのものと混同せず、
「kintoneから返されたAPIエラー」として記録・表示する。

ただし、利用者向けメッセージには
秘密情報・認証ヘッダー・内部パス等を含めない。

kintone APIエラー発生時には、
接続成功状態へ更新してはならない。

既に「接続確認済み」であった場合でも、
今回の通信が失敗したことを成功として上書きしない。

接続テストの成功状態は、
実際に対象kintoneアプリへAPI通信を行い、
正常レスポンスを取得した場合のみ設定する。


============================================================
3.6 外部通信
============================================================

kintoneおよびSMTP通信には接続・読み取りタイムアウトを設定する。

外部通信結果はHTTPステータスだけでなく、
レスポンス本文および通信エラーも確認して判定する。

少なくとも以下を区別できる構造とする。

- 正常応答
- 認証エラー
- 設定・入力エラー
- API / SMTPエラー
- HTTPエラー
- リダイレクト
- 接続エラー
- タイムアウト
- レスポンス取得不能
- 結果不明

通信結果不明を成功として扱わない。

外部サービスからHTTP 300番台のレスポンスを受信した場合、
明示的に成功と判定できる仕様がない限り成功扱いしない。

特に302および303は成功扱いしない。

HTTPレスポンスの自動リダイレクト追従は、
外部サービスの302 / 303を成功レスポンスとして
誤認する可能性があるため、原則として行わない。

外部サービス通信処理は、
HTTPレスポンスを受信して結果を確定する責務を持つ。

外部サービス通信処理から画面遷移を直接実行しない。


============================================================
3.7 POST処理と画面遷移
============================================================

フォームPOST処理、外部サービス通信、画面遷移を分離する。

基本処理：

    POST受信
      ↓
    入力値検証
      ↓
    業務処理・保存・外部通信
      ↓
    外部通信結果判定
      ↓
    処理結果確定
      ↓
    必要な状態保存
      ↓
    結果表示または画面遷移

kintone処理では、
HTTPレスポンスおよびレスポンス本文を確認して
処理結果を確定してから画面表示または遷移を行う。

パスワードを含むPOSTを再送するために、
パスワードをURLのGETパラメータへ変換してはならない。

パスワードを303リダイレクト先へ引き継いではならない。


============================================================
3.10 秘密情報
============================================================

秘密情報には、kintoneパスワード、
SMTPパスワード等の外部サービス認証情報を含む。

kintoneパスワードのように、
外部サービス接続時に元の値が必要となる秘密情報は、
password_hash()による一方向ハッシュ保存を使用しない。

サーバー側で復号可能な認証付き暗号化方式により保護する。

平文保存は禁止する。

暗号鍵はアプリケーションデータとは分離して管理し、
サーバー環境変数等のサーバー側設定から取得する。

暗号鍵そのものをindex.phpへハードコードしてはならない。

暗号鍵が利用できない場合は処理を失敗として扱い、
秘密情報を保存しない。

ただし、接続テスト・項目取得・顧客同期等の
単一リクエスト内でPOSTされたkintoneパスワードについては、
当該処理に必要な範囲でのみメモリ上に保持して使用してよい。

POSTされたパスワードを保存済み設定として扱う場合は、
必ず本要件で規定した認証付き暗号化保存方式を使用する。

保存済みパスワードをHTMLのvalue属性、
hidden input、JavaScript、Cookie、URLへ再出力しない。


============================================================
受入確認への追加
============================================================

kintone接続について、以下を満たすことを確認する。

- kintoneの実環境へ接続できる。
- 正しいサブドメインからAPI接続先を生成できる。
- URL付きのサブドメイン入力を正規化できる。
- `.cybozu.com` の二重付加が発生しない。
- 顧客管理アプリIDを正しくAPIへ渡せる。
- 接続テストで `/k/v1/app.json?id=nnn` を使用する。
- 項目取得で `/k/v1/app/form/fields.json?app=nnn` を使用する。
- 顧客同期で `/k/v1/records.json?app=nnn` を使用する。
- kintone REST APIのパスワード認証を使用する。
- `X-Cybozu-Authorization` を使用する。
- `X-Cybozu-Authorization` の値が
  `Base64(ログイン名:パスワード)` になっている。
- `Authorization: Basic ...` と
  `X-Cybozu-Authorization` を混同していない。
- APIトークン認証へ勝手に切り替わっていない。
- GET APIへ不要なPOSTボディを送信していない。
- HTTP 2xx以外を成功扱いしない。
- HTTP 302 / 303を成功扱いしない。
- kintoneのレスポンス本文を取得している。
- kintoneのcode / messageを取得している。
- CB_IL02等のkintone APIエラーを判別できる。
- APIエラー発生時に接続成功状態へ変更しない。
- 通信エラーをAPI成功として保存しない。
- 接続タイムアウトを設定している。
- 読み取りタイムアウトを設定している。
- Proxy設定を通信へ反映している。
- SSL証明書検証設定を通信へ反映している。
- X-Cybozu-Authorizationを画面へ出力しない。
- kintoneパスワードを画面へ出力しない。
- kintoneパスワードをURLへ出力しない。
- kintoneパスワードをCookieへ保存しない。
- kintoneパスワードをlocalStorageへ保存しない。
- kintoneパスワードをsessionStorageへ保存しない。
- kintoneパスワードをJavaScriptへ渡さない。
- kintoneパスワードをhidden inputへ再設定しない。
- kintoneパスワードをログへ出力しない。
- API通信処理から直接Locationヘッダーを発行しない。
- 外部サービスの302 / 303と、
  アプリケーション自身の303を区別している。
- 外部通信結果確定前に成功表示しない。
- 外部通信結果確定前に成功保存しない。
- 外部通信結果確定前に303を発行しない。
- 通信結果不明を成功扱いしない。
- エラー発生時に白画面にならない。
- kintone API通信処理と画面処理が分離されている。


============================================================
実装時の禁止事項
============================================================

kintone接続について、以下を実装してはならない。

- APIトークン認証への無断変更
- kintoneパスワードをAuthorizationヘッダーへ直接流用
- HTTP Basic認証とkintoneパスワード認証の混同
- `Basic <Base64(...)>` をX-Cybozu-Authorizationへ設定
- X-Cybozu-AuthorizationをURLへ付加
- パスワードをGETパラメータへ付加
- パスワードをCookieへ保存
- パスワードをHTMLへ出力
- パスワードをJavaScriptへ出力
- パスワードをlocalStorageへ保存
- パスワードをsessionStorageへ保存
- パスワードをログへ出力
- APIレスポンスの302 / 303への無条件追従
- HTTPステータスだけによる成功判定
- kintone APIエラーの握り潰し
- APIエラー発生時の成功状態保存
- 通信処理からの直接画面リダイレクト
- 接続先URLのユーザー入力による任意ホスト化
- APIパスのユーザー入力による任意変更
- CB_IL02等のAPIエラーをPHP内部エラーとしてのみ扱うこと


============================================================
改訂後の実装原則
============================================================

本システムのkintone接続は、

    入力値検証
        ↓
    サブドメイン正規化
        ↓
    固定されたkintone API URL生成
        ↓
    ログイン名:パスワード生成
        ↓
    Base64エンコード
        ↓
    X-Cybozu-Authorization生成
        ↓
    kintone REST API通信
        ↓
    HTTPステータス確認
        ↓
    レスポンス本文取得
        ↓
    kintoneエラーコード・メッセージ確認
        ↓
    成功 / APIエラー / HTTPエラー /
    リダイレクト / 接続エラー /
    タイムアウト / 結果不明 の分類
        ↓
    構造化された通信結果を返却
        ↓
    呼び出し元で成功・失敗を確定
        ↓
    必要な状態保存
        ↓
    結果表示またはアプリケーション自身の303

という責務分離を維持する。

kintone通信処理は、通信そのものの責務を持ち、
画面遷移・画面表示の責務を持たない。

また、kintone APIの仕様上必要な認証形式を
実装者の判断で変更してはならない。

特にパスワード認証については、

    X-Cybozu-Authorization:
    Base64(ログイン名:パスワード)

という具体的な通信条件を本要件の固定仕様とする。


============================================================
最終確認
============================================================

以上の要件は、既存の業務要件・実装要件・画面構成を変更せず、
kintone接続について実装者間の解釈差を減らし、
同一条件で再実装した場合にも同じ接続方式を再現できることを
目的として追加する。

単純な局所修正ではなく、
本要件定義全体との整合性を保ったindex.phpとして実装する。

kintone接続については、
「公式仕様に従う」という記述だけでなく、
本章で明示した認証方式、URL形式、HTTPメソッド、
エラー判定、リダイレクト処理、秘密情報保護、
通信処理と画面処理の分離を満たすこと。

以上を実現するためのindex.php全文をコードブロックに表示する。
